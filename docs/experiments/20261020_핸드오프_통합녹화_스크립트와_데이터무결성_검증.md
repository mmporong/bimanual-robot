# 물따르기→컵배치 통합 녹화 스크립트와 데이터 무결성 검증 (트러블슈팅 기록)

최초 작성 2026-10-20 · 조작(IL) 담당자 작성

## 0. 한 줄 요약

물따르기와 컵배치를 **두 개의 `lerobot-record`로 따로 실행**하던 워크플로가, 두 번째
프로세스가 다시 연결을 맺는 구간에서 계속 `COM15 motor ID 6(왼팔 그리퍼) 없음`으로
실패했다. 이 **재연결 지점 자체를 없애려고**, 한 프로세스가 연결을 한 번만 맺고 물따르기→
(끊김 없이)컵배치를 이어 녹화한 뒤 두 데이터셋을 각각 저장·업로드하는 통합 스크립트
[`tools/recording/record_handoff_combined.py`](../../tools/recording/record_handoff_combined.py)를
만들었다. 하드웨어를 붙이기 전에 API를 오프라인으로 전수 검증해 **실행 전·중에 실제
버그 4개**(카메라 설정 타입, import 출처, rerun 초기화 누락, 이미지 라이터 스레드 미설정)를
잡았고, 이미 수집된 9+9개와 **앞으로 모을 데이터가 추론을 망칠 요소가 없는지** 스키마·
타임스탬프·관절 연속성·카메라까지 데이터로 직접 검증했다.

---

## 1. 동기 — 재연결 지점에서 반복되던 왼팔 그리퍼 연결 실패

- 물따르기 녹화(1 프로세스) 종료 후, 컵배치 녹화(2 프로세스)를 시작하면 연결 단계에서
  `FeetechMotorsBus motor check failed on port 'COM15': Missing motor IDs: - 6`
  (왼팔 그리퍼, ID 6)이 **반복**됐다. 그 사이 핸드오프를 위해 팔로워가 컵을 쥔 채
  유지돼야 해서, 재연결 실패는 그 라운드를 통째로 날렸다.
- 여러 가설을 세우고 **데이터·코드로 배제**했다:
  - "`--dataset.push_to_hub=false`일 때만 난다" → `lerobot_record.py`의 teardown을
    읽어보니 `robot.disconnect()`는 플래그와 무관하게 `push_to_hub()`보다 **항상 먼저**
    실행된다. 직접적 코드 인과 없음 → 기각.
  - "업로드 대기가 사라져 포트 해제가 레이스" → 사용자가 수동 지연을 2번 넣어 재현 →
    둘 다 같은 실패. 레이스 가설 기각.
  - 남은 유력 가설: **재연결 그 동작 자체의 취약성 + 긴 세션의 누적 부하**(완전히
    격리 확정하진 못함). 이 지점을 없애는 게 가장 확실한 대응이라고 판단했다.
- (기록) 이 과정에서 검증 안 된 보조 스크립트(`hold_leader_pose.py` 등)를 라이브 수집에
  투입해 에피소드를 날린 적이 있다. 라이브 데이터 수집에는 **검증된 경로만** 넣는다는
  교훈을 남겼다.

## 2. 설계 — 연결을 한 번만, 명령어 1회 = 1라운드

[`record_handoff_combined.py`](../../tools/recording/record_handoff_combined.py):

- `BiSOFollower`/`BiSOLeader`를 **프로세스 시작 시 한 번만** 연결한다. 물따르기→컵배치의
  **핸드오프 구간에서 끊지 않으므로**, 1절의 재연결 실패 지점이 원천 제거된다.
- **명령어 1회 = 1라운드, 저장은 원자적(atomic)**: 물따르기(최대 100초) → `→`/`n` →
  끊김 없이 컵배치(최대 50초) → `→`/`n`. **두 단계가 모두 `→`로 완료됐을 때만**
  그제서야 두 에피소드를 **함께 저장**하고 HF에 업로드한다. 어느 단계든 중간에
  `ESC`/`q`로 끊으면(= `→` 안 누름) **물따르기까지 포함해 둘 다 폐기**된다 — 로컬·HF
  어디에도 아무것도 저장/업로드되지 않는다. 다음 라운드는 병·컵 재배치 후 같은 명령을
  다시 실행(로컬 root가 있으면 자동 `resume`).
- **왜 원자적인가**: 핸드오프 한 라운드는 '물따르기 + 컵배치'가 한 단위다. 물따르기를
  저장한 직후 컵배치를 중단하면 **짝 없는 물따르기 에피소드**가 남아 두 데이터셋의
  개수가 어긋난다(실제로 이 세션에서 그렇게 어긋난 에피소드를 사후에 지워 맞춘 일이
  있다). `run_phase()`가 저장을 하지 않고 버퍼만 채우도록 바꾸고, 두 단계 결과를 보고
  `main`이 `save_episode()`(둘 다) 또는 `clear_episode_buffer()`(둘 다)를 일괄 호출하게
  해서, **물따르기/컵배치 개수가 항상 1:1로 맞고 반쪽 라운드가 저장되지 않는다.**
- `←`/`r`은 각 단계 안에서 **대기 없이 즉시 재녹화**(패치된 `record_loop()`의
  `exit_early` 즉시 감지 경로 그대로). 패치된 `record_loop()`를 그대로 재사용해
  카메라 타임아웃 방어·경과시간 로그도 자동 상속한다.
- 카메라 인덱스는 실행 직전 `resolve()`로 재탐색
  (→ `20261020_카메라_인덱스_안정화와_뎁스_프레임_검증.md`).

### 2.1 task 문구 — 재설계를 고려했으나 기존 데이터와의 일관성 위해 원복

핸드오프 안정화를 위해 "물따르기 끝에 컵을 완전히 놓았다가 살짝 다시 쥐고, 컵배치
시작 때 세게 다시 쥔다"는 **동작 재설계**를 한때 반영했다. 그러나 이미 수집된 9+9개가
**원래 설계("컵을 쥔 채 유지" / "쥐고 있는 컵을 배치")**로 녹화돼 있어, 텍스트 입력을
그 데이터와 **글자 단위로 일치**시키는 쪽으로 원복했다(혼용 시 구조적 동작 불일치).
`POUR_TASK`/`PLACE_TASK`가 저장된 info/tasks와 정확히 일치함을 확인했다.

## 3. 실행 전·중에 잡은 실제 버그 4개

하드웨어를 붙이는 스크립트라, 넘기기 전 소스를 읽어 API를 전수 대조했고 아래를 잡았다:

1. **카메라 설정 타입** — `SOFollowerConfig.cameras: dict[str, CameraConfig]`에 평범한
   중첩 dict를 넣었다(= CLI 문자열 파서에서만 통하는 형식). `OpenCVCameraConfig(...)`
   **인스턴스**로 고쳐야 파이썬 직접 구성에서 동작. (실행 전 소스 읽고 수정)
2. **import 출처** — `combine_feature_dicts`를 `lerobot.datasets`에서 import했으나 실제
   위치는 `lerobot.utils.feature_utils`. 그대로면 실행 즉시 `ImportError`. (원본
   `lerobot_record.py` 대조로 수정)
3. **rerun 초기화 누락** — `record_loop(display_data=True)`은 호출 전 `init_visualization()`
   (rerun 세션 생성)이 선행돼야 하는데 빠져서, 첫 틱에 "rerun.init 먼저 호출하라"는
   `ValueError`로 죽었다. 연결 직후 `init_visualization`, teardown에 `shutdown_visualization`
   추가(원본 `record()`의 호출 위치 그대로). **이때 저장된 데이터는 없음**(`save_episode`
   전에 예외)을 코드로 확인.
4. **이미지 라이터 스레드 미설정 → FPS 저하** — `LeRobotDataset.create()/resume()`에
   `image_writer_threads`를 안 넘기면 `AsyncImageWriter`가 아예 안 켜지고(비동기 저장
   미동작), 매 프레임 PNG 저장이 **메인 제어 루프에서 동기로** 실행돼 27Hz로 떨어졌다
   ("running slower ... CPU starvation" 경고). 원본 CLI와 동일하게 `카메라수 × 4`
   스레드를 넘기도록 수정.

추가로 원본 CLI가 `resume` 시 하는 `sanity_check_dataset_robot_compatibility`(스키마
불일치 시 한 프레임 전에 큰 소리로 중단)를 스크립트에도 넣었다.

## 4. 데이터 무결성 검증 — "이미 모은 것·앞으로 모을 것이 추론을 망치지 않는가"

수집자가 "정상이라 믿은 데이터로도 추론이 안 됐던 적이 있다, 놓친 게 없는지 꼼꼼히
보라"고 요구해, 추측 대신 **저장된 데이터와 스크립트를 직접 검증**했다.

- **스키마 글자단위 일치** — 하드웨어 없이 로봇 객체를 오프라인 구성해 스크립트가 만들
   feature를 저장된 `info.json`과 대조: 키·순서(action, observation.state, left_wrist,
   top, right_wrist)·dtype·shape·관절명 **차이 0**. 기존 9+9개와 섞어 학습해도 정합.
- **데이터셋 내부 정합** — `file-005`가 빠져 손상을 의심했으나, 삭제 후 `episode_index`가
   0~8로 재번호되고 파일명만 옛 번호(`file-006`이 ep5)로 남은 것. 프레임 총합
   (물따르기 22118 / 컵배치 7547)이 `info.json`과 정확히 일치 → 손상 아님.
- **타임스탬프는 합성값** — `timestamp = frame_index / fps`로 **항상** 균등 간격. 따라서
   **FPS가 느려진 채 저장된 take는 사후에 느린지 알 수 없다**(그 에피소드만 30fps로
   라벨되어 빨리감기처럼 재생·속도 과대). 운영 규칙: 녹화 중 "CPU starvation" 경고가
   그 take 내내 **반복**되면 저장하지 말고 `←`로 다시 찍는다. (3절 4번 수정으로 재발
   확률은 크게 낮아짐.)
- **관절 연속성** — 카메라 타임아웃 방어 패치는 타임아웃 틱의 녹화를 건너뛰므로 시간
   구멍(큰 점프)을 낼 수 있다. 전 에피소드의 프레임 간 관절 L2 변화 최대가 **일관되게
   ~4.1°**로, 몇 초짜리 구멍이 냈을 15~40° 점프가 **없다** → 이 9+9개엔 구멍 없음.
- **카메라 유효 FPS·싱크** — 별도 문서(`20261020_카메라_인덱스_안정화...`) 6절에서
   18개 영상 디코딩으로 확인(유효 FPS 에피소드 간 일관, 뎁스 "멈춤"은 재생 아티팩트,
   싱크는 `frame_index`로 구조 보장).

**판정**: 저장된 9+9개와 이 스크립트로 모을 데이터 자체에는 추론을 망칠 결함이 없다.
남는 리스크는 "반복 CPU starvation take 버리기", "손목캠 케이블 안 바꾸기", "롤아웃
시작 자세를 학습 분포 안으로"(10-16 OOD 사건) — 모두 **데이터 결함이 아니라 운영
습관**의 영역이다.

## 5. 라운드당 한 번 vs 연속 — 시간 오버헤드

- 라운드당 한 번 방식의 **순수 오버헤드 ≈ 20~40초**: 재연결(로그 기준 ~7초) +
  그 라운드 **증분** HF 업로드(~10~30초, 이미 올라간 에피소드는 재업로드 안 함).
- 한 라운드 실제 작업 ≈ 2~3분(물따르기 ~80초 + 컵배치 ~30초 + 수동 재배치) 대비
  **약 10~20%**. 영상 인코딩 비용은 에피소드당 1회로 두 방식이 동일(차이 아님).
- 장점: 매 라운드가 끝나는 즉시 로컬+HF까지 안전 확정. 라운드를 많이 돌릴 때 속도가
  더 중요하면, 한 번 연결해 N라운드 찍고 마지막에 한 번만 업로드하는 **연속 모드**로
  전환 가능(크래시 시 미업로드분은 로컬에만 남아 나중에 올림).

## 6. 교훈

- **실패하는 "동작"이 있으면, 그 동작을 더 잘하게 만들기 전에 없앨 수 있는지 먼저 본다**
  (재연결 자체를 제거).
- **하드웨어 붙이는 스크립트는 넘기기 전에 소스로 API 전수 대조.** 이번에 실행 전·중
  버그 4개를 실데이터 손실 없이 잡았다.
- **"정상이라 믿었다"는 검증이 아니다.** 스키마·타임스탬프·연속성·싱크를 각각 측정
  가능한 실패 모드로 쪼개 데이터로 턴다. 단, 합성 타임스탬프처럼 **사후 검출이 원천적으로
  안 되는 모드**는 정직하게 인정하고 운영 규칙으로 막는다.
