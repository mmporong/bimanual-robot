# GR00T N1.7을 NVIDIA Brev A100에서 SmolVLA·π0와 같은 조건으로 학습 (실험 기록)

2026-10-26 작업이다. 차체 결합 데이터로 GR00T N1.7 모델 8개(2 task × 20·40·60·80개)를 학습한다.

## 0. 한 줄 요약
- 학교 서버(RTX 4090 24GB)에서는 GR00T가 메모리 때문에 학습되지 않았다. 그래서 NVIDIA Brev의 A100 80GB 인스턴스를 빌려 학습했다.
- 학습은 SmolVLA·π0와 같은 lerobot 커밋(d20a453), 같은 조기 종료 패치, 같은 데이터·검증셋·증강·batch·최대 step으로 맞췄다.
- 물따르기 80은 17,500 step 끝까지 학습했고 최저 eval_loss는 **0.0147**(마지막 step)이다.
- 컵배치 80은 3,000 step에서 **디스크가 가득 차 학습이 죽었다**. 체인이 끝난 뒤 다시 학습한다(4절).

## 1. 환경

| 항목 | 값 |
|---|---|
| 인스턴스 | Brev `groot-chassis` (Crusoe A100 80GB × 1, 중지 가능 유형) |
| 드라이버 | 565 (CUDA 12.7) → torch는 cu126 빌드로 교체 |
| 모델 | `nvidia/GR00T-N1.7-3B` (`--policy.type=groot`). 현재 lerobot은 N1.5를 지원하지 않는다 |
| 학습 파라미터 | 전체 3.1B 중 1.62B (lerobot 기본: 언어·시각 백본 고정, projector·diffusion head·vlln 학습) |
| GPU 메모리 | 약 36GB (batch 8, 증강 켬) |
| 속도 | 약 2.15~2.3 step/s, eval 1회 약 5.6분 |
| 비용 | 사전 견적은 최악 약 29시간·약 $60이었고, 사용자가 상한 $100을 승인했다 |

- 환경 구성: [`tools/training/brev_groot_setup.sh`](../../tools/training/brev_groot_setup.sh)
- 학습 체인: [`tools/training/chain_groot_chassis.sh`](../../tools/training/chain_groot_chassis.sh)
- 조기 종료 패치: [`tools/training/lerobot_train_earlystop_server_d20a453.patch`](../../tools/training/lerobot_train_earlystop_server_d20a453.patch)

### 설치 중 해결한 문제
1. **cuDNN 초기화 실패**
   - 증상: torch를 `--no-deps`로 cu126 빌드로 바꾸자 conv에서 `CUDNN_STATUS_NOT_INITIALIZED`가 났다.
   - 원인: nvidia-cudnn 등 의존 패키지와 짝이 맞지 않았다.
   - 해결: 의존성까지 함께 재설치했다.
2. **numpy 버전 충돌**: 재설치 과정에서 numpy가 2.3 이상으로 올라가 lerobot과 충돌했다. `numpy>=2.0,<2.3`으로 고정했다.
3. **데이터 전송**
   - 학교 서버에서 tar로 보내려 했지만, 출력에 `du` 결과가 섞여 묶음이 깨졌다. 파일 단위 전송은 너무 느렸다.
   - 결국 Brev에서 HF의 v1(60개)·part2(20개)를 직접 받아 -80/-40/-20 부분집합을 다시 만들었다.
   - 프레임 수와 액션 값을 서버 데이터와 대조해 같음을 확인했다.
4. **WSL 네트워크**
   - Brev CLI는 WSL(Ubuntu-22.04)에 있다. WSL 네트워크가 끊겨 `C:\Users\USER\.wslconfig`에 `networkingMode=mirrored`를 넣었다.
   - 되돌리려면 이 파일을 지운다.

위 1·2번 해결은 `brev_groot_setup.sh`에 반영했다.

## 2. 학습 조건 (SmolVLA·π0와 같음)
- 검증셋: 모든 크기에서 v1 54~59번 6개
- eval_split: 80개 0.07, 60개 0.1, 40개 0.15, 20개 0.3
- 최대 step: 물따르기 17500 / 13000 / 8500 / 4000, 컵배치 19500 / 14500 / 9500 / 4500 (80/60/40/20)
- 500 step마다 eval, 3회 연속 개선이 없으면(1e-4 미만) 조기 종료
- batch 8, 이미지 증강 켬(학습 때만 적용, 데이터 수는 늘지 않음)
- 학습 순서: 80 → 60 → 40 → 20
  - 예산이 중간에 끊겨도 중요한 결과부터 남도록 했다.
- 최적 체크포인트는 HF private `jun-seo/<모델명>_<step>S`에만 올린다. 하나가 약 12GB라 PC로는 받지 않는다(2026-10-26 결정, 처음 받은 물따르기 80 사본도 지웠다).
- 체인이 끝나면 PC의 감시 스크립트가 `brev stop groot-chassis`로 인스턴스를 중지한다. 중지하면 GPU 과금이 멈추고 디스크는 보존된다.

## 3. 결과 (2026-10-26 19시 기준)

| 모델 | 최대 step | 결과 | 최적 step | 최저 eval_loss |

| 컵배치 80 | 19500 | **3000 step에서 디스크 부족으로 중단** | (3000) | (0.0646, 학습 미완) |
| 물따르기 60 | 13000 | 진행 중 | — | — |

- 물따르기 80의 eval 기록: 500:0.1213 → 4000:0.0499 → 8000:0.0291 → 12000:0.0214 → 16000:0.0152 → 17500:0.0147
  - 마지막까지 계속 내려가서 조기 종료가 걸리지 않았다. step을 더 주면 더 내려갈 가능성이 있다.
- 물따르기 80은 HF `jun-seo/water_pour_chassis_groot_80_17500S`(11.7GB, `model.safetensors` 포함)에 올렸다.
- eval_loss는 모델마다 계산 방식이 달라 SmolVLA·π0와 직접 비교하지 않는다. 비교는 실물 롤아웃으로 한다.

## 4. 사고: 컵배치 80이 디스크 부족으로 죽었는데 "exit 0"으로 기록됨

**증상**
- 체인 로그에는 `cup_place_chassis_groot_80 training finished (exit 0)`, 최적 3000 step으로 남았다.
- 계획은 19,500 step이었지만 3,000 step에서 끝났다.

**원인 1: 디스크 부족**
- 학습 로그에 3000 step 체크포인트 저장 중 `safetensors ... No space left on device (os error 28)`가 찍혀 있었다.
- 디스크 124GB 중 데이터·캐시·conda가 약 47GB를 쓴다.
- GR00T 체크포인트는 하나에 **24GB**이고, 그중 학습 재개용 상태가 약 12GB다.
- 앞 모델(물따르기 80)의 최적 체크포인트 24GB를 업로드 뒤에도 지우지 않았다. 여기에 컵배치 80의 최적·최신·저장 중 체크포인트가 겹쳐 디스크가 넘쳤다.

**원인 2: 종료 코드 기록 오류**
- `echo "$(date -Iseconds) ... (exit $?)"`에서 `$(date)`가 먼저 실행되면서 `$?`를 0으로 덮어썼다.
- π0 체인도 같은 코드였다.

**영향**
- 업로드 단계가 폴더 존재만 확인해서, HF `jun-seo/cup_place_chassis_groot_80_3000S`에는 `config.json`만 올라갔다(가중치 없음).
- PC로 받은 폴더도 비어 있어 지웠다.
- **HF의 이 빈 저장소는 지우지 않았다.** HF 데이터·모델은 건드리지 않는다는 규칙 때문이다. 정리 여부는 사용자가 정한다.

**조치 (Brev에 바로 적용)**
1. 물따르기 80의 Brev 출력을 지웠다(24GB). HF 업로드와 PC 사본을 확인한 뒤에 지웠다. 여유 공간은 30GB에서 54GB가 됐다.
2. `prune_ckpts.py`가 "최적이지만 최신이 아닌" 체크포인트의 `training_state`를 지운다. 최대 동시 사용량이 72GB에서 60GB로 줄어든다.
3. `rerun_place80.sh`
   - 체인이 끝나면(`chain all done`) 컵배치 80을 `cup_place_chassis_groot_80_rerun`으로 다시 학습한다.
   - 종료 코드는 바로 변수로 받는다.
   - 업로드 전에 `model.safetensors`가 있는지 확인한다.
   - 끝나면 `rerun all done`을 남긴다.
4. PC 감시 스크립트가 `chain all done` 대신 `rerun all done`을 기다렸다가 인스턴스를 중지하도록 바꿨다.

**저장소 스크립트 수정 (다음 학습부터)**
- `chain_groot_chassis.sh`·`chain_pi0_chassis.sh`
  - 종료 코드를 정확히 기록한다.
  - `model.safetensors`가 있을 때만 업로드한다.
- `chain_groot_chassis.sh`: 업로드가 끝난 모델의 출력 폴더를 지운다.
- `prune_ckpts.py`: `training_state`를 정리한다.
