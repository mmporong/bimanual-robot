# 노트북(RTX 5050 8GB)에서 GR00T·π0·ACT 80개 모델 로컬 추론 점검 (실험 기록)

2026-10-28 작업. 데이터 80개로 학습한 GR00T·π0·ACT 모델(과제당 1개씩, 총 6개)을 노트북에 내려받았다. 그리고 팔 없이 로딩과 추론만 시험했다.
SmolVLA 80은 이미 로컬에서 롤아웃하고 있던 모델이라 제외했다.

## 0. 한 줄 요약

| 모델 | 로컬 롤아웃 | GPU 메모리 | 추론 1회(첫 회 제외) | 비고 |
|---|---|---|---|---|
| GR00T N1.7 | **가능** | 6.4GB | 약 0.46초 (40스텝 묶음) | `rollout_handoff.py`가 bf16으로 불러오도록 고침 |
| ACT | **가능** | 0.3GB | 약 0.04초 (100스텝 묶음) | 그대로 동작 |
| π0 | **불가** | 8.9GB (로딩 직후) | — | GPU 메모리 초과 + 서버·로컬 lerobot 버전 차이로 추론 오류 |

- 시험 조건: 팔·카메라 없이 무작위 이미지와 0 상태로 추론 3회를 돌렸다. 실제 동작 품질은 확인하지 않았다.
- 첫 추론은 10~40초 걸린다(GPU 커널 준비). 롤아웃 시작 직후 잠깐 멈춰 있어도 정상이다.

## 2. GR00T: 패키지 설치와 bf16 로딩

### 증상 1 — `ImportError: 'diffusers' is required`
- 로컬 so101_env에 GR00T용 추가 패키지가 없었다.
- 아래처럼 lerobot `groot` extra의 버전 범위로 필요한 것만 설치했다.
  ```
  python -m pip install "diffusers>=0.38.0,<0.40.0" "peft>=0.18.0,<1.0.0" "timm>=1.0.0,<1.1.0" "dm-tree>=0.1.8,<1.0.0"
  ```
  설치된 버전: diffusers 0.39.0, peft 0.21.2, timm 1.0.30, dm-tree 0.1.10
- 먼저 `--dry-run`으로 torch(2.11.0+cu128)와 transformers(5.5.4)가 바뀌지 않는 것을 확인했다.
- `pip install 'lerobot[groot]'`는 쓰지 않았다. 다른 의존성까지 올릴 수 있어서다.

### 증상 2 — GPU 메모리 부족 또는 매우 느린 추론
- **확인한 원인**: 체크포인트 설정이 `model_params_fp32: true`이고, Qwen3-VL 백본(1.52B)이 fp32로 만들어진다.
  - `--policy.model_params_fp32=false`만 주면 action head(1.62B)는 bf16이 되지만, 백본은 fp32로 남아 GPU 9.35GB가 된다.
  - 8GB를 넘는 부분은 Windows 공유 메모리로 넘친다. 그래서 추론 1회가 2.1초였고, 한 번은 CUDA OOM이 났다.
  - 장치를 cuda로 두면 lerobot이 12.6GB fp32 state dict를 GPU로 바로 읽어 순간 사용량이 더 커진다.
- **조치**: `tools/rollout/rollout_handoff.py`에 자동 처리를 넣었다(파일 머리말 6번).
  - 정책 `config.json`의 `type`이 `groot`이면 `GrootPolicy.from_pretrained`를 감싼다.
  - CPU에서 불러오고 → 모델 전체를 bf16으로 바꾸고 → 원래 장치(cuda)로 옮긴다.
  - 결과: GPU 6.31GB, 추론 피크 6.42GB, 추론 1회 약 0.46초. 물따르기 80으로 측정했다.
  - 컵배치 80도 같은 경로로 로딩과 출력이 정상이었다. 다만 측정 중 다른 롤아웃이 GPU를 함께 써서 속도는 재지 못했다.
  - `--groot.fp32`를 주면 이 처리를 끈다.
- **정밀도 영향**: 학습 forward도 `torch.autocast(bfloat16)` 안에서 돌았다. 그래서 행렬 계산 정밀도는 같고, 저장된 fp32 가중치가 bf16으로 반올림되는 차이만 있다.
- 실물 롤아웃에서의 동작 품질은 아직 확인하지 않았다.

## 3. ACT
- 추가 조치 없이 동작한다. GPU 0.3GB, 추론 약 0.04초.
- ACT는 문장(`--task`)을 입력으로 쓰지 않는다. 명령에 넣어 둬도 무시된다.

## 4. π0: 로컬 롤아웃 불가

다음 순서로 막혔다.

1. **`DecodingError: text_tokenizer_name are not valid for PI0Config`**
   - 원인: 학교 서버 lerobot이 로컬(커밋 `7e241bd6`, 2026-08)보다 새 버전이다. 새 버전 설정에만 있는 항목이 config에 들어 있다.
   - 값은 `google/paligemma-3b-pt-224`로, 로컬 기본값과 같다. 그래서 **로컬 사본의** `config.json`에서 이 항목을 지웠다.
2. **`tokenizer is not a local folder`**
   - 원인: 새 버전은 토크나이저를 모델 폴더 안 `tokenizer/`에 저장하고, 전처리 설정에 상대 경로 `"tokenizer"`로 적는다. 옛 버전은 이 경로를 현재 작업 폴더 기준으로 찾는다.
   - **로컬 사본의** `policy_preprocessor.json`에서 이 값을 절대 경로로 바꿨다.
   - 위 두 파일의 원본은 같은 폴더에 `*.server_original.json`으로 남겼다. HF 원본은 건드리지 않았다.
3. **`RuntimeError: The size of tensor a (32) must match the size of tensor b (12)`**
   - 원인 추정(미확인): 새 버전은 action을 32차원으로 채워 학습하고 출력 단계에서 잘라내는데, 옛 버전은 이 처리 위치가 다른 것으로 보인다.
   - 고치지 않았다.
4. **GPU 메모리**: 로딩 직후 8.89GB로, 8GB GPU를 이미 넘는다. 파라미터가 bf16과 fp32로 섞여 있다.
   - 2026-09-23에도 같은 노트북에서 π0 추론이 1회 최대 7.4초라 롤아웃이 불가능했다([pi0 서버 원격 추론 기록](20260923_pi0_서버원격추론_실험기록.md)).

**결론**: π0는 노트북에서 돌리지 않는다. 실물 평가를 하려면 다음 중 하나가 필요하다.
- 서버 원격 추론: lerobot `async_inference`의 `policy_server`(학교 서버, 같은 lerobot 버전) + `robot_client`(노트북)를 SSH 터널로 연결한다(2026-09-23 기록의 방식).
  - 이 경로는 `rollout_handoff.py`의 시작·끝 자세, 자동 종료, 그리퍼 풀기를 쓰지 못한다. 이 부분은 따로 맞춰야 한다.
- 또는 로컬 lerobot을 서버와 같은 버전으로 올린다. 메모리 문제는 그대로 남는다.

## 5. 실행 명령 (GR00T·ACT)
SmolVLA 80 명령과 같고, `--policy.path`만 바꾼다. 물따르기 예:
```
"C:\Users\USER\miniconda3\envs\so101_env\python.exe" tools\rollout\rollout_handoff.py --strategy.type=base --policy.path="C:\Users\USER\lerobot-training\outputs\water_pour_chassis_groot_80\checkpoints\017500\pretrained_model" --policy.device=cuda --robot.type=bi_so_follower --robot.id=arms --robot.calibration_dir=calibration\bi_follower --robot.left_arm_config.port=COM15 --robot.left_arm_config.gripper_protection=true --robot.left_arm_config.disable_torque_on_disconnect=false --robot.left_arm_config.max_relative_target=15 --robot.left_arm_config.cameras="{ wrist: {type: opencv, index_or_path: {left}, width: 640, height: 480, fps: 30} }" --robot.right_arm_config.port=COM16 --robot.right_arm_config.disable_torque_on_disconnect=false --robot.right_arm_config.max_relative_target=15 --robot.right_arm_config.cameras="{ wrist: {type: opencv, index_or_path: {right}, width: 640, height: 480, fps: 30} }" --robot.cameras="{ top: {type: opencv, index_or_path: {depth}, width: 640, height: 480, fps: 30, mirror: true} }" --task="Pick up the cup with the left arm, pick up the water bottle with the right arm, pour water from the bottle into the cup, set the bottle down to the right of where it was picked up, move the cup onto the robot chassis with the left arm, and keep holding the cup." --duration=100 --display_data=true --start.pose=pour --end.pose=final --end.auto=pour
```

`--policy.path`를 바꿀 경로:

| 모델 | 경로 |
|---|---|
| GR00T 물따르기 | `...\water_pour_chassis_groot_80\checkpoints\017500\pretrained_model` |
| GR00T 컵배치 | `...\cup_place_chassis_groot_80\checkpoints\013000\pretrained_model` |
| ACT 물따르기 | `...\water_pour_chassis_act_80\checkpoints\008500\pretrained_model` |
| ACT 컵배치 | `...\cup_place_chassis_act_80\checkpoints\003500\pretrained_model` |

컵배치는 다음 플래그를 쓴다.
```
--task="While holding the cup already loaded on the robot chassis with the left arm, move it to the table and place it down." --duration=50 --display_data=true --end.pose=place_end --end.auto=place
```
컵배치에는 `--start.pose`를 주지 않는다.

**주의**: 다른 롤아웃이 GPU를 쓰는 중에 GR00T를 띄우지 않는다. 함께 돌면 GPU 메모리가 모자라 느려진다(측정 중 실제로 추론이 8~10초로 늘었다).

## 6. 왜 GR00T는 노트북에서 되고 π0는 안 되나 (학습 메모리와 추론 메모리의 차이)

HF 파일은 GR00T가 더 크다(12.6GB vs 8.9GB). 하지만 실제 파라미터 수는 π0가 더 크다. 파일 크기는 저장 형식(fp32는 숫자 하나에 4바이트, bf16은 2바이트)에 따라 달라지므로 모델 크기의 기준이 아니다.
2026-10-28 로컬 체크포인트로 직접 센 값이다.

### 추론: 전체 파라미터 수가 결정
추론은 가중치를 GPU에 올려 계산만 한다. 그래서 **전체 파라미터 수 × 숫자 형식**이 거의 전부다.

| | GR00T N1.7 | π0 |
|---|---|---|
| 전체 파라미터 | 3.14B (Qwen3-VL 백본 1.52B + 행동 헤드 1.62B) | 4.03B (bf16 3.61B + fp32 0.42B) |
| HF 파일 | 12.6GB (백본 fp32 저장) | 8.9GB (대부분 bf16) |
| 전부 bf16일 때 가중치 | 약 6.3GB | 약 8.1GB |
| 노트북 RTX 5050 8GB | 들어감 (측정 6.31GB) | 안 들어감 (현재 형식 측정 8.89GB) |

- GR00T는 Qwen3-VL 언어모델의 앞쪽 일부 층만 쓰고 나머지는 잘라낸다(`groot_n1_7.py`, `select_layer`). 그래서 "3B"라도 백본은 1.5B다.
- π0는 PaliGemma(약 3B)를 통째로 쓰고 행동 전문가를 따로 붙인다. Gemma는 단어 사전이 25만 개가 넘어 임베딩 표만 수억 개 파라미터다.
- 따라서 노트북 8GB에는 대략 3.5B 이하만 bf16으로 올라간다.

### 학습: 업데이트하는 파라미터 수가 결정
학습은 업데이트하는 파라미터마다 기울기, AdamW 상태값 2개, fp32 원본이 붙는다. 다 합치면 **학습 파라미터 1개당 약 16바이트**다. 얼린 부분은 가중치만 차지한다.

| | GR00T N1.7 | π0 |
|---|---|---|
| 학습 설정 | 백본 얼림, 행동 헤드·projector·vlln 학습(약 1.6B) | `train_expert_only=true`, VLM 얼림, 행동 전문가만 학습(약 0.3B급) |
| 학습 파라미터 추가분 (16바이트 기준 추정) | 약 26GB | 약 5GB 안팎 |
| 그 밖에 | 설정상 파라미터 fp32 유지(`model_params_fp32`) | gradient checkpointing으로 중간 계산값 절약 |
| 학교 서버 RTX 4090 24GB | batch=1도 OOM ([실험계획 문서](../architecture/20260922_모델별_데이터개수별_실험계획.md)) → Brev A100 80GB에서 학습 | 학습 가능 |

학습 행의 GB 값은 규모를 보여 주는 추정이다. 측정값이 아니다. 24GB에서 GR00T가 OOM이 나고 π0가 학습된 것은 실제 결과다.

### 정리
- **학습에는 GR00T가, 추론에는 π0가 더 많은 메모리를 요구했다.**
- 원리: **학습 메모리는 학습하는 파라미터 수가, 추론 메모리는 전체 파라미터 수가 결정한다.**
- 이 결과는 **우리 학습 설정 기준**이다.
  - GR00T도 LoRA처럼 학습 부분을 줄이면 24GB에서 될 수 있었다. 2026-09에는 당시 lerobot이 처음부터 LoRA로 학습하는 경로를 막아 쓰지 못했다.
  - 반대로 π0를 전체 미세조정하면 24GB에 들어가지 않는다.
- 학교 서버(π0·SmolVLA·ACT 학습), Brev A100(GR00T 학습), 노트북(GR00T·SmolVLA·ACT 추론), 학교 서버 원격 추론(π0)으로 장소를 나눈 이유가 이것이다.

## 7. π0 서버 원격 추론 명령 (미실행)
4절 결론에 따라 π0는 학교 서버에서 추론하고 노트북은 로봇만 제어한다. lerobot `async_inference`를 쓰고, 2026-09-23과 같은 구조다([pi0 서버 원격 추론 기록](20260923_pi0_서버원격추론_실험기록.md)).

2026-10-28 확인 내용:
- 서버 lerobot은 π0 학습 버전(`d20a453`)이다.
- 로컬(`7e241bd6`)과 `async_inference`·`transport` 차이는 `robot_client.py`의 카메라 import 몇 줄뿐이다.
- grpc는 양쪽 모두 1.84.0이다.

**① 서버 (창 1)**
```
ssh 210.94.172.150
source ~/miniforge3/etc/profile.d/conda.sh && conda activate lerobot_vla
nvidia-smi
python -m lerobot.async_inference.policy_server --host=127.0.0.1 --port=8080
```
- `nvidia-smi`로 다른 학습이 GPU를 쓰지 않는지 먼저 본다.
- `127.0.0.1`로만 열고 노트북은 SSH 터널로 접속한다(포트를 네트워크에 직접 열지 않는다).

**② 노트북: SSH 터널 (창 2, 켜 두기)**
```
ssh -N -L 8080:127.0.0.1:8080 210.94.172.150
```

**③ 노트북: 로봇 클라이언트 (창 3, 저장소 폴더)**

`robot_client`는 `{left}` 같은 자리표시자를 채우지 않는다. 그래서 카메라 번호를 먼저 확인한다.
```
"C:\Users\USER\miniconda3\envs\so101_env\python.exe" tools\camera\resolve_camera_indices.py
```
출력된 번호를 `<L>` `<R>` `<D>`에 넣는다.

컵배치 80은 두 군데만 바꾼다.
```
--pretrained_name_or_path=jun-seo/cup_place_chassis_pi0_80_5000S
--task="While holding the cup already loaded on the robot chassis with the left arm, move it to the table and place it down."
```

**옵션 설명**
- `--pretrained_name_or_path`: HF 저장소 이름을 쓴다. 서버가 직접 받는다(첫 실행 약 9GB).
- `--actions_per_chunk=50`: 학습 설정 `n_action_steps=50`과 같다.
- `--aggregate_fn_name=latest_only`: 2026-09-23에는 기본값(묶음 평균)에서 제자리 떨림이 있었다. 그래서 최신 묶음만 쓴다.

**평소 롤아웃(`rollout_handoff.py`)과 다른 점**
- 시작 자세 맞추기가 없다. 실행 전에 팔을 학습 시작 자세에 맞춘다([시작 자세 OOD 원인](20261016_SmolVLA_제자리떨림_시작자세_OOD_원인규명.md)).
- 자동 종료와 끝 자세가 없다. `Ctrl+C`로 멈추고, 토크는 켜진 채 남는다.
- 실행 전 그리퍼 풀기가 없다. 과부하가 남아 연결이 실패하면 `rollout_handoff.py`를 한 번 실행했다 끈다.
- 이번 버전으로 끝까지 실행한 적은 없다. 처음에는 비상정지를 준비하고 짧게 확인한다.

**끝낸 뒤**
- 창 3 → 창 2 → 창 1 순서로 `Ctrl+C`를 누른다.
- 정책 서버를 켜 두면 서버 GPU를 계속 차지한다.
