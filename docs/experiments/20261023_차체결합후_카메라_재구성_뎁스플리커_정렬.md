# 양팔을 차체에 결합한 뒤 카메라 재구성 — 뎁스 교체·조명 줄무늬·top 정렬·손목캠 교체 (트러블슈팅 기록)

최초 작성 2026-10-26 · 조작(IL) 담당자 작성 · 대상 기간 2026-10-22 ~ 10-24

## 0. 한 줄 요약

양팔을 실제 로봇 차체에 결합하면서 카메라 4대 중 3대의 상태가 바뀌었다.
- top 뎁스는 차체에 달린 다른 기종으로 바꿨다가, 조명 줄무늬 때문에 학습 때 쓰던 기종으로 되돌렸다.
- 왼쪽 손목캠은 다른 기종으로 바뀌었다.
- 오른쪽 손목캠은 USB 포트가 바뀌었다.

그때마다 생긴 문제를 측정으로 원인까지 확인하고, 카메라 도구 5개를 고치거나 새로 만들었다. 결론적으로 **설정(해상도·fps·노출 방식·좌우 반전)은 학습 때와 같고, 남은 차이는 top 카메라의 방향과 차체 결합으로 바뀐 장면 배치**다. 그래서 차체 결합 상태로 데이터를 새로 모았다(→ [데이터 수집 기록](20261023_차체결합_데이터수집_레포구성과_에피소드정리.md)).

## 1. 뎁스(top) 카메라

### 1-1. 차체에 달린 뎁스가 안 잡힘
- 증상: 브리지(`tools/camera/astra_rgb_virtualcam_bridge.py`)를 실행해도 Astra를 못 찾았다.
- 확인한 것:
  - 장치 관리자의 "ORBBEC Depth Sensor"는 모두 "Unknown"이었다. 예전에 꽂혔던 기록만 남아 있었다.
  - 다시 꽂자 새 장치가 **`PID_0402`(Astra S, 근거리형)** 로 잡혔지만 상태는 "Error, 코드 10(장치를 시작할 수 없음)"이었다.
  - 학습 데이터를 찍은 top 카메라는 **`PID_0401`** 이다. 즉 다른 기종이다.
- 조치: 다른 USB 포트에 직접 꽂자 "ORBBEC Close Depth Sensor"로 정상 인식됐다.
- 운영 주의: **브리지를 쓸 때 OBS 앱은 꺼 둔다.** OBS 가상 카메라는 한 프로그램만 잡을 수 있다. OBS 앱이 켜져 있으면 브리지가 가상 카메라를 못 연다. OBS는 설치만 돼 있으면 된다. 이전 안내에서 "OBS를 켜라"고 한 것은 잘못이었다.

### 1-2. 화면에 가로 줄무늬가 흐름 (60Hz 조명 플리커)
- 증상: 새 카메라(`PID_0402`) 화면에서 어두운 가로줄 약 4개가 프레임마다 아래로 흘러갔다. 행별 밝기 편차는 ±25였다.
- 원인: 천장 조명은 초당 120번 깜빡인다(전원 60Hz). 카메라 자동 노출이 이 주기(8.3 ms)보다 짧은 2.5 ms를 골라서 줄무늬가 생겼다.
- 측정 도구: `tools/camera/astra_flicker_sweep.py`를 새로 만들었다. 노출값을 바꿔 가며 줄무늬 세기와 밝기를 잰다.
- 측정 결과:

| | 이전 카메라 0401 (학습 데이터) | 새 카메라 0402, 자동 노출 | 새 카메라 0402, 노출 8.3 ms |
|---|---|---|---|
| 줄무늬 세기 | 1.2~2.3 (없음) | 23~24 | 0.15 (없음) |
| 평균 밝기 | 130~166 | 115 | 184 |
| 하얗게 날아간 면적 | 0~1% | 0% | 55% |

- 알아낸 것:
  - 노출 단위는 0.1 ms다. 83(=1/120초)의 정수배인 83·167·250에서 줄무늬가 사라진다.
  - gain은 32 이하면 모두 같은 밝기다.
  - **드라이버는 마지막으로 쓴 값과 같은 값을 다시 쓰면 무시한다.** 읽으면 83이 나오는데 센서는 여전히 자동 노출이었다. 그래서 한 칸 다른 값을 먼저 쓰고 목표값을 쓰도록 고쳤다.
- 브리지 수정: `--exposure`, `--gain` 옵션을 추가했다. 옵션 없이 켜면 기존과 똑같이 자동 수렴한 뒤 고정한다.
- 결론:
  - 새 카메라는 노출 83에서 줄무늬가 사라지지만, 이 조명에선 너무 밝아서 투명 병이 날아간다.
  - 원인은 두 카메라의 빛 감도 차이로 **추정**한다. 이전 카메라의 실제 노출값이 0으로만 읽혀 확정하지 못했다.
  - **이전 카메라(0401)로 되돌렸다.** 학습 때와 같은 기종이라 줄무늬와 화면 차이가 함께 해결된다.
  - 펌웨어의 깜빡임 방지 설정은 찾지 못했다. 후보 항목은 바꾸는 순간 영상이 멈추거나 변경이 거부됐다. 마지막에 원래 값으로 복구한 것까지 확인했다.
- 실수 기록: 이전 카메라에 `--exposure 83`을 붙여 켰다가 화면이 밝기 192에 57%가 날아갔다. **`--exposure`는 새 카메라용 옵션이다. 이전 카메라는 옵션 없이 켠다.** 옵션 없이 켜자 밝기 135.5로 학습 범위(131~164) 안이었다.

### 1-3. 프레임이 아예 안 들어오면 화면이 멈춘 채 남음
- 증상: 시험 도구가 카메라를 따로 열자 브리지 화면이 마지막 프레임에서 멈췄다.
- 원인: 기존 감시는 "같은 화면이 계속 들어올 때"만 재연결했다. 프레임이 아예 안 오면 `read_frame()`이 영원히 기다렸다.
- 수정: `wait_for_any_stream(timeout=2.0)`으로 2초 넘게 새 프레임이 없으면 재연결한다.
- 한계: 실제로 멈추는 상황에서 복구되는지는 아직 시험하지 못했다.
- 운영 규칙: **브리지가 켜져 있는 동안 다른 프로그램이 Astra를 직접 열지 않는다.**
- 참고: 수집 중 브리지 재연결 로그가 찍히면 그 사이 프레임이 멈췄다는 뜻이다. USB 연결부터 확인한다. 추론 중에도 같은 일이 생기면 정책이 멈춘 화면을 보게 된다.

### 1-4. top 화면이 학습 때와 다르게 보임 (줌아웃처럼 보임, 오른팔이 덜 보임)
- 결론: **소프트웨어가 아니라 카메라 방향과 장면 배치 차이다.**
  - 브리지 코드에는 자르기(crop)나 크기 조절(resize)이 없다. 렌즈도 고정이라 같은 기종이면 화각이 같다.
  - 물체의 가로 배율은 학습 때와 같았다. 왼팔 폭은 화면의 32% vs 30%, 오른팔은 29% vs 29%였다.
  - 대신 세로 구도가 달랐다. 테이블 먼 끝이 16% → 8% 지점, 갈색 패드 윗변이 70% → 76% 지점으로 옮겨갔다. 카메라 기울기가 달라졌고, 팔이 테이블에서 차체로 옮겨가면서 장면 배치 자체가 바뀌었기 때문이다.
- 정렬 도구: `tools/camera/view_virtualcam_live.py --ref-dataset <학습 데이터셋>`
  - 학습 화면을 반투명하게 겹쳐 보여 준다.
  - 학습 에피소드 8개와의 어긋남(중앙값)을 픽셀 숫자로 0.5초마다 표시한다. ±3 안이면 "맞음"이 뜬다.
  - 검증: 학습 화면 자기 자신은 (−0.1, +0.3)px로 나왔다. 일부러 (+12, −8)px 민 화면은 (+12.0, −7.7)px로 정확히 찾아냈다.
  - 당시 차체 장착 상태의 어긋남은 **가로 +16.8px, 세로 +17.6px**였다. 그만큼 오른쪽 가장자리의 흰 팔이 잘려 나갔다.
  - 테이블 배치가 바뀐 상태에서는 숫자가 흔들릴 수 있다. 그래서 차체에 고정된 두 팔과 손목캠 보드가 겹치는지를 눈으로 보는 것을 우선한다.
- 남는 차이(흰 책상 → 검은 타공판 차체, 테이블 모서리 위치)는 카메라로 맞출 수 없는 분포 차이다. 그래서 새 데이터를 모았다.

### 1-5. 라이브 창 표시 (`view_virtualcam_live.py`)
- 창에 찍힌 19.7fps는 창이 그림을 그리는 속도였다. 가상 카메라에서 직접 재면 30.2fps로 들어왔고, 그중 29.6fps가 새 프레임이었다. 그래서 받는 스레드와 그리는 스레드를 나누고 두 fps를 따로 표시하게 고쳤다.
- 화질이 나빠 보인 원인은 세 가지였다.
  1. 창이 640×480을 960×720으로 늘려 보여 줬다. 지금은 원본 크기가 기본이고, 키우려면 `--scale 1.5`를 붙인다.
  2. 장면에 따라 노출이 다르게 잡혔다.
  3. 렌즈 오염 가능성이 있었다.
- 녹화와 추론에는 브리지의 640×480 원본이 그대로 들어간다. 잘라내기나 줌이 없고, 좌우 반전(`mirror: true`)도 녹화·추론·라이브 창이 같다.
- 운영 팁: 브리지는 **병과 컵을 수집 때처럼 다 올려 둔 상태에서 켠다.** 노출이 켤 때 보는 장면에 맞춰 고정되기 때문이다.

## 2. 손목 카메라

| 시점 | 왼쪽 손목 | 오른쪽 손목 |
|---|---|---|
| v2 데이터 수집(테이블 거치) | USB 2.0 PC Cam, DevicePath `268b1cad` | USB 2.0 PC Cam, `30e3ab42` |
| 10-23 | **Innomaker-U20CAM-720P로 교체**, `2bd3af6b` | 그대로 |
| 10-24 (차체 결합) | 그대로 | **USB 포트 이동**, `b7049f8` |

- 왼쪽 교체 경위: 왼쪽 카메라가 세션 중 3번 빠졌다. 장치 설명자 요청 실패로 "알 수 없는 USB 장치"가 됐다. 사용자가 다른 기종으로 교체했다.
- 확인 방법: 각 인덱스 화면을 찍어 비교했다. 순정 SO-101 집게가 보이면 왼쪽, 검은 평행 그리퍼와 병이 보이면 오른쪽이다.
- 위험했던 점: 고정 번호(1/2/3)로 실행하면 **좌우가 뒤바뀐 영상이 오류 없이 들어갈 수 있다.** 실제로 기종 교체 직후 명령이 좌우를 바꿔 넣었다.
- 조치: `tools/camera/resolve_camera_indices.py`의 DevicePath 힌트를 두 번 갱신했다. 롤아웃과 텔레옵 명령은 `{left}` `{right}` `{depth}` 자리표시로 매번 다시 찾는다. 카메라가 하나라도 없으면 로봇을 움직이기 전에 멈춘다.
- 10-24 기준 인덱스는 왼쪽 2, 오른쪽 0, 뎁스 3이다. 1은 노트북 내장 웹캠이다. USB를 다시 꽂으면 바뀌지만, 자리표시를 쓰면 상관없다.
- `tools/camera/capture_indexed.py`: 캡처 저장 폴더를 `camera_index/`(환경변수 `CAPTURE_OUT_DIR`로 변경 가능)로 바꿨다. 한글 경로에서 `cv2.imwrite`가 실패해서 `imencode`로 저장하게 했다.

## 3. 새로 만든 확인 도구

| `tools/camera/view_virtualcam_live.py` | top(가상 카메라)만 실시간으로 본다. `--ref-dataset`이면 학습 화면을 겹쳐 보고 어긋난 픽셀을 표시한다 | 손목캠을 안 잡아서 롤아웃 직전까지 켜 둬도 된다 |
