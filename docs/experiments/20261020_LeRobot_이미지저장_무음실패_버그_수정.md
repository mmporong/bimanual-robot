# LeRobot 이미지 저장 "무음 실패" 버그 규명과 수정 (트러블슈팅 기록)

최초 작성 2026-10-20 · 조작(IL) 담당자 작성

## 0. 한 줄 요약

데이터 수집 중 에피소드가 끝나고 **몇 분 뒤** 영상 인코딩 단계에서 뜬금없이
`OSError: image file is truncated`로 녹화가 통째로 죽는 사고가 있었다. 추적해 보니
진짜 원인은 인코딩이 아니라 그 **한참 전**, LeRobot 로컬 포크의 `write_image()`가
프레임 저장 중 난 예외를 **삼키고 로그만 남긴 채 성공한 척** 넘어간 것이었다. 비동기
저장 완료 대기(`wait_until_done()`)가 "다 됐다"고 거짓 보고하는 바람에, 빠진 프레임은
수집이 끝난 뒤 인코더에서야 폭발했다 — 그때는 이미 복구 불가. **실패가 난 바로 그
지점에서 크게 터지도록** 재시도+재던짐+실패추적으로 고쳤다.

> 수정 대상은 로컬 LeRobot 포크(`.../so101-mobile-manipulation-main/lerobot`)의
> `src/lerobot/datasets/image_writer.py`다. 이 팀 저장소에는 **패치 형태로** 보존했다:
> [`tools/recording/lerobot_image_writer_silent_failure_fix.patch`](../../tools/recording/lerobot_image_writer_silent_failure_fix.patch) (184줄).

## 1. 증상 — 에피소드가 끝나고 몇 분 뒤에 터지는 크래시

- 녹화는 멀쩡히 끝난 것처럼 보였는데, 저장/인코딩 중 아래 트레이스백으로 죽었다:
  `_encode_video_worker` 내부의 PIL 디코딩에서 `OSError: image file is truncated`.
- 혼란스러웠던 점: **에러가 난 위치(영상 인코더)와 실제 문제의 위치(프레임 저장)가
  달랐다.** 인코더는 "디스크에 있는 PNG를 읽어 mp4로 묶는" 소비자일 뿐, 그 PNG가
  잘린(불완전한) 이유는 인코더 코드엔 없었다. 에러 지점만 보면 영원히 못 고친다.

## 2. 원인 — `write_image()`가 예외를 삼켜서, 완료 대기가 거짓 보고

LeRobot의 비동기 이미지 저장 파이프라인은 이렇게 돈다:

1. 제어 루프가 프레임을 `AsyncImageWriter`의 큐에 넣는다(`save_image`).
2. 워커 스레드가 큐에서 꺼내 `write_image()`로 디스크에 쓴다.
3. 에피소드 저장(`save_episode`) 시 `wait_until_done()`(`queue.join()`)으로 **모든
   저장이 끝날 때까지 동기화 배리어**를 건 뒤, 영상 인코딩으로 넘어간다.

문제는 2번이었다. 원본 `write_image()`는 `PIL.Image.save()` 중 난 **모든 예외를
`except`로 잡아 로그만 찍고 그냥 넘어갔다**(재던지지 않음). 그래서:

- 한 프레임 저장이 조용히 실패해도 워커는 `task_done()`을 호출하고 끝난다.
- `queue.join()`은 "큐의 모든 작업이 처리됨"만 보므로, **실패한 작업도 '완료'로
  센다.** 결국 `wait_until_done()`은 **빠진 프레임이 있는데도 "다 됐다"고 거짓
  보고**한다. 배리어 자체는 멀쩡했고, 문제는 배리어가 "완료 전에 일어난 실패"를
  감지할 수단이 없었다는 것이다.
- 그 디렉터리에 프레임 하나가 비거나 잘린 채로 영상 인코더에 넘어가고, 인코더가
  그 파일을 읽다가 **몇 분 뒤** `image file is truncated`로 폭발한다. 이미 라이브
  녹화는 끝난 뒤라 복구 불가.

**원인 귀속**: L3(로직) 버그다. 하드웨어·좌표·분포가 아니라, 실패 경로를 설계가
삼킨 것. 증상(인코더 크래시)과 원인(저장 무음 실패)의 레이어가 달라 추적이 꼬였다.

## 3. 수정 — 실패 지점에서 크게 터지게

`image_writer.py`를 아래와 같이 고쳤다(패치 파일에 전체 diff 보존):

- **`write_image()`**: `max_retries=3`, `retry_delay_s=0.1`로 **짧게 재시도**(긴 수집
  중 디스크 경합·백신 스캔 락 같은 일시적 I/O 딸꾹질은 흔하므로 재시도가 값어치 있다).
  재시도를 다 쓰고도 실패하면 **마지막 예외를 재던진다**(원본은 여기서 삼켰다).
- **`worker_thread_loop(queue, failures)`**: `write_image()`를 try/except로 감싸,
  실패 시 `(경로, 에러문자열)`을 공유 `failures` 리스트에 적는다. 단 `task_done()`은
  **항상** 호출해 `queue.join()`이 데드락에 빠지지 않게 한다.
- **`AsyncImageWriter`**: 스레드 모드는 평범한 리스트, 프로세스 모드는
  `multiprocessing.Manager().list()`로 `self.failures`를 두고 워커에 넘긴다.
- **`wait_until_done()`**: `queue.join()` 뒤 `self.failures`가 비어 있지 않으면,
  실패 경로 미리보기(최대 5개)와 함께 **`RuntimeError`로 크게 터뜨린다** — 호출자가
  "프레임이 빠진 디렉터리를 영상 인코딩"으로 넘어가기 **직전에**, **실제 문제가 난
  곳에서** 멈춘다.
- **`stop()`**: 매니저를 만든 경우 `self._manager.shutdown()`까지 정리.

`py_compile`로 검증했고, 실제 녹화 재개 후 재발하지 않았다.

## 4. 교훈

- **실패를 삼키지 마라. 특히 "완료"를 보고하는 경계 바로 앞에서.** 비동기 파이프라인은
  "작업이 처리됨"과 "작업이 성공함"을 구분하지 못하면, 완료 신호가 거짓이 된다.
- **에러가 터진 레이어 ≠ 원인 레이어.** 인코더 크래시를 인코더 버그로 보면 못 고친다.
  "이 파일은 왜 잘렸나"를 역으로 따라가야 저장 경로의 무음 실패에 닿는다.
- **일시적 I/O 실패는 재시도로, 영구 실패는 크게 터뜨림으로.** 둘을 같은 `except`로
  뭉개면 둘 다 못 다룬다.
