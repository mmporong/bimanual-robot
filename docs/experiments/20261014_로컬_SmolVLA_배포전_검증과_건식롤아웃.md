# 로컬 SmolVLA 배포 전 검증과 건식(무수분) 롤아웃 기록

최초 작성 2026-10-14 · 조작(IL) 담당자 작성 · 목적: 과정 기록 + 포트폴리오용 소재

원격 서버에서 학습한 SmolVLA 체크포인트(9000스텝, `20261014_원격GPU서버_학습셋업_기록.md`
참고)를 로컬로 내려받아, 팀 문서(`20260911_양팔_IL_데이터수집_HuggingFace_학습_인계.md`
13절)에 정해둔 "학습 후 배포 전 게이트"를 실제로 밟아본 기록이다. 하드웨어를
건드리지 않는 오프라인 검증부터, 실제 로봇을 물 없이 돌리는 건식 롤아웃까지 다룬다.

---

## 1. 체크포인트 다운로드 — 추론에 필요한 것만

서버의 체크포인트 폴더에는 `pretrained_model/`(1.2GB, 추론용)과
`training_state/`(1.9GB, 옵티마이저·RNG 등 재학습 재개용)가 같이 있었다.
로컬 배포는 재학습이 아니라 추론만 할 거라, `training_state`는 빼고
`pretrained_model`만 내려받아 700MB 가까운 전송을 아꼈다. 로컬 경로는
서버와 같은 상대 구조(`outputs/<run>/checkpoints/<step>/pretrained_model`)로
맞춰서, 서버에서 쓰던 명령어 패턴을 그대로 재사용할 수 있게 했다.

---

## 2. 게이트 1단계 — 오프라인 입력/출력 shape 확인, 그리고 예전에 포기했던
## 토크나이저 버그를 이번엔 고쳤다

held-out 에피소드(학습에 전혀 안 쓰인 데이터) 하나를 읽어 정책에 통과시켜
action의 shape·범위만 확인하는 단계다. 로봇 하드웨어는 전혀 건드리지 않는다.

**막혔던 지점**: `make_pre_post_processors`로 전처리 파이프라인을 로드하는데
`tokenizer is not a local folder` 에러가 났다. 체크포인트 안에 토크나이저
파일이 분명히 있는데도(`pretrained_model/tokenizer/`), 전처리기 설정에 저장된
`tokenizer_name` 값이 `"tokenizer"`라는 상대 문자열이라, 라이브러리가 이걸
HuggingFace Hub의 레포 이름으로 오인해서 인터넷에서 찾으려다 404가 났다.

**해결**: `make_pre_post_processors`의 `preprocessor_overrides`에 토크나이저
폴더의 절대경로를 직접 넘겼다. 체크포인트 파일(`policy_preprocessor.json`)
자체에도 같은 값을 절대경로로 박아넣어서, 이후 어떤 스크립트(오프라인 검증,
`lerobot-rollout` 등)로 이 체크포인트를 불러오든 다시 겪지 않게 했다.

**검증 결과**: action shape (1,12), NaN/Inf 없음, 같은 프레임의 실제 시연
action과 비슷한 값 범위(둘 다 대략 ±97 수준) — 터무니없는 출력은 아니라는
1차 확인을 통과했다.

## 3. 게이트 2단계 — 관절 한계 검사, 그리고 "기준 자체가 틀렸던" 사례

held-out 데이터 여러 프레임에 대해 정책이 예측한 action 청크(50스텝)
전부가 실제 관절 가동범위 안에 드는지, 한 스텝 사이 변화량이 비정상적으로
크지 않은지를 확인하는 단계다. 역시 하드웨어는 건드리지 않는다.

**처음 기준(calibration 파일의 range_min/max)으로 돌렸더니 3000개 예측
스텝 중 2179개(73%)가 "한계 초과"로 나왔다** — 처음엔 정책이 위험한
값을 낸다고 판단할 뻔했다.

**재확인**: 같은 기준으로 **실제 시연(ground truth) action**도 대조해보니,
시연 데이터 자체가 이미 4개 관절에서 그 "한계"를 넘고 있었다(그리퍼는
최대 99.92°인데 calibration 한계는 ±61.23°로 거의 40° 차이). calibration
파일의 range_min/max는 캘리브레이션 스윕 당시 기록된 값일 뿐, 실제 안전
가동범위 전체를 담보하지 않는다는 뜻이다.

**기준을 "실제 시연이 안전하게 도달한 범위"(시연 최대값 + 5° 여유)로
바꿔서 재검사**하니, 3000개 중 19개(0.6%)만 경계 근처에서 살짝 초과했고
그나마 한 관절·한 구간에 국한됐다. 스텝당 변화량 이상치도 3000개 중 1개뿐.

**교훈**: calibration 파일도 "자작 프로브"의 일종이다 — CLAUDE.md의
"프로브가 실물과 다르면 프로브를 의심한다" 원칙이 여기도 그대로 적용됐다.
안전 기준을 검증 없이 하나만 믿지 않고, **독립적인 두 번째 근거(실제
시연 데이터)와 대조**해서 기준 자체의 타당성부터 확인한 게 핵심이었다.

## 4. `lerobot-record`가 아니라 `lerobot-rollout` — 로컬 포크가 이미 분리해둔 것

실물로 정책을 돌리려고 익숙한 `lerobot-record --policy.path=...`를 썼더니
`unrecognized arguments: --policy.path`로 거부당했다. 이 로컬 포크는
`lerobot-record`를 **데이터 수집 전용**으로 명시적으로 막아두고, 정책
배포는 별도 CLI `lerobot-rollout`을 쓰게 설계돼 있었다(에러 메시지 자체가
"For policy-based deployment, use lerobot-rollout instead"였다).

`lerobot-rollout`은 전략이 여러 개다(`base`=녹화 없이 그냥 실행,
`episodic`=에피소드 단위 녹화, `sentry`=상시 녹화+자동 업로드 등). 이번
목적(일단 안전하게 되는지만 확인)에는 **녹화 없는 `base` 모드**가 제일
간단해서 그걸 썼다. 추론 백엔드도 `sync`(틱마다 한 번 추론)와 `rtc`(느린
VLA용 실시간 청킹) 중, SmolVLA가 로컬에서 이미 충분히 빠른 걸 확인했기 때문에
기본값인 `sync`를 그대로 썼다 — 더 복잡한 `rtc` 경로를 쓸 이유가 없었다.

카메라 설정도 미묘하게 갈린다: 양팔에 각각 붙은 손목캠은
`--robot.{left,right}_arm_config.cameras="{wrist: ...}"`로 넣으면 `left_wrist`/
`right_wrist`로 자동 접두어가 붙고, 어느 팔에도 안 붙은 top(3인칭) 카메라는
`--robot.cameras="{top: ...}"`로 최상위에 넣어야 접두어 없이 `top`
그대로 들어간다(`bi_so_follower`의 `config_bi_so_follower.py` 주석에 명시돼
있었다). 이 구분을 코드로 먼저 확인하지 않고 추측으로 넣었으면 체크포인트가
기대하는 `observation.images.top` 키 자체가 비어서 엉뚱하게 움직였을
것이다.

## 5. 카메라 인덱스 캡처 스크립트의 한글 경로 버그

인덱스 확인용 `tools/camera/capture_indexed.py`를 돌렸는데, 콘솔엔
`RESULT_START`/파일 경로가 정상 출력됐지만 **실제로는 파일이 하나도
저장되지 않았다.** 원인은 두 겹이었다:

1. `PYTHONUTF8`/`PYTHONIOENCODING`을 안 켠 상태로 실행하면 한글 경로
   문자열 자체가 콘솔 출력 단계에서 깨진다(이 저장소에서 이미 여러 번
   재발한 것으로 기록된 문제).
2. 인코딩을 고쳐도 **`cv2.imwrite()`는 Windows에서 비ASCII 경로를 못 쓴다**
   — 반환값(성공/실패)을 확인 안 하는 기존 스크립트 구조 때문에 실패가
   조용히 묻혔다.

**해결**: `cv2.imencode()`로 메모리에 JPEG 바이트를 만든 뒤 `Path.write_bytes()`로
직접 저장하는 방식으로 우회했다 — 이건 순수 Python 파일 I/O라 유니코드
경로를 정상적으로 다룬다.

**교훈**: "콘솔에 성공했다고 찍힌다"와 "파일이 실제로 생겼다"는 다르다.
반환값을 안 보는 I/O 호출은 한글 경로가 섞인 프로젝트에서 특히 의심해야
한다.

## 6. 정체불명의 "느린 제어 루프"를 격리 테스트로 추적한 과정

실물 롤아웃을 돌리면 목표 30Hz 대신 꾸준히 1.5~1.8Hz로 돌았다. 바로
재시도를 반복하지 않고, 하드웨어 없이도 테스트 가능한 두 구성요소를
각각 격리해서 확인했다:

1. **정책 쪽 캐싱**: 같은 입력으로 `select_action()`을 60번 연속 호출 →
   정확히 설계대로 50번(=n_action_steps)에 한 번만 느리고(청크 재계산)
   나머지는 1.3ms 수준으로 빨랐다. **정책은 정상.**
2. **카메라·모터 읽기**: `robot.get_observation()`만 로봇 안 움직이고
   20번 반복 → 틱당 2ms. **이것도 정상.**

둘 다 정상인데 실제 루프는 느렸다는 건, 둘을 격리했을 때는 안 드러나는
무언가가 범인이라는 뜻이었다. 처음엔 안전 확인용으로 켜둔 Rerun
시각화(`--display_data=true`)를 의심해 꺼봤지만 그래도 느렸다.

**최종 범인**: 더 긴 시간(70초) 돌리자 결국 `TimeoutError: OpenCVCamera(2)
latest frame is too old`가 터졌다 — 오른쪽 손목캠이 이미 `20261014_데이터수집_운영_트러블슈팅_기록.md`에
기록해둔 바로 그 간헐적 프레임 지연 문제를 일으키고 있었다. 짧은 격리
테스트(20번, 몇 초)에서는 운 좋게 이 간헐적 지연 구간을 안 만났을 뿐이었다.

**교훈**: 구성요소를 각각 격리해서 "정상"을 확인하는 건 중요하지만,
**간헐적(intermittent) 문제는 격리 테스트의 짧은 실행 시간 안에 재현이
안 될 수 있다** — 실제 조건(더 긴 시간, 로봇이 실제로 계속 움직이는 상태)에서
한 번 더 확인해야 비로소 드러났다.

## 7. `disable_torque_on_disconnect`의 위험 — 카메라 하나 때문에 쥔 걸 놓친다

카메라 타임아웃이 제어 루프 **도중**(테어다운이 아니라) 터지면 예외가
그대로 전파돼 `run()`이 죽고, 뒤이은 `teardown()`의 `disconnect()`가
기본 설정값(`disable_torque_on_disconnect=True`) 때문에 **토크를 그 자리에서
끊어버렸다.** 하필 오른팔이 물병을 들어올리던 중이었던 적이 있었는데,
그대로 바닥에 떨어졌다 — "스톨 감지 시 정지 명령을 보낸다"는 원칙과
정반대로, 오히려 안전장치가 사고를 만든 셈이었다.

**조치 두 가지**:
1. **근본 수정**: `lerobot-rollout`의 `base` 전략 제어 루프에 패치를
   적용해, 카메라 읽기 실패 시 그 틱만 건너뛰고(새 명령을 안 보내 마지막
   목표 위치를 그대로 유지) 계속 돌도록 했다. 연속 5초 넘게 실패해야만
   진짜로 멈춘다. 패치는 `tools/rollout/lerobot_rollout_camera_timeout_resilience.patch`로
   보존했다(기존 `tools/camera/*.patch` 관례와 동일).
2. **추가 안전망**: `--robot.{left,right}_arm_config.disable_torque_on_disconnect=false`를
   기본 실행 명령에 추가했다 — 어떤 이유로든 연결이 끊겨도 토크가 유지돼,
   쥐고 있던 걸 놓치는 실패 모드 자체를 구조적으로 막는다.

패치 적용 뒤 같은 조건(70초, 로봇이 계속 움직이는 상태)으로 여러 차례
재검증했고, 카메라 지연이 실제로 발생해도 크래시 없이 끝까지 도는 것과
(지연이 아예 없었던 실행 포함) 정상 완주를 함께 확인했다.

## 8. 실물 건식 롤아웃 결과 — 중심부는 완주, 지터 극단은 약함

총 8회의 실물 시도(건식, 물 없음) 중 겪은 일을 조건별로 정리한다.

| 조건 | 결과 |
|---|---|
| 짧은 duration(20초)에 작업 중간에 끊김 | "복귀 루틴"이 들고 있던 물체를 내려놓는 것으로 보여서 처음엔 "토크 결함"으로 오인 — 실제로는 설계된 "초기 자세 복귀" 동작이었다 |
| 카메라 크래시(패치 전) | 쥐고 있던 물체를 바닥에 떨어뜨림 — 7절 참고 |
| 중심부/비극단 위치(여러 차례) | **붓기·컵 적재·초기 자세 복귀까지 전 과정 완주** — 여러 번 재현 확인 |
| 지터 범위 안이지만 가장자리(최대한 뒤/옆으로) | 병은 접근 정렬 실패로 못 집음, 컵은 팔이 과격하게 움직이며 손날로 쳐서 날림 — 그립 실패와 충돌, 두 가지 다른 양상으로 실패 |

**해석**: 실패들을 1건씩 보면 "정책이 불안정하다"로 오인하기 쉽지만,
조건별로 나눠보면 패턴이 뚜렷하다 — 시스템 안정성 문제(카메라 크래시)는
패치로 해결됐고, 남은 실패는 전부 **지터 범위의 가장자리**에서만 나타났다.
±3cm라는 좁은 범위 안에서도 중심부와 가장자리의 성능 차이가 이 정도로
크다는 건, 추후 데이터를 더 모은다면 가장자리 쪽 비중을 늘리는 게
효율적이라는 뜻이다.

## 9. 포트폴리오에 쓸 만한 요약

"학습된 VLA 체크포인트를 실물에 배포하기 전, 토크나이저 경로·관절 한계
기준 같은 두 가지 함정을 발견해 고치고(특히 '안전 기준으로 쓰려던 값
자체가 틀렸다'는 걸 독립적인 두 번째 데이터로 교차검증해서 확인), 정책·
관측 읽기를 각각 격리 테스트로 검증한 뒤에도 남아있던 간헐적 하드웨어
결함을 실제 조건에서 재현해 추적한 경험. 하드웨어 결함이 오히려 '안전
장치'(연결 해제 시 토크 차단) 때문에 사고로 이어지는 걸 발견하고, 근본
수정(예외 처리 패치)과 방어적 설정(토크 유지 플래그)을 함께 적용해 실물
검증을 안전하게 반복 가능한 상태로 만들었다."
