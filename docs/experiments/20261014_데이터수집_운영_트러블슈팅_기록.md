# 데이터 수집(본수집) 운영 중 트러블슈팅 기록

최초 작성 2026-10-14 · 조작(IL) 담당자 작성 · 목적: 과정 기록 + 포트폴리오용 소재

`20261013_뎁스카메라_연동_트러블슈팅_기록.md`(카메라 셋업, 가상카메라가 멈춘
프레임을 내보내는 현상과 diff 기반 진단)와 `20260923_녹화_트러블슈팅_재녹화키_카메라인덱스.md`
(재녹화 키 오작동, 케이블 당김으로 인한 카메라 인덱스 문제)에서 이미 다룬
내용은 반복하지 않는다. 여기서는 그 문서들에 없는, 실제로 60개 에피소드를
수집하는 동안 새로 겪은 문제들만 정리한다.

가상카메라 자동 재연결(watchdog)은 `20261013` 문서가 다룬 "멈춘 프레임"
현상에 대한 사후 조치인데, 코드로 구현한 것이라 별도 문서화 없이
`tools/camera/astra_rgb_virtualcam_bridge.py` 모듈 docstring에 직접 남겨뒀다
(연속 프레임 완전 동일 시 재연결, 물리적 USB 재연결이 필요했던 한계도 그
안에 기록).

## 1. 경로 구분자 버그로 삭제한 데이터가 되살아난 사고

**증상**: 뎁스캠이 멈춘 채 녹화된 32~36번 에피소드를 `lerobot-edit-dataset`으로
삭제했는데(허깅페이스에서 32개로 정상 확인), 바로 다음 배치를 이어 찍은 뒤
보니 **삭제했던 32~36번이 되살아나 있었다.**

**원인**: 삭제 명령을 **Git Bash**로 실행하면서 Windows 경로(`C:\Users\...`)의
백슬래시를 그대로 썼는데, bash가 이걸 이스케이프 문자로 해석해버렸다. 그 결과
실제로는 `bimanual-robot-git` 저장소 **안에 엉뚱한 이름의 폴더**
(`UsersUSER.cachehuggingfacelerobot...`)가 생겨서 거기에 결과가 저장됐고,
**진짜 로컬 캐시는 삭제가 전혀 반영 안 된 채로 그대로 남아있었다.** 이 상태에서
`--resume=true`로 이어찍기를 하니, "삭제 안 된 옛 상태"를 기준으로 새 에피소드가
추가됐고, 그걸 그대로 허깅페이스에 푸시하면서 **삭제가 통째로 되돌려졌다.**

**해결**:
1. 같은 삭제 작업을 **PowerShell로** 다시 실행해서(Windows 경로를 깨뜨리지
   않는 셸) 정확한 로컬 캐시 경로에 반영.
2. 허깅페이스 쪽 상태를 직접 재조회해서(`huggingface_hub`로 `total_episodes`
   확인) 숫자가 실제로 맞는지 매번 검증.
3. 저장소 안에 잘못 생긴 폴더는 삭제.

**교훈**:
- **Windows 경로를 다루는 명령은 Git Bash가 아니라 PowerShell로** 실행해야
  한다 — 백슬래시 이스케이프 문제가 반복적으로 생겼다(이전에도 카메라 인덱스
  스크립트에서 한글 경로 문제로 한 번 겪었던 것과 같은 계열의 "셸이 경로를
  깨뜨리는" 문제).
- **"작업을 했다"와 "실제로 반영됐다"는 다르다** — 삭제 명령이 에러 없이
  끝났다고 믿지 않고, 매번 허깅페이스를 직접 재조회해서 숫자로 확인하는
  습관 덕분에 이 사고를 바로 발견하고 복구할 수 있었다. 만약 "명령이
  성공했으니 됐겠지"하고 넘어갔다면 망가진 데이터가 그대로 최종 학습에
  들어갈 뻔했다.

## 2. 손목캠 프레임 타임아웃 — 케이블 문제 말고 다른 원인도 섞여 있었다

**증상**: `TimeoutError: OpenCVCamera(2) latest frame is too old: 524.4 ms
(max allowed: 500 ms)` — 오른쪽 손목캠에서 반복 발생.

케이블 당김으로 인한 카메라 문제는 이미 `20260923_녹화_트러블슈팅_재녹화키_카메라인덱스.md`
에 정리돼 있어서, 여기서는 그걸로 다 설명되지 않았던 부분만 남긴다: 케이블
여유를 확보하기 **전에** 먼저 시스템 리소스 경합을 의심했는데, 실제로 **OBS
Studio 본체 앱, 미리보기 창, rerun 시각화**가 불필요하게 백그라운드에서
CPU/USB 자원을 쓰고 있는 걸 발견해 종료했다. 그런데도 같은 카메라에서
재발해서(소프트웨어 부담을 줄였는데도 반복 = L1 하드웨어를 더 의심해야
한다는 신호), 그제서야 케이블 쪽을 봤다.

**교훈**: 겉으로 같은 에러 메시지라도 **원인이 한 가지가 아닐 수 있다** —
이번엔 "소프트웨어 리소스 경합"과 "하드웨어 케이블 문제"가 같은 증상(타임아웃)
으로 나타났다. 하나를 고쳤는데 재발하면 "고친 게 틀렸다"가 아니라 "다른
원인이 하나 더 있다"로 접근해야 한다.

## 3. 키보드가 "녹화 창에 포커스 없어도" 입력을 가로채는 구조

**증상**: 리셋 대기 중에 엉뚱한 키 입력들이 로그에 찍히며 재녹화·종료가
의도치 않게 발동, 결국 녹화 세션이 중간에 `q` 입력으로 통째로 종료됨.

**원인**: lerobot의 키보드 리스너가 `pynput` **전역 후킹** 방식이라, 터미널
창에 포커스가 있는지와 무관하게 **컴퓨터 전체에서 눌리는 모든 키**를
감지한다. 다른 창에 뭔가 타이핑하는 동안에도 그 키 입력이 그대로 녹화
명령으로 들어간다.

**해결**: 코드 수정이 아니라 **운영 규칙**으로 대응 — 녹화(리셋 대기 포함)
중에는 다른 어떤 창에도 타이핑하지 않기.

**교훈**: 모든 문제가 코드로 고칠 수 있는 건 아니다 — 이건 설계상 의도된
동작(전역 단축키라 SSH 지연 환경에서도 안정적으로 동작하게 하려는 선택)이라,
오히려 **사용자가 이 제약을 알고 행동을 바꾸는 게 올바른 해결책**이었다.

## 4. lerobot 재설치 시 기존 패치 재적용 — 체크리스트가 없어서 빠뜨릴 뻔함

`20260923_녹화_트러블슈팅_재녹화키_카메라인덱스.md`에서 고쳤던 재녹화 키
패치(`lerobot_record.py`, `keyboard_input.py`)를, lerobot을 통째로
재설치하면서(공식 v0.6.1 + 패치 재적용) 재적용을 깜빡할 뻔했다. 실제 본수집
직전에 알아채고 다시 적용했다.

**교훈**: 환경을 재구축할 때, "이전에 겪었던 버그 목록"을 체크리스트로 들고
있지 않으면 **똑같은 버그를 또 겪는다.** 이번엔 기억하고 있다가 녹화 직전에
처리해서 피했지만, 재구축 작업엔 "적용해야 할 패치 목록"을 명시적으로
만들어두는 게 더 안전하다.

## 5. held-out 설계 — 통계적으로 공정하게, 그러면서도 번거롭지 않게

60개 중 12개(14,15,19,20,24,27,32,37,42,47,52,57)를 held-out으로 뺐다.
**배치(5개)마다 미리 정해둔 위치(처음 1~2개)를 결과 보기 전에 지정**하는
방식을 썼다 — 결과를 보고 나서 "이게 잘 됐으니 평가용으로 쓰자"처럼
사후에 고르면 평가 자체가 왜곡되기 때문이다. 정밀한 jitter 오프셋 기록은
(처음 계획과 달리) 생략했는데, 범위 자체가 ±3cm로 작아서 "거리별 분석"의
실익이 크지 않다고 판단했기 때문이다 — 측정 비용과 얻는 정보량을 저울질해서
의도적으로 생략한 것이지, 빠뜨린 게 아니다.

재검증 습관 덕분에 즉시 발견·복구한 경험. 같은 에러 메시지 뒤에
소프트웨어·하드웨어 두 가지 원인이 섞여 있을 때 조건을 바꿔가며 원인을
분리한 디버깅 과정도 포함."
