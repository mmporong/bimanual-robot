# 프로젝트 기획보고서 이동형 양팔 물 서빙 로봇

웹 주문 한 건을 받아 물을 따르고, 컵을 운반해 테이블에 놓은 뒤 도크로 복귀하는 로봇을 개발한다. 프로젝트의 목표는 준비·운반·전달을 하나의 미션으로 연결하고, 어느 단계에서 성공하거나 실패했는지 주문별로 남기는 것이다.

작성 기준일은 2026년 10월 1일이다. 이동·조작·관제의 개별 검증 근거는 확보했으며, 실물 전체 미션의 반복 평가와 물 양 판정 연동은 남아 있다. 이 보고서는 노션 기획보고서의 10개 항목을 따르며, 현재 성과와 앞으로의 개발 목표를 구분한다.

### 대상 사용자와 현장

대상 사용자는 식당에서 물 준비와 테이블 전달을 맡는 직원이다. 초기 시험 환경은 사전에 지도와 작업 위치를 등록한 실내 공간으로 제한한다. 물 받는 곳, 한 종류의 컵·물통, 한 개 테이블, 도크를 먼저 연결한다. 손님이 오가는 실제 매장의 상시 운용은 이번 MVP의 검증 범위에 넣지 않는다.

## 2. 문제 정의와 근거

### 현재 작업과 문제

트레이 운반형 서빙 로봇을 사용하는 흐름에서도 음료 준비, 트레이 적재, 테이블에 내려놓기는 사람이 맡을 수 있다. 본 프로젝트는 이 중 물 한 잔의 준비와 테이블 배치를 양팔로 수행해 이동 구간과 연결할 수 있는지 검증한다. PUDU의 BellaBot 공식 제품 설명은 음식 배송·자율주행·트레이 운반을 중심으로 소개한다. 이 제품 사례를 모든 서빙 로봇의 기능 제한으로 일반화하지 않는다.[S1]

직원의 개입을 줄일 수 있는지 판단하려면 운반 거리 외에도 준비 시간, 물 양 확인, 컵 재파지와 전달, 실패 후 복구 시간을 함께 측정해야 한다. 두 팔과 센서가 추가되면서 비용과 유지보수 부담도 늘어나므로 활용도 개선은 이번 프로젝트의 검증 가설이다.

### 관찰과 근거

| 근거 | 확인한 내용 | 해석의 범위 |
|---|---|---|
| 9월 7일 팀 결정 | 물 준비·서빙을 단일 미션으로 선정 | 범용 조작과 여러 태스크를 제외한 프로젝트 결정 |

### 확인된 사실과 가정

- 확인된 사실: 시뮬레이션에서 전체 연결 경로가 실행됐고, 실차에서 서비스 이동 구간이 실행됐다. 두 결과는 서로 다른 환경과 실행이다.
- 검증 가설: 한 로봇이 물 준비와 테이블 전달을 맡으면 주문당 사람 개입이 줄어든다.
- 검증 가설: 조작 phase별로 계획 기반 제어와 학습 정책을 비교하면, 전 구간에 한 방식만 쓰는 것보다 운영에 적합한 구성을 찾을 수 있다.
- 확인 필요: 현장 작업 빈도, 직원의 준비·회수 시간, 사용자 수용성, 총 제작·유지비, 실제 절감 효과. 현장 인터뷰 완료로 표시할 근거는 확보하지 않았다.

발표 자료의 노동연령 인구 감소·임금 비율·자동화 지원 수요 수치는 원 조사표와 조사 대상을 확인하기 전까지 이 보고서의 확정 근거로 사용하지 않는다. 선정 이유는 현재 확보한 장비, 양팔 협응이 필요한 붓기 작업, 시연 수집 가능성, 이동체와의 통합 검증 가능성에 둔다.

## 3. 제안 솔루션과 사용자 가치

### 목표 작업 시나리오

1. 직원이 웹에서 물 주문과 테이블을 선택한다.
2. 미션 상태기가 주문 ID를 발급하고 한 건을 활성화한다.
3. 로봇이 도크를 이탈해 물 받는 곳으로 이동한다.
4. 작업대 앞에서 위치·방향을 정렬하고 바퀴 정지를 확인한다.
5. 왼팔로 컵을 고정하고 오른팔로 물통을 잡아 물을 따른다.
6. 물 양과 흘림 상태를 확인한 뒤 물통을 반환하고 컵을 상판에 놓는다.
7. 컵이 상판에 지지되고 손이 떨어졌는지 확인한 뒤 테이블로 이동한다.
8. 테이블 앞에서 정렬하고 바퀴가 정지한 상태로 컵을 다시 잡아 테이블에 놓는다.
9. 컵의 테이블 지지와 손 분리를 확인하고 도크로 복귀한다.
10. 도크 도착·정지와 충전 시작을 별도 판정으로 기록한다.

전체 흐름이 개발 목표다. 현재 시뮬레이션 완주에는 충전 물리가 포함되지 않았으며, 실차 이동 시험에는 양팔 조작·물 양 판정이 포함되지 않았다. 실제 충전 시작 확인은 도크 복귀와 구분해 후속 게이트로 둔다.

### 모방학습과 규칙 기반 제어의 역할

| 영역 | 선택한 방식 | 책임과 경계 |
|---|---|---|
| 컵·물통 파지, 붓기, 반환·적재 | 텔레옵 시연으로 학습한 정책과 계획 기반 제어 비교 | 동일한 물체·시작 조건에서 행동과 실패를 평가 |
| 지도·주행·정렬 | SLAM·AMCL·Nav2와 결정적인 정렬 실행기 | 학습 정책의 관절 action과 분리 |
| 미션 순서 | 상태기계와 ROS 2 Action | 조작 결과를 기다리고 성공·취소·timeout을 구분 |
| 물 양·흘림 | 비전 추정과 보정표, 외부 감독 판정 | 목표 도달·초과·흘림·불확실 판정과 정지 연동은 후속 검증 |
| 명령·안전 | 단일 제어권, 명령 중재, watchdog, hold/stop | 정책이나 자연어 해석이 안전 판정을 대신하지 않음 |
| 자연어·에이전트 | 후속 선택 기능 | 허용된 스킬 선택·예외 설명만 담당. 실시간 모터 제어 제외 |

발표의 `IK_ALL / IL_ALL / HYBRID`는 제어 방식 비교를 설명하는 이름이다. 저장소 계약의 `PLANNED_ALL / ACT_ALL / HYBRID`와 표기를 연결하되, `IL_ALL`을 모든 모델이 지원되는 구현으로 해석하지 않는다. SmolVLA를 연결하려면 모델별 adapter, 관절 순서·단위, 관측·명령 시각, checkpoint 식별자를 검증해야 한다. 어느 phase에 학습을 배치할지는 공통 평가 후 결정한다.

### 사람 개입과 복구

실패가 나면 현재 phase를 정지하고 증상·센서 상태·관절 상태·개입을 주문 ID에 연결한다. 물체를 들고 있는 경우에는 hold와 토크 해제를 구분한다. 복구는 안전 상태와 물체 위치를 다시 확인한 뒤 명시적인 재개 절차로 수행하고, 취소된 주문의 늦은 결과가 다음 단계로 전진시키지 않도록 한다. 문서에 복구 절차가 있다는 사실과 실물 복구 시험 통과는 별도 상태로 관리한다.

### 사용자 가치와 Physical AI의 필요성

물 준비와 전달은 물체를 잡고 기울이며 이동 후 다시 놓는 물리 작업이다. 위치·자세·하중이 바뀌므로 화면의 주문 처리만으로 끝나지 않는다. 본 프로젝트는 양팔 협응, 센서 관측, 이동체, 학습 정책과 결정적인 제어를 연결하고, 사람 개입과 실패 기록을 포함해 작업 단위로 평가한다.

## 4. MVP 요구사항과 범위

다음 표는 개발 수용 기준이다. 구현하거나 시험한 범위는 6절의 현황 표에 따로 표시한다. 숫자 목표가 합의되지 않은 항목은 확정된 값처럼 쓰지 않는다.

| ID | 요구사항 | 우선순위 | 수용 기준 | 검증 방법 |
|---|---|---|---|---|
| FR-01 | 웹 주문과 미션 연결 | Must | 유효한 주문에 ID 부여, 중복 방지, 활성 미션 한 건 유지, 실패·취소 기록 | API·큐 시험, DB와 이벤트 대조 |
| FR-02 | 물 받는 곳·테이블·도크 이동 | Must | 등록한 station을 순서대로 방문, 정렬·정지·복귀 판정 기록 | 실차 이벤트·bag·영상, 외부 거리 대조 |
| FR-03 | 양팔 물 준비 | Must | 컵·물통 파지, 붓기, 물통 반환, 상판 적재를 물체 관측으로 판정 | 실물 영상·phase 기록, 저울·계량 기록 |
| FR-04 | 상판 운반과 테이블 전달 | Must | 컵이 상판에 독립 지지된 채 이동, 정차 후 재파지·테이블 지지·손 분리 | 지지·기울기·흘림·영상 대조 |
| FR-05 | 조작 Action 연동 | Must | 성공·실패·취소·timeout으로 다음 상태가 결정되고 늦은 응답은 전이를 만들지 않음 | Action mock, fault-injection, 통합 로그 |
| FR-06 | 실제 충전 시작 확인 | Should | 도크 도착 외에 충전 신호·전류 근거 확보. 미구현 시 도크 복귀로 범위 명시 | 접점·충전 신호와 시간 기록 |
| DR-01 | 시연 데이터와 BC 기준선 | Must | 에피소드 조건·포함/제외·split·보정·카메라·정책 버전을 추적 | loader·스키마 검사, dataset card, 학습 로그 |

### 포함 범위

- 한 종류의 컵·물통·물, 고정 작업대, 초기 한 개 테이블의 물 서빙 미션

### 선택 범위와 제외 범위

웹 UI는 네 테이블과 냉수·온수 선택을 제공하지만 물리 검증 범위는 따로 제한한다. MVP에서는 상온의 물과 한 테이블을 먼저 사용하고, 온수 조작·테이블 확대는 기본 통합이 통과한 뒤 검토한다.

실제 장비 온라인 강화학습, 고속 사람 협업, 다중 로봇 배차, 대규모 멀티태스크, 개방 매장 상시 운용은 제외한다. 음성·자연어 주문, 실험실 적용, Pi 5 전환은 후속 후보로 둔다.

### 이동과 조작 연결

실차 이동은 Cartographer 지도 생성, 저장 지도의 AMCL 위치추정, NavFn 경로 계획, RPP 추종, Collision Monitor로 역할을 나눈다. 지도 생성과 저장 지도 반복 운용을 같은 기능으로 묶지 않는다. 박스 면 관측·정렬·접근과 도크 후진은 별도 실행 단계로 관리한다.

조작은 `ExecuteManipulationSkill` Action에 연결한다. 현행 계약에는 요청·미션·주문 ID, skill, strategy, phase와 backend, checkpoint, timeout, 성공·실패·취소·개입 수가 포함된다. 물 양과 센서·안전 관측의 전달 위치는 추가 계약으로 확정해야 한다. 이동 성공만으로 조작을 성공 처리하지 않는다.

Isaac Sim Python 3.11과 ROS 2 Jazzy Python 3.12는 프로세스를 분리하고 Unix socket JSON으로 연결했다. 시뮬레이션 이동은 A*와 차동구동 추종을 사용했으며, 실차 Nav2와 동일한 주행 실행이라고 쓰지 않는다.

### 물 양 판정

컵·액체 영역 분리 → 원근·기울기 보정 → 액면 높이 또는 부피 충전율 → 컵별 mL 보정 → UNDER·TARGET·OVER·SPILL·UNKNOWN 판정의 순서로 개발한다. 높이 비율은 컵이 차 있는 정도이며 mL 측정값이 아니다. 컵 형태별 보정표와 저울·눈금 계량 대조가 필요하다.

목표량·허용오차, 불확실 판정의 처리, 붓기 감속·정지 시점을 먼저 고정한다. 초과·흘림·불확실 상태의 추가 붓기를 차단하는 감독 기능은 실물 시험으로 확인하기 전까지 완료로 표시하지 않는다.

### 데이터와 재현성

데이터셋·모델·영상·bag은 코드 저장소에 넣지 않고 비공개 Hub 또는 외부 산출물 저장소에 보존한다. 공용 저장소에는 인덱스·스키마·버전·해시를 남긴다. 현재 `data/README.md`에는 팀원 정책 실험의 데이터셋 인덱스가 등록되지 않았으므로, 발표의 60개 에피소드와 checkpoint를 연결하는 작업이 필요하다.

원인이 확인되지 않은 실패는 성공 BC 데이터에 섞지 않는다. 하드웨어·연결 → 좌표·표현 → 로직·파라미터 → 데이터·분포 → 측정 순서로 원인을 배제하고, 조치 후 동일 조건과 회귀 조건에서 재시험한다.

## 7. 차별성과 기대효과

### 유사 사례와 차이

| 사례 | 공통점 | 이번 프로젝트와의 차이 |
|---|---|---|
| BellaBot 음식 배송 로봇[S1] | 주문 위치로 이동하고 음식·물건을 운반 | 본 프로젝트는 물 준비와 컵 재파지·테이블 배치를 개발 목표에 포함. 제품 수준 신뢰성·적재량과 경쟁 검증한 것은 아님 |
| A mobile robotic chemist, Nature 2020[S2] | 이동형 조작 로봇이 장소를 오가며 연속 작업 | 광촉매 탐색에서 8일간 688회 실험한 연구. 물 서빙의 성능·사업성 근거로 전용하지 않음 |

이번 프로젝트의 비교 대상은 개별 알고리즘 성능보다 주문 단위의 작업 연결이다. 같은 환경에서 계획 기반 조작과 학습 정책을 평가하고, phase별 제어 방식·개입·실패·버전을 남긴다. 학습의 효과는 고정 프로토콜 결과로 판단하며, 현재 한 번의 rollout 관찰만으로 계획 기반보다 우수하다고 결론 내리지 않는다.

### 기대효과

- 사용자: 물 준비·운반·전달에서 사람이 개입하는 구간을 측정하고 줄일 수 있는지 확인한다.

2026-10-02 추가. 아래 **답변**은 면접에서 말할 수 있는 문장이고, **추가 설명**은 꼬리 질문에 대비한 구현 근거다. 코드와 기존 실험 기록을 대조한 내용이며, 이번 문서 작업에서 새 로봇 실험을 실행하지 않았다. 개인 담당은 이동·미션 연결·URDF·Isaac 검증이며, 정책·인지 파트의 성과는 팀 성과로 설명한다.

### Q1. 기본적인 차체 URDF는 어떻게 만들었나요?

**답변:** 차체를 프레임·상판·바퀴·캐스터·팔 장착부 같은 강체 단위로 나누고, 각 부품을 `link`, 부품 사이 연결을 `joint`로 정의했습니다. 고정 부품은 fixed joint, 구동 바퀴는 continuous joint로 연결했습니다. 프로젝트에서는 기구 치수 YAML과 CadQuery 생성기로 STEP·STL을 만들고, 차체·센서·양팔을 모듈별 Xacro로 구성해 최종 URDF로 확장했습니다. 마지막에 링크 트리, 메시 경로, 관절축·한계, 질량·관성을 검사했습니다.

**추가 설명:**

1. 기준 좌표계와 부품 중심·장착 위치를 정한다. 이 모델의 루트는 `base_footprint`이며 차체 `base_link`와 연결한다.
2. 각 link에 외형 `visual`, 접촉 형상 `collision`, 질량·무게중심·관성텐서 `inertial`을 정의한다.
3. joint에 parent·child, 장착 변환 `origin`, 회전축 `axis`, 형식과 필요한 limit·dynamics를 넣는다. 왼쪽·오른쪽 바퀴 축은 이 모델에서 `0 1 0`이다.
4. 차체·센서·팔을 Xacro 모듈로 합친다. 팔은 검증된 SO-101 원본 URDF에서 링크와 관절을 추출하고 `left_`·`right_` 접두어를 붙여 이름 충돌을 피한다.
5. STL의 mm 좌표는 mesh scale `0.001`로 m에 맞춘다. URDF의 길이는 m, 질량은 kg, 회전은 rad 기준으로 맞춘다.
6. `validate_description.py`가 Xacro를 확장해 `check_urdf`를 실행하고, 생성 결과를 커밋된 URDF와 비교한다. 시각적으로 잘 보이는 것만으로 모델 검증을 끝내지 않는다.

기구 YAML·CAD 생성기·Xacro의 역할은 서로 다르다. CAD의 세부 형상에는 생성기 안의 정의도 있으므로 모든 URDF 값이 YAML 한 파일에서 자동 생성된다고 설명하지 않는다. 캐스터는 고정 구면 충돌 프록시이며 실제 캐스터의 모든 회전 자유도를 재현한 모델은 아니다.

**근거:** [기구 치수](../design/mechanical/hold_flow_mechanical_v0_3.yaml), [CAD 생성기](../design/cad/generate_hold_flow_cad.py), [차체 Xacro](../src/hold_flow_description/urdf/mobile_base.xacro), [전체 Xacro](../src/hold_flow_description/urdf/hold_flow.urdf.xacro), [SO-101 변환기](../src/hold_flow_description/scripts/generate_so101_arm_xacro.py), [URDF 검증기](../src/hold_flow_description/scripts/validate_description.py).

### Q2. visual·collision·inertial을 왜 따로 설정하나요?

**답변:** visual은 화면에 보이는 외형, collision은 물체끼리 부딪히는 형상, inertial은 힘을 받았을 때 움직이는 특성을 정의합니다. 외형 메시를 그대로 모든 충돌 계산에 쓰면 계산량이나 접촉 안정성 문제가 생길 수 있어 차체에는 단순한 box 같은 충돌 형상을 사용했습니다. 반면 컵 입구나 그리퍼처럼 접촉이 과업을 결정하는 부분은 형상을 더 자세하게 모델링했습니다. 질량과 관성은 모델이 보기 좋게 움직이도록 임의 조정하는 값으로 취급하지 않고 실물과 대조해야 합니다.

**추가 설명:** 균일한 직육면체의 중심 관성은 `Ixx = m × (ly² + lz²) / 12`처럼 계산할 수 있지만, 실제 복합 부품의 질량 분포를 같은 식으로 확정할 수는 없다. 무게중심 좌표와 양의 관성값을 검사하는 것과 실물 동역학을 보정하는 것도 다른 단계다. 초기 프리뷰의 바퀴·캐스터 배치 보정은 실험용 URDF 사본에 적용했으며, 그 배치 변경에 따른 관성까지 실측 보정했다고 주장하지 않는다.

**근거:** [모델 설명·검사 범위](../src/hold_flow_description/README.md), [프리뷰와 물리 시험의 구분](20260918_URDF_Isaac51_작업환경_프리뷰.md).

### Q3. URDF를 Isaac Sim에 어떻게 적용했나요?

**답변:** 실제 물리 시험은 Isaac Sim 5.1에서 URDF importer의 `URDFCreateImportConfig`와 `URDFParseAndImportFile`을 호출해 USD stage에 로봇을 가져오는 방식으로 진행했습니다. 고정된 주방에서 양팔 물붓기만 시험할 때는 `fix_base=True`, 식당 안에서 바퀴로 이동할 때는 `fix_base=False`로 설정했습니다. 가져온 뒤 관절 이름으로 제어 인덱스를 맞추고, Articulation에 관절 목표를 전달하며 물리 시뮬레이션을 진행했습니다.

**추가 설명:** 실제 importer 설정에는 fixed joint 병합, 관성텐서 가져오기, self collision, convex decomposition이 포함된다. `collision_from_visuals=False`로 URDF의 충돌 정의를 사용하고 `parse_mimic=False`를 명시하므로, mimic 기구가 importer에 의해 자동 완성됐다고 말하지 않는다. 가져오기 성공 다음에는 중력·접촉·관절 추종을 확인해야 한다. 초기 프리뷰의 `set_joint_positions()` 자세 표시와 물리 시험의 `ArticulationAction` 목표 전달을 구분한다. 저장소에 있는 Isaac 6.0용 YAML·import 도구는 별도 계약이며, 5.1 물리 성공 결과의 실행 경로가 아니다.

**근거:** [양팔 물붓기 실행기](../tools/simulate_bimanual_pour.py), [이동형 실행기](../tools/simulate_restaurant_mobile.py), [NVIDIA Isaac Sim 5.1 URDF importer](https://docs.isaacsim.omniverse.nvidia.com/5.1.0/importer_exporter/ext_isaacsim_asset_importer_urdf.html).

### Q4. 식당이나 컵·물통 같은 에셋은 어떻게 만들었나요?

**답변:** 식당은 배치 JSON에 있는 크기와 위치를 읽어 바닥·벽·테이블·의자·작업대·도크를 절차적으로 만들었습니다. 로봇과 컵·물통은 USD reference로 배치하고, 물리 시험에서는 컵·물통을 각각 독립된 rigid body로 구성했습니다. 같은 식당 배치에서 충돌체와 주행 지도를 만들도록 해 화면에 보이는 가구와 경로 계획의 장애물 위치가 맞도록 했습니다.

**추가 설명:** 발표용 정적 scene의 렌더와 물리 실행 scene은 목적이 다르다. 정적 배치가 그럴듯하게 보이는 것만으로 rigid body·충돌·유체 동작을 검증한 것은 아니다. 컵 내부를 하나의 convex hull로 처리하면 빈 공간이 충돌체로 메워질 수 있다. 물리 물붓기에서는 바닥과 벽을 나누고 컵의 벽을 원주 32분할·높이 3구간으로 구성해 입자가 들어갈 내부 공간을 유지했다. 실험용 물체·그리퍼 프록시는 실물 접촉면과 동일하다고 보장하지 않는다.

**근거:** [식당 scene 생성](../tools/build_restaurant_scene.py), [배치·지도 생성](../tools/restaurant_layout.py), [컵·병·입자 구성](../tools/simulate_bimanual_pour.py), [식당 환경 설명](20260921_식당_시뮬레이션_환경.md).

### Q5. 카메라는 몇 개 썼고 각각 무슨 역할이었나요?

**답변:** 실물 관제에는 상단 RGB 1대와 양쪽 손목 RGB 2대, 총 3대를 사용했습니다. 상단에서는 전체 작업 배치와 팔·물체 관계를 보고, 손목에서는 그리퍼 주변의 접근·접촉을 확인했습니다. 다만 검증된 Isaac 물붓기는 카메라 인식 입력으로 제어한 실험이 아니라 시뮬레이터의 물체 좌표와 접촉 상태를 사용한 실험입니다. 실제 카메라 수, 발표 렌더 시점 수, 정책에 입력한 카메라 수를 나눠 설명하고 있습니다.

| 실물 RGB 관제 | 상단 1 + 손목 A/B 2 = 3대 | 대시보드·진행 기록에서 연결 확인 |

### Q6. 컵과 물통의 위치는 어떻게 알아냈나요?

**답변:** 계획 기반 Isaac 시험에서는 scene에 정의한 초기 위치와 시뮬레이터가 반환하는 물체 pose를 사용했습니다. 이 조건에서 파지·붓기·운반 로직을 먼저 검증했습니다. 따라서 해당 결과를 카메라로 컵을 찾아 임의 위치에서 잡은 결과로 설명하지 않습니다. 실물 일반화에는 물체 인식 결과를 로봇 좌표계로 변환하는 단계와 위치 오차를 포함한 반복 평가가 필요합니다.

**추가 설명:** 물체 검출의 픽셀 좌표만으로 IK 목표를 만들 수 없다. 영상 관측을 사용할 경우 카메라 좌표의 3차원 위치를 장착 변환을 거쳐 팔 기준 좌표로 바꾸고, 물체 중심이 아닌 실제 파지점·접근 방향을 정해야 한다. 실물 상대 IK 시험은 잠정 모델과 엔코더 피드백을 사용했으며, 영상상 컵 동반 상승을 확인했지만 책상 완전 분리나 위치 정밀도까지 인증한 것은 아니다.

**근거:** [Isaac 물체 관측](../tools/simulate_bimanual_pour.py), [실물 상대 IK](../tools/bench_relative_ik.py), [실물 영상·보정 기록](../PROGRESS.md).

### Q7. Isaac Sim에서 컵과 물통을 어떻게 잡았나요?

**답변:** 왼팔은 컵, 오른팔은 물통의 파지점으로 접근하는 관절 경로를 만들고 그리퍼를 닫은 뒤 들어 올렸습니다. 컵·물통을 손목에 fixed joint로 붙여 따라오게 하지 않고, 독립 rigid body와 그리퍼 사이의 물리 접촉으로 유지하도록 했습니다. 성공 판정도 모터가 닫혔다는 값만 사용하지 않고 양쪽 손가락 접촉·들림·미끄럼·상대 회전을 함께 확인했습니다.

**추가 설명:** 물체를 따라가는 고정 프레임은 상대 pose 측정용이며 물체 attachment가 아니다. 코드에는 파지 접촉 상실, 상대 위치 미끄럼, 상대 회전, 비파지 링크의 충돌 등을 실패로 판정하는 조건이 있다. 해당 실험의 대표 한계는 미끄럼 2 cm 초과·상대 회전 15° 초과·접촉 상실 0.1초 초과다. 이는 시뮬 실험 판정값이며 실물 운용 안전 기준으로 자동 전환하지 않는다. 전체 왕복 성공은 구형 강체 패드 조건이고, 이후 순정 죠의 단독 컵 접촉 시험을 전체 물 서빙 검증으로 확대하지 않는다.

**근거:** [파지·접촉·실패 판정](../tools/simulate_bimanual_pour.py), [컵 접촉 프록시](../tools/cup_contact_model.py), [병 접촉 프록시](../tools/bottle_contact_model.py), [URDF·순정 그리퍼 검증 범위](20260918_URDF_Isaac51_작업환경_프리뷰.md).

### Q8. 물통을 기울일 때 어떤 IK를 사용했나요?

**답변:** 병 입구의 위치와 병의 기울기를 함께 맞추는 수치 IK를 사용했습니다. 관절값에서 FK로 병 입구와 축 방향을 계산하고, 목표와의 오차를 줄이도록 damped least squares 방식으로 관절값을 갱신했습니다. 이전 자세를 다음 계산의 초기값으로 넣어 자세 분기 변화를 줄였고, 관절 한계와 컵 쪽으로 향하는 붓기 방향을 검사했습니다.

**추가 설명:** `_solve_pour_mouth()`의 오차에는 입구 xyz, 병 축의 기울기, 컵 쪽 방향 조건, 이전 관절값과의 연속성이 포함된다. 수치 차분으로 Jacobian을 만들고 `Δq = (JᵀJ + λI)⁻¹Jᵀe`, `q ← q − Δq` 형태로 보정한다. 각 목표 해는 관절 한계 안으로 제한하며 잔차가 기준을 넘거나 붓기 방향 조건을 만족하지 않으면 거부한다. 손목 하나의 roll만 돌리는 방법은 병 입구도 크게 이동시키므로, 여러 관절을 함께 움직여 입구 위치를 맞추었다. 이 계획기를 MoveIt 기반 전체 동작 계획기로 설명하지 않는다.

**근거:** [병 입구 IK·경로 생성](../tools/bimanual_pour_plan.py).

### Q9. 물 따르기는 어떻게 구현했나요?

**답변:** 왼팔로 컵의 수직 자세를 유지하고, 오른팔은 병 입구가 컵 위에 오도록 하면서 병을 단계적으로 기울였습니다. 현행 계획 설정에서는 병을 0°에서 105°까지 5° 간격으로 기울이는 목표와 입구 높이 스케줄을 만들고, 각 단계의 IK 결과를 관절 목표로 실행했습니다. 물은 PhysX GPU PBD 입자로 모델링해 중력과 용기 접촉으로 이동하게 했습니다. 물 양 판정은 영상 액면 인식 대신 컵·병·외부 영역에 있는 입자 수를 사용했습니다.

**추가 설명:** 해당 시험은 120 Hz 물리 step을 사용한다. 초기 물은 918개 입자이고 설정으로 환산한 명목 부피는 58.752 mL지만, 실물 계량값이 아니다. 마지막 구간에서 컵·병·외부 입자 수와 보존 여부, 컵 수직성, 병 입구와 컵 림의 위치 관계, 파지 유지, 원래 자세 복귀를 평가했다. 실험의 `task_pass`는 컵 포집률 50% 이상·외부 입자 5% 이하 같은 여러 조건을 함께 요구한다. 목표 mL에서 인식 피드백으로 붓기를 정지한 실물 폐루프 결과는 아직 이 근거에 포함되지 않는다.

**근거:** [기울기·입구 목표 계획](../tools/bimanual_pour_plan.py), [PBD 물리 실행](../tools/simulate_bimanual_pour.py), [입자·자세 성공 판정](../tools/pour_geometry.py).

### Q10. 물을 받은 컵은 어떻게 놓고 운반했나요?

**답변:** 주방에서 물을 받은 컵을 로봇 상판에 내려놓고, 상판이 컵을 지지하는 상태를 확인한 다음 그리퍼를 열고 팔을 분리했습니다. 팔로 컵을 들고 주행하는 방식 대신 상판 지지를 사용했습니다. 테이블 앞에서는 베이스를 정렬하고 안정화한 뒤 컵을 다시 잡아 테이블에 놓았습니다.

**추가 설명:** 놓기에서는 컵 높이만 맞추는 것이 아니라 지지면 접촉, 물체 안정 상태, 그리퍼 개방과 분리를 순서대로 확인한다. 분리 경로가 컵이나 상판을 통과하지 않도록 상승·후퇴 waypoint를 사용한다. 주행 중에는 컵 pose와 입자 손실을 확인한다. 상판 지지와 파지·놓기는 강체·유체 시뮬 조건의 결과이며, 실제 가속도·상판 마찰·하중 조건의 운반 시험은 별도다.

### Q11. 식당 안의 경로는 어떻게 생성했나요?

**답변:** 시뮬레이션에서는 식당 배치의 가구 경계를 격자 장애물로 바꾸고, 로봇의 계획 반경만큼 장애물을 부풀린 지도에서 A*를 실행했습니다. 8방향 이웃을 탐색하되 대각선 이동 때 가구 모서리를 가로지르지 않도록 검사했습니다. 도크·주방·테이블 앞의 목표점을 연결하는 경로를 만들고 셀 중심 좌표를 경로 추종기에 전달했습니다.

**추가 설명:** 실제 scene과 같은 배치 입력에서 PGM·YAML 지도와 경로 JSON을 생성한다. 장애물 inflation은 로봇 중심 경로가 가구와 너무 가까워지는 것을 줄이기 위한 모델 처리이며, 실제 정지거리·사람·센서 오차까지 모두 포함한 안전 인증은 아니다. 이 A*는 알려진 정적 배치의 시뮬 경로 계획기다. 최신 실차 운용은 저장 지도와 Nav2의 NavFn 경로 계획기를 사용하므로 “실차에서도 이 A* 코드를 실행했다”고 말하지 않는다.

**근거:** [점유격자·A*·경로 내보내기](../tools/restaurant_layout.py).

### Q12. 경로를 따라가는 주행 로직은 무엇이었나요?

**답변:** 시뮬레이션에서는 현재 위치와 방향에서 경로 앞쪽의 lookahead 지점을 잡고, 그 방향으로 향하는 곡률을 계산해 선속도와 각속도를 만들었습니다. 목표 근처에서는 위치와 최종 yaw를 맞추는 pose regulator로 전환했습니다. 계산한 속도를 차동구동 식으로 좌우 바퀴 각속도로 바꾸고, 위치·방향 오차가 모두 기준 안에 들어와야 도착으로 판정했습니다.

**추가 설명:**

- `ωL = (v − L × ω / 2) / r`
- `ωR = (v + L × ω / 2) / r`
- `v`: 차체 선속도(m/s), `ω`: 차체 yaw 각속도(rad/s), `L`: 좌우 구동 바퀴 중심 간격(m), `r`: 바퀴 반지름(m).

기본 모델 값은 반지름 0.0329 m, 바퀴 간격 0.510 m다. 차체 기준점과 구동 축의 0.105 m 오프셋도 반영해 목표 위치에 차체가 정렬되도록 했다. 속도와 각속도를 제한하고 급한 회전에서는 감속한다. 이는 자체 경로 추종기이며, Nav2 RPP 플러그인의 실행 결과로 표시하지 않는다.

**근거:** [차동구동·lookahead·최종 정렬](../tools/mobile_service_control.py).

### Q14. 전체 미션은 어떤 순서로 실행했나요?

1. `NAVIGATE_KITCHEN` — 도크에서 주방으로 이동
2. `ALIGN_KITCHEN` — 주방 작업 위치 정렬
3. `GRASP_CUP` — 왼팔 컵 파지
4. `GRASP_BOTTLE` — 오른팔 물통 파지
5. `POUR` — 물붓기

11. `SERVE` — 테이블 배치

### Q15. ROS 2 통신 구조는 어떻게 만들었나요?

**답변:** 웹 주문을 미션 계층에서 받고, 오래 걸리는 조작은 `/execute_manipulation_skill` ROS 2 Action으로 요청하도록 구성했습니다. Action에는 목표뿐 아니라 진행 feedback과 최종 result가 있어 완료·실패·취소·timeout을 나눌 수 있습니다. Isaac 쪽은 ROS 2와 별도 프로세스로 실행하고 Unix socket JSON으로 phase 요청과 결과를 주고받았습니다. 따라서 웹 주문이 바퀴나 관절의 저수준 명령을 곧바로 보내는 구조는 아닙니다.

**현재 시뮬 연동 흐름:**

`웹 주문 → 미션 계층 → ROS 2 Action client/server → Unix socket JSON → Isaac phase executor → 물리 실행 → 결과·feedback`

| 통신 방식 | 기본 용도 | 이 프로젝트 답변에서 구분할 점 |
|---|---|---|
| Topic | 센서·상태·속도처럼 반복 전달되는 데이터 | Action goal과 관절 제어 주기를 같은 것으로 설명하지 않음 |
| Service | 짧은 요청·응답 | 오래 걸리는 전체 파지·붓기 완료 대기를 Service 하나로 설명하지 않음 |
| Action | 오래 걸리는 과업, 진행·결과·취소 | `ExecuteManipulationSkill`의 주문·phase 계약 |
| Unix domain socket | 같은 PC의 프로세스 간 요청·응답 | ROS DDS Topic이나 Wi-Fi 원격 통신이 아님 |

**추가 설명:** 인터페이스에 request·mission·order ID, skill·strategy·phase·backend·checkpoint·timeout을 넣는다. 실행 결과에는 success·failure·canceled·timed_out·개입·시각 정보, feedback에는 현재 phase·진행 상황을 담는다. Isaac의 실제 관절 목표는 시뮬 내부 Articulation API로 전달하며, 현재 성공 경로를 Isaac ROS Bridge의 joint command Topic 연결로 설명하지 않는다. 실물 이동+조작+원격 정책 전체 연결은 별도 통합 검증 범위다.

**근거:** [Action 인터페이스](../src/hold_flow_interfaces/action/ExecuteManipulationSkill.action), [Action client](../src/hold_flow_mission/hold_flow_mission/action_client.py), [로컬 IPC](../src/hold_flow_mission/hold_flow_mission/planned_ipc.py), [웹 backend](../tools/service_order_server.py), [ROS 2 Jazzy 공식 Action 문서 원문](https://github.com/ros2/ros2_documentation/blob/jazzy/source/Tutorials/Beginner-CLI-Tools/Understanding-ROS2-Actions/Understanding-ROS2-Actions.rst).

### Q16. Isaac과 ROS 2를 왜 프로세스로 분리했나요?

**답변:** 현재 Isaac Sim은 Python 3.11, ROS 2 Jazzy 환경은 Python 3.12를 사용해 하나의 Python 프로세스에 섞어 넣는 대신 실행 환경을 분리했습니다. 연결 경계는 JSON으로 제한해 Python 라이브러리 의존성을 공유하지 않도록 했습니다. 또 Isaac world를 한 프로세스에서 유지해 phase마다 로봇·물체·물 상태를 새로 만들지 않고 이어서 실행했습니다.

**추가 설명:** socket thread는 요청을 받고 simulation thread는 Physics·USD 상태를 다룬다. 실행기는 한 world를 한 mission에 귀속하고 phase 순서를 검사한다. 중복 요청 ID와 충돌하는 payload, 잘못된 다음 phase, 다른 mission, 오래된 executor instance를 거부하며 물리 결과의 식별자도 대조한다. phase 경계의 대기에서는 시뮬 물리 시간을 진행하지 않는다. JSON timeout이나 Action 취소 접수는 물리 정지 완료와 같지 않으므로 최종 phase 결과와 정지 확인을 구분한다.

**근거:** [world·mission·취소 경계](../tools/isaac_phase_executor.py), [bounded JSON·결과 식별자 검사](../src/hold_flow_mission/hold_flow_mission/planned_ipc.py).

### Q17. mock이나 로그 재생과 실제 물리 실행은 어떻게 구분하나요?

**답변:** backend 이름과 실행 provenance를 결과에 남겨 구분했습니다. mock은 통신 계약을 시험하고, artifact 모드는 기존 로그를 검증하며, physics executor는 Isaac world를 진행합니다. 왕복 모드는 이동 phase까지 포함한 같은 world를 사용합니다. API 응답이 성공했다는 사실만으로 새 물리 시험이나 실물 과업이 성공했다고 처리하지 않습니다.

| 웹 backend | 확인하는 범위 |
|---|---|
| `immediate` | CPU 미션 응답 경로 |
| `ros2-mock` | ROS 2 Action 계약·feedback·result |
| `ros2-planned-artifact` | 기존 실행 산출물 대조·재생, 새 물리 실행 아님 |
| `ros2-planned-session` | 설정된 executor 세션과 phase 연결. mock/물리 provenance 확인 필요 |
| `ros2-planned-roundtrip` | Isaac 왕복 phase 실행·도크 복귀 요구. 실제 Nav2·충전 실행과 구분 |

**추가 설명:** physics 결과의 `simulator_accessed=true`, `hardware_accessed=false`와 ID를 검사한다. 전체 물리 결과가 있다고 해서 모든 웹 backend로 동일 실험을 반복 성공했다는 뜻은 아니다. 실차 실행과 동일하게 주문 ID로 물 양·조작·이동 결과를 연결하는 반복 평가는 남아 있다.

**근거:** [backend 선택](../tools/service_order_server.py), [IPC 결과 provenance](../src/hold_flow_mission/hold_flow_mission/planned_ipc.py).

### Q19. 구현 중 어려웠던 점과 해결 방법은 무엇인가요?

**답변:** 동작이 화면에서 비슷하게 보여도 접촉과 좌표 조건이 다르면 과업이 실패하는 문제가 있었습니다. 병을 기울일 때 입구가 컵에서 벗어나거나 반대 방향으로 향하는 문제는 입구 위치·기울기·컵 쪽 방향을 함께 제한하는 IK로 보완했습니다. 컵을 놓은 뒤 팔이 분리되는 경로도 별도로 만들어 컵·상판 관통을 피했습니다. 또 구형 패드에서 얻은 결과를 순정 그리퍼에 그대로 적용하지 않고 형상별 접촉 시험으로 나눴습니다.

**추가 설명:** 실물에서는 LeRobot 보정 영점과 URDF 영점의 대응, 관절 목표 미도달, 카메라 가림이 별도의 문제로 남았다. 엔코더 목표 도달과 실측 TCP 정밀도, 영상상 컵 동반 상승과 완전 분리를 각각 나눠 기록했다. 실패 기준을 낮추거나 모델의 책상 높이를 옮겨 성공으로 처리하지 않는다. 본인의 설명은 확인한 관측과 수정한 제약을 중심으로 하고, 게인·중력·마찰 중 어느 것이 원인인지 검증되지 않은 경우 단정하지 않는다.

**근거:** [병 입구 IK](../tools/bimanual_pour_plan.py), [서비스 놓기·분리](../tools/water_service_mission.py), [순정 형상·실물 실패 기록](../PROGRESS.md).

### Q20. 시뮬레이션을 실물로 옮길 때 무엇을 더 검증해야 하나요?

**답변:** 형상·관절 영점·좌표계·질량과 접촉·센서 관측을 실제 장비와 맞추는 것이 먼저입니다. 현재 시뮬은 정답 물체 pose와 강체 프록시를 사용하므로 실물에서는 인식 오차, 서보 추종 오차, 마찰과 하중 차이가 추가됩니다. 현행 그리퍼와 보정으로 건식 파지·놓기를 확인하고, 계량 기준으로 물 양을 검증한 뒤 이동과 조작을 같은 주문으로 연결해 반복 평가하려고 합니다.

**추가 설명:** 확인 순서는 모델 좌표와 엔코더 변환 대조 → 작업셀·카메라 변환 확인 → 건식 접근·접촉·분리 → 제한된 물 양 시험 → 상판 운반 → 이동·조작 통합이다. 실물 물붓기의 stop 판단에는 목표 mL·허용오차와 불확실 관측 처리도 필요하다. 시뮬에서 입자가 컵에 들어갔다는 결과가 실물의 동일 mL·무유출·사람 주변 안전을 보장하지 않는다.

**근거:** [실물 매핑·실행 검토](../tools/bench_relative_ik.py), [현행 보정·영상 관측](../PROGRESS.md), 본 문서의 물 양 판정·평가·리스크 항목.

### Q21. 본인이 맡은 부분과 학습 정책의 관계를 설명해 주세요.

**답변:** 제 담당은 SLAM·Nav2 주행, 작업 위치 접근과 도크 복귀, 이동과 조작의 미션 연결, URDF와 Isaac Sim 검증입니다. 계획 기반 조작에서는 접촉·입구 IK·물 입자 판정으로 기준 동작과 실패 조건을 확인했습니다. SmolVLA 학습과 정책의 실물 완주는 정책 파트의 팀 성과이며, 제 시뮬 IK가 SmolVLA 실행이었다고 설명하지 않습니다. 앞으로 계획 기반 제어와 정책을 같은 조건에서 비교해 각 단계에 어떤 방식을 적용할지 결정하는 구조입니다.

**추가 설명:** 팀 발표의 loss 감소율은 학습 지표이며 과업 성공률 증가와 동일하지 않다. 학습 입력·dataset split·checkpoint·당시 보정과 반복 rollout 원본이 연결된 뒤 정책 성능을 확정한다. 정책 요청을 이동·조작 Action과 연결하는 기능과 실제 한 미션에서 두 backend가 함께 동작한 HYBRID 성과도 구분한다.

**근거:** 본 문서의 팀 역할, 출정식 PDF 10~16쪽, [데이터·평가 규약](../data/README.md), [Action 계약](20260922_ExecuteManipulationSkill_ROS2_Action.md).
