# pi0 서버 원격 추론 실험 기록

작성 2026-09-23. pi0(4B)가 로컬 GPU(RTX 5050, 8GB)에서는 추론 속도 부족으로 실제 로봇 롤아웃이
불가능했던 문제를, **정책 연산은 서버(RTX 4090)에서, 로봇 제어는 로컬에서** 하는 원격 추론
브리지로 우회 시도한 기록이다. 속도 문제는 해결했지만 다른 문제가 남아 다음 세션에 넘긴다.

## 배경

[`20260923_세션인계_현황과_유의사항.md`](20260923_세션인계_현황과_유의사항.md)의 "pi0 로컬 추론
불가" 절 참고 — 로컬에서 pi0 추론 1회에 최대 7.4초, RTC를 켜도 첫 액션 청크조차 90초+ 안에
못 끝나 로봇이 아예 안 움직이는 상태였다. 로봇 하드웨어(카메라·서보)가 이 노트북에만 연결돼
있어서, 정책 연산만 서버로 넘기고 로봇 제어는 로컬에 남기는 구조가 필요했다.

## 사용한 기능 — LeRobot 내장 `async_inference`

`lerobot.async_inference` 모듈에 이미 이 구조가 구현돼 있다 — 새로 만들 필요 없이 그대로
썼다.

- `policy_server.py` — 서버에서 실행. 정책을 로드하고 gRPC로 관측(observation)을 받아 액션
  청크를 돌려준다.
- `robot_client.py` — 로컬에서 실행. 카메라 캡처·로봇 상태 읽기를 하고, 서버로 관측을 보내
  액션을 받아 실제 로봇에 적용한다.

두 파일 모두 로컬 lerobot 포크와 서버 공식 클론 양쪽에 이미 존재했다. 실행에 필요한 통신
스텁(`services_pb2.py` 등)도 이미 저장소에 포함돼 있어서, `pip install grpcio`만 양쪽에
추가하면 됐다.

## 보안 — 포트를 네트워크에 노출하지 않기

처음에 서버를 `--host=0.0.0.0`으로 띄우려다가, 이게 그 포트를 로봇 클라이언트뿐 아니라 같은
네트워크의 누구에게나 여는 셈이라 자동 승인 정책에 막혔다(사용자가 요청한 범위를 넘어서는
노출). **SSH 터널로 대체**해서 해결:

1. 서버에서 `policy_server`를 `--host=127.0.0.1`(로컬호스트 전용)로 띄운다.
2. 로컬에서 `ssh -N -L 8080:127.0.0.1:8080 dgu@210.94.172.150`로 서버의 8080 포트를 우리
   컴퓨터의 8080으로 터널링한다.
3. 로컬 `robot_client`는 `--server_address=localhost:8080`으로 접속한다 — 실제로는 SSH
   터널을 타고 서버의 127.0.0.1:8080에 도달한다.

이러면 SSH 인증 없이는 그 누구도 정책 서버에 접근할 수 없다. 포트를 네트워크에 직접 여는
방식보다 이쪽을 항상 우선할 것.

## 실행 명령어

서버 (SSH로 먼저 실행, `lerobot_vla` conda env):
```bash
python -m lerobot.async_inference.policy_server --host=127.0.0.1 --port=8080
```

로컬 (SSH 터널이 떠 있는 상태에서):
```cmd
python -m lerobot.async_inference.robot_client ^
  --server_address=localhost:8080 ^
  --policy_type=pi0 ^
  --pretrained_name_or_path=jun-seo/pi0_40E_9500S ^
  --policy_device=cuda ^
  --actions_per_chunk=20 ^
  --task="Pour water from bottle into cup" ^
  --robot.type=bi_so_follower --robot.id=arms ^
  --robot.calibration_dir=C:\Users\USER\bimanual-robot\calibration\bi_follower ^
  --robot.left_arm_config.port=COM15 --robot.left_arm_config.gripper_protection=true ^
  --robot.right_arm_config.port=COM16 ^
  --robot.cameras="{ front: {type: opencv, index_or_path: 2, width: 640, height: 480, fps: 30}, left_wrist: {type: opencv, index_or_path: 3, width: 640, height: 480, fps: 30}, right_wrist: {type: opencv, index_or_path: 0, width: 640, height: 480, fps: 30} }"
```

`pretrained_name_or_path`는 서버가 직접 HF에서 내려받으므로 로컬 체크포인트 경로가 아니라
HF repo id를 쓴다.

## 결과

**속도 문제는 완전히 해결됐다.** 서버 로그 기준 관측 1건당 추론 130~140ms — 청크 20개(30fps
기준 약 667ms 분량)를 여유 있게 커버한다. 로컬에서 7초+ 걸리던 것과 비교하면 압도적으로
빠르다.

**그런데 로봇이 "제자리에서 계속 지 혼자 움직이는" 증상은 그대로 남았다.** 로컬에서 느린
추론 때문에 보이던 것과 겉으로는 비슷한 증상이지만, 이번엔 추론이 충분히 빠른 상태에서도
발생했으므로 **속도가 원인이 아니다** — 다른 문제다.

## 남은 의심 지점 (다음 세션 조사용)

`robot_client.py`는 `lerobot-rollout`의 RTC/sync 엔진과는 **완전히 다른, 별도의 액션 처리
파이프라인**을 쓴다 — 오늘 처음 써본 경로라 검증이 안 됐다.

1. **청크 블렌딩(`aggregate_fn`)**: 기본값 `weighted_average`(겹치는 타임스텝의 액션을
   0.3×이전 + 0.7×신규로 평균)가 여러 목표 사이에서 로봇을 진동시키고 있을 가능성.
   `--aggregate_fn_name=latest_only`(블렌딩 없이 최신 청크만 사용)로 바꿔서 진동이
   사라지는지 확인해볼 것 — 가장 싸고 빠르게 시도해볼 수 있는 진단.
2. **전처리/정규화 불일치**: `policy_server`가 `lerobot-rollout`과 동일한
   전처리기(preprocessor)·정규화 통계를 쓰는지 확인 필요. 다르면 액션 스케일이 미묘하게
   틀어져 있을 수 있다.
3. **pi0 모델 자체의 한계**: 같은 데이터(`bimanual_tilt`)로 학습한 SmolVLA는 이미 검증된
   경로(`lerobot-rollout`)로 태스크를 완수했다. pi0이 이 경로 버그가 아니라 정말로 이
   태스크에서 SmolVLA보다 약할 가능성도 배제하지 않는다 — 다만 그걸 확인하려면 위 1, 2번을
   먼저 배제해야 공정한 비교가 된다.

## 참고

사용한 프로세스 정리 방법 — 로컬 `robot_client`는 `Ctrl+C` 또는 PID로 강제 종료, 서버
`policy_server`는 SSH로 접속해 `kill <PID>`. SSH 터널은 로컬 ssh 프로세스를 종료하면 같이
끊긴다. 서버 재사용 시(다른 실험을 서버에서 돌릴 때) 이 `policy_server` 프로세스가 GPU를
계속 점유하고 있지 않은지 `nvidia-smi`로 확인할 것.
