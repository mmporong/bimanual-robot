최종 갱신: 2026-09-09

기구 모델링을 이어갈 때는 [하단 프레임 실물 치수 기록](20260909_하단프레임_실물치수_모델링기록.md)부터 읽는다.

다른 세션은 이 문서에서 시작한다. 현재 태스크와 역할의 단일 원본은

그보다 오래된 커넥터·음성·병과 컵 운반 시나리오는 결정 이력일 뿐 현행 범위가 아니다.

## 0. 한 줄

충전소에서 대기하던 이동형 양팔 로봇이 웹 요청을 받고 주방으로 가서 물을 따른 뒤,
컵을 로봇 선반에 싣고 손님 테이블로 운반·서빙하고 충전소로 복귀한다.

## 1. 절대 어기지 않는 것

| 규칙 | 이유 |
|---|---|
| 실물 팔·베이스 이동은 결정적 차단 장치가 있는 환경에서만 수행 | 오명령이 실기체 손상으로 이어진다 |
| Codex처럼 `arm-motion-guard`가 없는 환경에서는 제어 스크립트를 dry-run으로만 다룸 | 훅이 없는 실행을 승인으로 간주할 수 없다 |
| 스톨 감지 시 정지 명령을 보냄 | 로그만 남기면 서보가 계속 민다 |
| 조작 중 베이스 정지, 주행 중 팔은 운반·정지 자세 유지 | 두 계층의 동시 이동을 금지한다 |
| 스테이징은 변경 파일을 경로별로 명시 | 사용자 파일과 다른 세션 변경을 섞지 않는다 |
| 데이터셋·모델·rosbag 같은 대용량 파일은 저장소에 커밋하지 않음 | 외부 저장소와 `data/README.md` 인덱스를 사용한다 |
| ggao50 상류에는 라이선스가 없으므로 STL·STEP·G-code를 리포에 반입하지 않음 | 생성물은 저장소 밖에서 관리한다 |

GitHub Actions는 전면 금지가 아니다. 로컬 재현이 어려운 검증에만 제한적으로 사용하고,
배포·외부 전송 워크플로는 명시적 요청이 있을 때만 만든다.

## 2. 현행 태스크 흐름

```text
충전소 대기·충전
  → 웹 버튼으로 물/음료 요청
  → 주방까지 자율주행
  → 베이스 정지
  → 왼팔이 컵 파지·들기
  → 오른팔이 물통 파지·들기
  → 오른팔이 컵 위로 이동·붓기
  → 오른팔이 물통 원위치·정지
  → 왼팔이 컵을 로봇 선반에 적재
  → 손님 테이블까지 자율주행
  → 베이스 정지
  → 컵을 선반에서 손님 테이블로 이동
  → 충전소 복귀·충전
```

확정된 핵심은 세 가지다.

1. 태스크는 물 서빙 하나다.
2. 실제 키오스크 대신 웹 버튼으로 요청을 만든다.
3. 컵은 팔로 든 채 주행하지 않고 로봇 선반에 놓고 운반한다.

## 3. 조작 구간·전략 정의와 현재 충돌

### 3.1 회의에서 경계가 적힌 정책

| 미션 구간 | 범위 | 종료 상태 |
|---|---|---|
| `policy 1` | 주방의 왼팔 컵 파지부터 오른팔 붓기·물통 반환, 왼팔 컵 선반 적재까지 | 물통 원위치, 컵 선반 위, 양팔 정지 |
| `policy 2` | 테이블 도착 후 컵을 로봇 선반에서 손님 테이블로 옮김 | 컵 테이블 위, 사용 팔 정지 |

`policy 1/2`는 ACT checkpoint 이름이 아니라 미션 조작 구간의 ID다. 실제 실행은
`PLANNED_ALL`, `ACT_ALL`, `HYBRID` 가운데 하나를 선택하고 phase별 backend를 기록한다.

### 3.2 본수집 전 반드시 해결할 정책 번호

회의 TODO에는 `1순위 — 3번 policy 학습하고 배포, 실패 케이스 수집·수정`이라고 적혀
있다. 그러나 같은 메모에는 policy 3의 시작·행동·종료가 없다. 기존 R32의
`S3 RETURN_PLACE`는 회의 전 구형 정책이므로 자동 대응하지 않는다.

또한 policy 2는 본문에 왼팔이라고 적혔지만 괄호에는 오른팔이라고 적혀 있다. 이 둘을
확정하지 않고 수집을 시작하면 행동 차원과 카메라 관측 구성이 달라져 데이터를 다시
모아야 한다.

### 3.3 후속 구현 결정 — 세 전략을 같은 조건에서 비교

| 전략 | 뜻 |
|---|---|
| `PLANNED_ALL` | RGB-D·그립 계산·IK·검증 궤적·그리퍼 피드백·액면 폐루프 |
| `ACT_ALL` | 모든 조작 phase를 ACT checkpoint로 실행 |
| `HYBRID` | phase별로 PLANNED 또는 ACT 선택. 첫 후보는 `POUR`만 ACT |

주방 phase는 `CUP_PICK → JUG_PICK → MOVE_TO_PREPOUR → POUR → JUG_RETURN → SHELF_PLACE`로
기록한다. 전체 시연에 phase timestamp를 남기면 같은 원본을 전체 ACT와 로컬 ACT 학습에
재사용할 수 있다.

phase별 순차 전환에는 별도 `IK+IL` 통합 신경망이 필요하지 않다. 현재 backend 정지,
허용 자세, 남은 ACT chunk 폐기, command lease 해제·획득과 다음 backend reset이 필요하다.
같은 틱에서 두 출력을 더하는 residual 결합은 새 정책이 필요하므로 첫 구현에서 제외한다.

산업용 피킹·휴머노이드·ACT 적용 근거는
[`R33_산업용_피킹과_IL_ACT_적용경계.md`](../research/R33_산업용_피킹과_IL_ACT_적용경계.md)에 있다.

## 4. 물 양 인지 — YOLO

회의 결정은 YOLO 계열 비전을 사용한다는 것이다. 실행 개념은 다음과 같다.

```text
컵·테두리·액면 또는 액체 영역 검출
  → 컵 내부 높이 비율
  → 컵별 보정표
  → 부족 / 목표 / 과다 / 흘림 판정
```

YOLO의 바운딩 박스만으로 mL가 직접 계산되지는 않는다. 아래 항목은 미결이다.

- detection·segmentation·pose 중 학습 형식
- 투명 컵과 액면이 카메라에서 구분되는지
- 목표량과 허용 오차
- 컵별 높이-부피 보정표
- 정답 데이터 생성용 기준 계측
- 흘림 클래스 포함 여부

불투명 컵처럼 액면이 보이지 않는 조건은 RGB만으로 측정할 수 없다. 컵 재질과 시야를
고정하기 전에는 물 양 측정이 완료됐다고 쓰지 않는다.

### 6.2 URDF·IK

- SO-101 양팔, 왼쪽 기본 회전식 죠, 오른쪽 ggao50 프록시가 URDF에 있다.
- 왼쪽 `tool0`·`cup_tcp`, 오른쪽 `tool0`·`bottle_tcp`·`cup_tcp` 프레임이 있다.
- 기존 `solve_task_poses.py`는 왼팔 병·오른팔 컵인 구형 역할을 전제로 한다.
- 새 회의 역할은 왼팔 컵·오른팔 물통이므로 기존 자세를 그대로 재사용하면 안 된다.
- 이전 검증에서 `solve_task_poses.py`의 잔차·수치 자코비안 부호 불일치가 확인됐다.
  수정과 회귀 검증 전에는 정답 자세 생성기로 취급하지 않는다.
- v0.3 URDF는 Xacro·질량/관성·핵심 좌표·Isaac 정적 가져오기 계약을 통과했다.
- 실제 USD 생성·4점 접촉·joint gain·60초 안정성은 Isaac Sim 장비에서 아직 검증하지 않았다.
- 시뮬레이션 성공을 실물 성공으로 간주하지 않는다.

### 6.3 PLANNED·ACT 비교와 데이터

- 산업형 PLANNED와 LeRobot ACT를 같은 phase·scenario matrix에서 비교한다.
- 과거 실측에서 스크립트 시연 정책은 앙상블보다 `--replan 10~15` 청크 실행이 나았다.
- 이 결과는 구형 태스크에서의 관찰이므로 새 물 서빙 정책의 성공률을 보장하지 않는다.
- phase별 관측·행동·시작·종료 상태와 backend 전환이 확정되기 전에는 본수집을 시작하지 않는다.
- 전체 시연에는 phase 경계를 기록해 ACT_ALL과 phase별 ACT에 재사용한다.
- PLANNED가 만든 시작 상태와 사람 시연 상태의 차이는 HYBRID rollout에서 해당 phase만 보강한다.
- 성공 데이터만 모으지 않고 실패 구간과 수정 개입을 같은 스키마로 남긴다.
- 실패 원본은 failure bank에 보존하고, 관측 코드와 원인 가설·확정 원인을 분리한다.
- 수정 뒤에는 같은 조건 재시험과 다른 조건 회귀 검증을 각각 남긴다.
- 현행 기준선은 건식 순서 검증과 한 컵·한 고정량 평가까지다.

## 7. 현재 1순위 작업

회의가 지정한 1순위인 policy 학습·배포를 산업형 기준선과 비교 가능한 구조로 수행한다.

1. `3번 policy`의 정확한 의미와 경계를 확정한다.
2. policy 2의 팔 담당을 확정한다.
3. phase별 관측·행동·시작·종료와 `ExecuteManipulationSkill` 계약을 고정한다.
4. PLANNED_ALL mock·dry-run 기준선을 만든다.
5. phase 표시 텔레옵 시연을 수집한다.
6. ACT_ALL과 로컬 ACT를 학습하고 체크포인트·데이터 버전을 남긴다.
7. PLANNED_ALL·ACT_ALL·HYBRID rollout에서 실패를 strategy·backend·phase별로 수집한다.
8. 확인된 원인별로 시스템 수정 또는 phase 데이터 보강·재학습한다.
9. 같은 평가 조건에서 세 전략과 이전 버전을 비교한다.

실패 원본을 곧바로 BC 학습에 넣지 않는다. 먼저 하드웨어·좌표·실행기·측정 문제를 배제하고,
정책의 관측 분포 문제로 확인된 경우에만 새 성공 시연 또는 별도 HIL 복구 데이터를 만든다.

사용자의 SLAM·장애물 회피·IL/IK 작업은 이 루프와 병행한다. Isaac Sim은 현행 v0.3
URDF로 시작할 수 있으며, 실측값이 들어오면 YAML→CAD→URDF→USD 순서로 다시 생성한다.

## 8. 열려 있는 결정 — 막고 있는 순서

### 8.1 정책 3의 정의

현재 최우선 작업을 직접 막는다. 이름뿐 아니라 시작 상태, 관측, 행동 출력, 종료 조건,
사용 팔을 한 세트로 고정해야 한다.

### 8.2 policy 2 사용 팔

회의 본문은 왼팔, 괄호 주석은 오른팔이다. 수집 장비와 행동 벡터가 달라지는 결정이다.

### 8.3 YOLO 물 양 규격

라벨 형식, 컵 재질, 목표량, 허용 오차, 높이-부피 보정과 정답 계측을 정해야 한다.

### 8.4 주방·선반·테이블 좌표

컵과 물통 원위치, 선반 위치와 테이블별 Nav2 정지 자세가 필요하다. 모델과 실측값이
생기기 전에는 IK 목표를 확정할 수 없다.

### 8.5 충전소 인터페이스

Nav2 복귀 목표와 실제 충전 접점·충전 시작 판정은 별개다. 둘 다 정의돼야
`DOCKED / CHARGING` 상태를 닫을 수 있다.
