## 데이터 수집 중 키보드 오작동 — 해결됨

`lerobot-record`에서 오른쪽 화살표(다음)를 눌렀는데 재녹화가 발동해 좋은 에피소드가 날아가던
문제는 **이 세션 안에서 여러 차례 시행착오(왼쪽 화살표 비활성화 → 재녹화를 메뉴 방식으로
전환 → 전부 원상복구) 끝에, 다른 세션과 논의하며 진짜 원인을 찾아 해결됐다.**

진짜 원인은 하드웨어 고스트 키가 아니라 **`r`(재녹화) 키의 타이밍 설계 문제**였다 — `r`을
누르면 그 순간 재녹화가 확정되는 게 아니라 "환경 리셋 대기"를 먼저 거치는데, 그 대기 중에
오른쪽 화살표를 누르면 저장되는 게 아니라 대기만 조기 종료시키고, 그 직후 아까 눌렀던 `r`이
예약해 둔 재녹화가 그대로 실행됐다. `lerobot_record.py`를 재녹화 여부가 녹화 종료 즉시
확정(lock-in)되고 재녹화면 리셋 대기 없이 바로 재시작하도록 고쳐서 해결했다. 자세한 진단
과정·해결책·적용 확인 방법은
[`20260923_녹화_트러블슈팅_재녹화키_카메라인덱스.md`](20260923_녹화_트러블슈팅_재녹화키_카메라인덱스.md)
에 정리돼 있다 — 다음에 관련 문제가 또 생기면 거기부터 볼 것.

같은 문서에 **카메라 인덱스가 녹화 중 뒤바뀌는 문제**(원인 추정: 손목캠 케이블이 팔 움직임에
당겨지며 순간 재연결 → 인덱스 재배정)와 그 대응(케이블 여유 확보, 매 세션 인덱스 재확인)도
함께 정리돼 있다.

## GR00T 학습 불가 (확인됨, 더 팔 필요 없음)

- 백본(`nvidia/GR00T-N1.7-3B`)은 게이트 없이 접근 가능
- 토크나이저가 참조하는 `nvidia/Cosmos-Reason2-2B`는 게이트 모델 — jun-seo 계정으로 이미
  승인받음
- 학습 가능 파라미터를 최소(LLM·비전 인코더 프리즈)로 줄여도 1B+ 남아서, 서버 GPU(24GB)에서
  `batch_size=1`조차 OOM
- LoRA로 우회 시도 → `use_peft=True`는 **이미 파인튜닝된 lerobot 체크포인트가 있어야만
  적용 가능**하도록 막혀 있어서(`pretrained.py:413`, 우회 옵션 없음), 처음부터 LoRA로
  학습하는 경로 자체가 없음
- **결론**: 이 lerobot 버전 + 이 서버(24GB 1장) 조합으로는 GR00T 학습이 구조적으로 불가능.
  더 큰 GPU를 구하지 않는 한 재시도할 필요 없음

## pi0 로컬 추론 불가 (확인됨, 더 팔 필요 없음)

- pi0(4B)는 서버(24GB)에서 학습은 잘 됨 (`train_expert_only=true` + `dtype=bfloat16` +
  `gradient_checkpointing=true`, batch=4로 OOM 없이 정상 학습)
- 로컬(RTX 5050, 8GB)에서 실제 로봇으로 추론(롤아웃)을 시도했더니:
  - RTC 없이(sync): 추론 1회 최대 7.4초, 평균 6.22Hz (목표 30Hz) — 로봇이 뚝뚝 끊기며
    "제자리에서 흔들거림"
  - RTC 켜면: 첫 액션 청크조차 90초+ 안에 못 끝나서 **액션이 한 번도 안 나가고**, 빈
    에피소드를 저장하려다 크래시
- **결론**: 이 로컬 GPU로는 pi0 실시간 로봇 제어가 근본적으로 불가능. 로봇 하드웨어가 이
  노트북에만 연결돼 있어서 서버로 추론을 넘길 방법도 지금은 없음. pi0는 eval_loss 비교
  데이터포인트로만 쓰고 실제 롤아웃 검증은 포기하는 걸로 정리됨

## 로컬 vs 서버 lerobot 차이 (중요, 헷갈리기 쉬움)

로컬 포크와 서버의 공식 lerobot 클론은 **다른 버전**이다. 서버에서 학습한 체크포인트를
로컬로 가져와 추론할 때 config 스키마가 안 맞을 수 있다 — 실제로 pi0 체크포인트의
`config.json`에 있던 `text_tokenizer_name` 필드가 로컬 `PI0Config`엔 없어서 로드 에러가
났다. 로컬 pi0 코드는 토크나이저 이름을 config가 아니라 `processor_pi0.py`에 하드코딩해서
쓰므로, 이런 여분 필드는 로컬 체크포인트 사본에서 지워도 안전하다(서버 원본은 건드리지 말 것).
**다른 모델 체크포인트를 로컬로 가져올 때도 비슷한 문제가 생길 수 있으니, 로드 에러 나면
config.json 필드 차이부터 의심할 것.**

## 그 외 얻은 교훈

- **`save_freq`는 `eval_steps`와 같은 값으로 맞출 것.** 다르면 "진짜 최저 eval_loss 스텝"의
  체크포인트가 저장 안 될 수 있다 (ACT-20에서 실제로 겪음: 진짜 최저는 step2500인데
  save_freq=1000이라 저장 안 됐고, 저장된 것 중에서만 골라야 했음). 이후 실험부터
  `save_freq=eval_steps=500`으로 통일함.
- **체크포인트는 "가장 최근"이 아니라 "eval_loss가 가장 낮은 시점"으로 고를 것.**
  조기중단은 무개선이 patience(3)번 쌓인 뒤에 걸리므로, 중단 시점 체크포인트가 최선이
  아닐 수 있다.
- **체크포인트 HF 업로드 명명 규칙**: `{모델}_{에피소드수}E_{스텝}S` (예: `ACT_20E_2000S`,
  `smallVLA_40E_5500S`, `pi0_20E_8500S`), `jun-seo` 네임스페이스, **비공개(private=True)**로
  생성할 것 — 기본값(공개)으로 시도하면 자동 승인 정책에 막힌다.
- **rename_map은 사전학습 체크포인트를 이어받을 때만 필요.** 기본 모델에서 새로 풀파인튜닝할
  땐 데이터셋의 실제 카메라 키 이름을 그대로 쓰므로 불필요 (괜히 넣으면
  `ValueError: rename_map requires a pretrained policy checkpoint`로 막힘).
- **RTC(`--inference.type=rtc`)는 추론이 30Hz 제어 루프보다 눈에 띄게 느린 모델에만 필요.**
  SmolVLA는 있으나 없으나 큰 차이 없었지만, pi0(4B, 로컬 8GB)는 RTC로도 못 살렸다 — RTC는
  "약간 느림"을 보정하는 거지 "몇 초~몇십 초 걸리는 추론"까지 감당 못 한다.
- **`lerobot-edit-dataset --operation.type delete_episodes`는 남은 에피소드를 0부터
  순서대로 다시 번호 매긴다** (구멍이 안 남음). 삭제 전엔 항상 `total_episodes`를 먼저 확인할 것.
- **카메라 인덱스는 세션마다 바뀔 수 있다.** 매 세션 시작 시
  `C:\Users\USER\Desktop\bimanual-robot-main\output\capture_indexed.py`로 재확인할 것.
  마지막 확정 매핑: 0=오른쪽 손목캠, 2=3인칭캠, 3=왼쪽 손목캠 (단, 재확인 없이 그대로 믿지 말 것)
- **양팔 포트**: 왼팔 리더 COM5·팔로워 COM15, 오른팔 리더 COM14·팔로워 COM16. 왼팔만
  `gripper_protection=true` 필요 (스톡 회전 죠), 오른팔(ggao50)은 `false`.
- **Windows cmd에서 `lerobot-train --help` 실행 시 `UnicodeEncodeError`(cp949, em-dash
  문자) 크래시**는 `--help` 출력 자체의 인코딩 버그일 뿐, 실제 학습 실행에는 영향 없다.
- **HF 데이터셋 리포를 리네임해도 로컬 캐시 폴더명은 안 바뀐다** — `--dataset.repo_id`와
  로컬 폴더명을 수동으로 맞춰줘야 `--resume=true`가 정상 동작한다.
