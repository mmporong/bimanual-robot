# 원격 GPU 서버 SmolVLA 학습 셋업 기록

최초 작성 2026-10-14 · 조작(IL) 담당자 작성 · 목적: 과정 기록 + 포트폴리오용 소재

본수집한 60개 에피소드(held-out 12개 제외)로 SmolVLA를 학습시키기 위해
팀 공용 원격 GPU 서버에 환경을 셋업한 과정을 정리한다.

---

## 1. 드라이버 불일치 — 공유 서버라 재부팅 전에 반드시 확인한 것

**증상**: 서버에 접속해서 GPU 상태를 확인하려는데 `nvidia-smi`가 드라이버와
CUDA 버전 불일치로 실패했다.

**원인**: 커널 드라이버 모듈과 사용자 공간(userspace) 라이브러리 버전이
어긋나 있었다 — 보통 드라이버 업데이트 후 재부팅을 안 하면 생기는 상태다.

**해결 전에 먼저 한 것 — 안전 확인**: 이 서버는 **팀 공용**이라, 재부팅은
"남이 돌리고 있는 작업을 강제로 끊는" 행동이 될 수 있다. 그래서 재부팅을
실행하기 전에:
1. `w`/`who`로 다른 로그인 세션이 있는지,
2. `ps`/`nvidia-smi`로 다른 프로세스가 GPU를 쓰고 있는지
를 먼저 확인했다. 아무도 쓰고 있지 않은 걸 확인한 뒤에야 재부팅했고,
재부팅 후 `nvidia-smi`가 정상 출력되는 걸로 복구를 확인했다.

**교훈**: 공유 인프라에서는 "내 작업을 빨리 되게 하는 것"보다 **"남의 작업을
망가뜨리지 않는 것"이 우선**이다 — CLAUDE.md의 "하드 리셋 등 되돌리기 어려운
작업은 먼저 확인" 원칙이 개인 저장소뿐 아니라 공유 서버에도 그대로 적용된다.

---

## 2. 맨땅에서 시작하지 않고 팀의 기존 스크립트를 먼저 찾았다

서버에 처음 들어갔을 때 학습 파이프라인을 처음부터 짜지 않고, 팀이 이미
써둔 스크립트(`chain_smolvla40.sh`류 학습 체인 스크립트, `upload_best_pi0.py`
같은 best-checkpoint 업로드 스크립트)를 먼저 찾아서 읽고, 거기에 맞춰
명령어를 구성했다.

**교훈**: 팀 공용 저장소에서는 "내가 알아서 새로 만드는" 것보다 **"이미
검증된 팀의 패턴을 찾아서 따라가는" 게 우선**이다 — 새로 짜면 사소한 설정
하나(배치 크기, 체크포인트 저장 주기 등)를 놓쳐서 이전 실험들과 비교가
안 되는 결과를 낼 위험이 있다.

---

## 3. held-out 에피소드를 학습에서 명시적으로 제외

60개 중 12개(14,15,19,20,24,27,32,37,42,47,52,57)는 평가 전용으로 남겨둔
것이라, 학습 명령에 **`--dataset.episodes`로 제외 대상을 뺀 나머지만** 명시해서
넘겼다. "데이터셋 전체를 넣고 나중에 결과만 held-out 쪽으로 따로 본다"는
방식이 아니라, **애초에 학습 입력에서 그 12개를 아예 빼는 방식**을 썼다 —
그래야 "학습이 그 데이터를 못 봤다"는 걸 명령어 자체로 보장할 수 있고,
나중에 평가 결과를 의심받을 여지가 없다.

---

## 4. 조기 종료(EVAL_PATIENCE) — 이미 패치된 걸 재확인만

`lerobot_train.py`에 이미 팀이 patience 기반 조기 종료(`EVAL_PATIENCE`) 로직을
넣어둔 걸 확인했다 — 평가 손실이 일정 횟수 이상 개선 안 되면 자동으로 멈추는
방식이라, 과적합 지점을 넘어서까지 GPU 시간을 낭비하지 않게 돼 있었다.
새로 구현할 필요 없이 설정값만 확인하고 그대로 썼다.

---

## 5. 백그라운드 실행을 "껐다"가 아니라 "진짜로 살아있는지" 확인

`nohup ... &`로 학습을 백그라운드에 띄운 뒤 터미널 세션을 끊어도 학습이
계속 돌아야 하는데, 단순히 "명령어가 에러 없이 리턴했다"만 보고 믿지 않고
**`disown`까지 적용한 뒤 프로세스의 `PPID`가 `1`(즉 init/systemd에 입양돼
터미널 세션과 완전히 분리됨)인지 직접 확인**했다.

**교훈**: 이것도 위 "데이터 삭제가 되살아난 사고"에서 얻은 교훈과 같은
계열이다 — **"명령이 성공했다"와 "의도한 상태가 실제로 됐다"는 다르다.**
특히 SSH 세션이 끊기면 몇 시간짜리 학습이 중간에 죽을 수 있는 상황이라,
PPID 확인처럼 **외부에서 재검증 가능한 방법으로 직접 확인**하는 습관을
여기서도 그대로 적용했다.

---

## 6. 학습 완료 확인과 체크포인트 선택 — "최종 스텝"이 항상 최선은 아니다

학습이 끝난 뒤 서버 GPU가 유휴 상태(0%)인 걸 보고 "멈췄나?"부터 의심했는데,
로그 마지막 줄이 `End of training`으로 정상 종료였다. 10000/10000 스텝을
전부 돌았고(조기 종료 patience는 끝까지 안 터짐), 최종 체크포인트 저장까지
확인했다.

500스텝마다 찍힌 eval_loss를 전부 모아보니, **9000스텝(0.1632)이 최종
10000스텝(0.1668)보다 더 낮았다** — 그 뒤로는 소폭 다시 올라가는 모양이라
가벼운 과적합 신호로 봤다. 500스텝 간격으로 체크포인트가 전부 저장돼
있어서, "최종"이 아니라 **eval_loss가 가장 낮았던 9000스텝 체크포인트**를
다음 단계(로컬 배포)에 쓰기로 했다.

held-out 제외도 재확인했다 — 저장된 체크포인트의 `train_config.json`에
찍힌 `episodes` 목록을 까보니 held-out 12개(14,15,19,20,24,27,32,37,42,47,
52,57)가 정확히 빠진 48개였다. "명령어에 그렇게 썼다"가 아니라 **저장된
설정값으로 실제 반영을 재확인**했다.

**교훈**: 학습 스크립트가 "마지막에 저장한 체크포인트"를 쓰는 게 당연해
보이지만, patience가 아직 안 터진 상태로 스텝 한도에 도달해 끝난 경우엔
마지막 체크포인트가 최적이 아닐 수 있다 — eval_loss 곡선 전체를 보고
골라야 한다.

---

## 7. 포트폴리오에 쓸 만한 요약

"팀 공용 GPU 서버에서 드라이버 문제를 재부팅으로 해결하기 전에 다른
사용자의 작업 여부를 먼저 확인하는 안전 절차를 거치고, held-out 평가셋을
학습 입력 단계에서부터 명시적으로 제외해 평가 신뢰성을 명령어 수준에서
보장했으며, 백그라운드 학습 프로세스가 세션 종료 후에도 실제로 살아있는지
PPID로 직접 검증한 경험 — '명령이 성공했다'와 '의도한 상태가 실제로 됐다'를
구분해서 확인하는 습관을 데이터 운영과 인프라 운영 양쪽에 일관되게 적용했다."
