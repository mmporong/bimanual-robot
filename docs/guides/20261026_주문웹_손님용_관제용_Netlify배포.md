# 주문 웹 — 손님용·관제용 화면과 Netlify 배포

전체 시나리오의 첫 단계는 웹 주문이다(출정식 PPT 2·6·17쪽). 이를 위해 화면 두 개를 만들었다.

- **손님용 주문 화면**: 휴대폰에서 물을 주문하고 진행 상황을 본다.
- **운영자용 관제 화면**: 로봇 상태와 주문을 보고, 진행을 멈추거나 주문을 취소한다.

두 화면은 기존 주문 서버(`apps/service_order/service_order_server.py`)의 API를 그대로 쓴다.
이 서버의 주문·Mission 상태기계는 [웹 주문 dry-run 문서](../experiments/20260922_웹주문_미션관제_dry-run.md)에 있다.
2026-10-26 작업이다.

## 1. 바로 보기

| 화면 | 공개 주소(데모) | 로컬 서버 |
|---|---|---|
| 손님용 | https://ms-water-serving.netlify.app/order?table=3 | `http://127.0.0.1:8765/order?table=3` |
| 관제용 | https://ms-water-serving.netlify.app/control | `http://127.0.0.1:8765/control` |

- 공개 주소는 **체험용 데모**다. 실제 로봇과 연결되지 않으며 화면 위에 그 사실이 표시된다.
- 사이트 루트(`/`)는 손님 화면으로 넘어간다.
- Netlify 프로젝트 이름은 `ms-water-serving`이다(팀 `jjs6350`). 방문자 로그인 보호는 2026-10-26에 사용자가 해제해 공개 상태다.

## 2. 손님용 주문 화면 (`/order`)

> 2026-10-27에 화면 디자인을 식당 키오스크로 바꿨다(11절). 아래 흐름·API·단계 묶음은 그대로다.

휴대폰 세로 화면을 기준으로 만들었다. 375px 폭에서 가로 넘침이 없음을 확인했다.

1. **테이블 선택**
   - `?table=3`처럼 테이블 번호가 주소에 있으면 이 단계를 건너뛴다. 테이블 QR에 이 주소를 넣는 용도다.
   - 번호가 없거나 지도에 없는 번호면 1~4번 버튼을 보여 준다.
2. **음료 선택**: 냉수 또는 온수를 고른다. 음료를 고르기 전에는 `주문하기` 버튼이 꺼져 있다.
3. **진행 상황**: 로봇 내부의 11단계를 손님이 알아보기 쉬운 5단계로 묶어 보여 준다.

   | 손님 화면 단계 | 로봇 phase |
   |---|---|
   | 주문 접수 | 대기열(QUEUED) |
   | 주방으로 이동 | NAVIGATE_KITCHEN, ALIGN_KITCHEN |
   | 물 따르기 | GRASP_CUP ~ PLACE_DECK |
   | 테이블로 이동 | NAVIGATE_TABLE, ALIGN_TABLE |
   | 테이블에 놓기 | REGRASP_CUP, SERVE |

   - 대기 중이면 "앞에 N건의 주문이 있어요"가 나온다.
   - 완료되면 "물이 도착했어요"가 나온다.
   - 실패하면 "직원이 확인 후 직접 가져다드릴게요"가 나온다.
4. **취소**: 아직 대기 중인 주문만 취소할 수 있다. 준비가 시작되면 취소 버튼이 사라진다.
5. **새로고침·링크 공유**: 주문하면 주소에 `order=<주문 번호>`가 붙는다. 새로고침하거나 그 주소를 다시 열어도 같은 주문을 계속 보여 준다.

주문 번호는 `WEB-YYYYMMDD-HHMMSS-xxxx` 형식이다. 서버는 이 번호를 멱등 키로 쓰므로, 같은 주문을 다시 보내도 중복으로 생기지 않는다.

## 3. 운영자용 관제 화면 (`/control`)

| 영역 | 내용 |
|---|---|
| 상단 상태 | 로봇 상태, 현재 위치, 배터리, 실행 모드, 마지막 갱신 시각(1초마다 갱신) |
| 현재 작업 | 테이블·음료·주문 번호, 11단계 중 현재 단계. 재시도 중이면 몇 번째 시도인지 표시 |
| 대기 주문 | 순서·주문 번호·테이블·음료·접수 시각, 주문별 취소 |
| 최근 주문 | 끝난 주문 10건(완료·실패·취소). 실패하면 어느 단계에서 왜 실패했는지 표시 |
| 직원 대리 주문 | 테이블·음료를 골라 등록. 주문 번호는 `STAFF-…` |
| 손님 주문 링크 | 테이블별 손님 화면 주소 |
| 이벤트 기록 | 최근 30건(주문 접수, 단계 완료, 실패, 취소, 충전소 복귀 등) |

조작 버튼은 다음과 같다.

- **자동 진행 일시정지·재개**
  - 다음 단계를 시작하지 않게 한다. 진행 중인 단계는 끝까지 수행한다.
  - **비상 정지가 아니다.** 실기체 비상 정지는 기존 하드웨어 정지 절차를 따른다.
- **현재 주문 중단**: 진행 중인 주문을 취소한다. 로봇은 다음 주문이나 충전소 복귀로 넘어간다.
- **시험 도구**: dry-run과 데모 모드에서만 보인다.
  - 한 단계 진행
  - 현재 단계 실패 주입(`OPERATOR_INJECTED`)
  - 데모 초기화(데모 모드만)

기존의 상세 관제 화면(`/`, 지도·진단 포함)은 개발용으로 그대로 두었다.

## 4. 서버 변경

`apps/service_order/service_order_server.py`를 다음과 같이 바꿨다.

- **화면 경로 추가**: `/order`, `/order.js`, `/control`, `/control.js`, `/api.js`, `/config.js`.
- **`POST /api/control {"paused": bool}`**: 자동 진행을 일시정지하거나 재개한다. `/api/state`에 `auto_paused`가 포함된다.
- **`--cors-origin <주소>`**: 다른 주소(예: Netlify)에 올린 화면이 이 서버 API를 부를 수 있게 허용한다.
  - 지정하지 않으면 이전과 같다(CORS 헤더 없음, `OPTIONS`는 405).

로컬 실행 방법은 기존과 같다.

```bash
cd "$HOME/bimanual-robot"
python3 -m apps.service_order.service_order_server --port 8765               # 이 PC에서만
python3 -m apps.service_order.service_order_server --host 0.0.0.0 --port 8765 # 같은 망의 휴대폰에서도
```

로그인 같은 인증은 없다. `0.0.0.0`으로 열 때는 같은 내부망에서만 쓴다.

## 5. 서버 연결 방식 (`static/api.js`)

두 화면은 공통 모듈 `api.js`를 통해서만 서버와 통신한다. 연결 대상은 다음 순서로 정한다.

1. 주소의 `?api=<값>` (브라우저가 기억한다. `?api=`처럼 빈 값을 주면 지운다)
2. `config.js`의 `window.ORDER_API_BASE`
3. 둘 다 없으면 화면을 내려준 서버(같은 주소)의 `/api`

값이 `demo`이면 **브라우저 데모 모드**로 동작한다.

- 서버 없이 브라우저 안에서 주문 서버와 같은 흐름을 흉내 낸다. 주문, 대기열, 단계 진행(2.5초 간격), 취소, 일시정지, 실패 주입, 충전소 복귀가 동작한다.
- 상태는 그 브라우저의 IndexedDB에 저장된다.
  - 같은 브라우저의 탭끼리는 공유된다. 예를 들어 손님 탭에서 주문하면 관제 탭에 보인다.
  - **다른 기기 사이에는 공유되지 않는다.** 휴대폰 주문이 노트북 관제 화면에 나오지 않는다.
- 처음에는 localStorage를 썼다. E2E 시험 중 두 탭이 동시에 쓰면 서로의 변경을 덮어쓸 수 있는 구조임을 확인했다. 그래서 읽기-수정-쓰기를 IndexedDB 트랜잭션 하나로 묶었다.

## 6. Netlify 배포

Netlify에는 정적 파일만 올라간다. 파이썬 주문 서버는 올라가지 않는다.

```bash
cd "$HOME/bimanual-robot"
python3 -m apps.service_order.build_netlify --out /tmp/netlify_order        # 데모 묶음(기본)
npx -y netlify-cli login                                                     # 처음 한 번
npx -y netlify-cli deploy --dir /tmp/netlify_order --prod --site ms-water-serving
```

`build_netlify.py`가 만드는 묶음은 다음과 같다.

- 화면 파일 5개: `order.html`, `order.js`, `control.html`, `control.js`, `api.js`
- `config.js` (`ORDER_API_BASE = "demo"`)
- `_redirects` (`/` → `/order`)

`--api-base https://<서버 주소>`를 주면 데모 대신 그 서버에 연결하는 묶음을 만든다.

### 실제 로봇 서버에 연결하려면

1. 노트북에서 주문 서버를 실행한다: `--cors-origin https://ms-water-serving.netlify.app`.
2. 서버를 **HTTPS 주소**로 외부에 연다(예: Cloudflare 터널).
   - Netlify 화면은 HTTPS라서 `http://` 서버 주소는 브라우저가 막는다(mixed content).
3. 화면 주소에 `?api=https://<서버 주소>`를 붙여 연다. 그 브라우저가 연결 대상을 기억한다.

이 연결은 아직 실제로 해 보지 않았다. 서버 CORS 동작만 단위 시험으로 확인했다.

## 6-1. 팀원이 서버에 연결해 여는 방법

서버는 한 대(노트북)에서만 실행한다. 손님 화면과 관제 화면이 모두 그 서버에 붙으므로, 휴대폰에서 넣은 주문이 다른 사람의 관제 화면에 바로 보인다.
지금 서버의 기본 모드는 dry-run이다. 주문은 실제로 처리되지만 로봇은 움직이지 않는다.

### 방법 A — 같은 Wi-Fi (권장, 2026-10-26 확인)

1. 서버 노트북의 저장소 루트에서 실행한다.

   ```bash
   # Ubuntu / WSL
   python3 -m apps.service_order.service_order_server --host 0.0.0.0 --port 8765
   ```
   ```powershell
   # Windows (conda 환경 등 Python 3.10 이상)
   python -m apps.service_order.service_order_server --host 0.0.0.0 --port 8765
   ```

2. 노트북 IP를 확인한다.
   - Windows: `ipconfig`에서 Wi-Fi의 IPv4 주소
   - Ubuntu: `hostname -I`의 첫 값
3. 같은 Wi-Fi에 연결된 팀원이 브라우저로 연다.
   - 손님: `http://<노트북 IP>:8765/order?table=1`
   - 관제: `http://<노트북 IP>:8765/control`

주의할 점은 다음과 같다.

- Windows에서 처음 실행할 때 방화벽 팝업이 뜨면 **허용**을 누른다.
- 학교·카페 Wi-Fi는 기기끼리 통신을 막는 경우가 있다. 열리지 않으면 휴대폰 핫스팟에 노트북과 팀원 기기를 함께 연결한다.
- 2026-10-26 확인 범위: Windows 노트북의 Wi-Fi 주소(`192.168.0.15:8765`)로 `/order`, `/control`, `/api/health`가 응답했다. python 인바운드 방화벽 허용 규칙도 확인했다. 다른 기기에서 실제로 열어 보지는 않았다.

### 방법 B — 다른 네트워크에서 (Cloudflare 임시 터널, 미검증)

팀원이 다른 곳에 있거나 같은 Wi-Fi에서 막힐 때 쓴다.

1. 서버 노트북에 `cloudflared`를 설치한다.
   - Windows: `winget install --id Cloudflare.cloudflared`
   - Ubuntu: Cloudflare 배포 페이지의 `.deb`
2. 서버를 실행한다. 이 방법에서는 `--host` 옵션이 필요 없다.

   ```bash
   python3 -m apps.service_order.service_order_server --port 8765 --cors-origin https://ms-water-serving.netlify.app
   ```

3. 다른 터미널에서 터널을 연다: `cloudflared tunnel --url http://localhost:8765`.
   출력에 `https://<임의 이름>.trycloudflare.com` 주소가 나온다.
4. 팀원은 둘 중 하나로 연다.
   - **터널 주소로 직접 열기**:
     - 손님: `https://<터널 주소>/order?table=1`
     - 관제: `https://<터널 주소>/control`
   - **Netlify 주소로 열기**: `https://ms-water-serving.netlify.app/order?table=1&api=https://<터널 주소>`
     - 관제 화면도 같은 방식으로 `?api=`를 붙인다.
     - `?api=` 값은 그 브라우저가 기억한다. 데모로 돌아가려면 `?api=demo`를 붙인다.
     - 이 방식에는 서버의 `--cors-origin` 옵션이 필요하다(2번 명령에 포함).

주의할 점은 다음과 같다.

- 터널 주소를 아는 누구나 관제 화면을 열 수 있다(인증 없음). 시연·시험할 때만 열고 끝나면 `Ctrl+C`로 닫는다.
- 터널 주소는 실행할 때마다 바뀐다. 매번 새 주소를 팀원에게 공유한다.

### 실제 로봇으로 처리하려면

화면과 연결 방법은 위와 같고, 서버의 `--backend`만 바꾼다(예: `ros2-mock`).
각 backend의 조건은 [웹 주문 dry-run 문서](../experiments/20260922_웹주문_미션관제_dry-run.md)를 따른다.
실기체 주행·조작 backend는 아직 연결되지 않았다.

## 7. 검증

| 항목 | 방법 | 결과 |
|---|---|---|
| 서버·화면 제공, CORS, 일시정지 | `tests/apps/test_service_order_server.py`에 시험 5개 추가 | 30개 중 29개 통과. 실패 1개(`test_roundtrip_timeout_requests_cancel_and_marks_unknown`)는 변경 전 코드에서도 같은 실패 |
| 데모 상태기계 | Node에서 주문 3건(성공·실패 주입·취소), 일시정지, 잘못된 주문 거부 | 기대대로 동작 |
| 공개 사이트 E2E | `apps/service_order/e2e_demo.js`(puppeteer-core + Edge)로 실제 버튼 클릭 | 14개 항목 전부 통과, 배포 주소에서 3회 |

E2E 14개 항목은 다음과 같다.

1. 음료 선택 전 주문 버튼 비활성
2. QR 테이블 번호 표시
3. 375px 폭 가로 넘침 없음
4. 주소에 주문 번호 기록
5. 관제 화면에 현재 주문 표시
6. 일시정지 배너 표시
7. 일시정지 중 단계 멈춤
8. 한 단계 진행
9. 대리 주문 2건이 대기열에 들어감
10. 관제에서 대기 주문 취소
11. 손님 화면 완료 표시
12. 대기 순서 안내
13. 손님이 대기 주문 취소
14. 관제 최근 주문에 완료·취소 기록

E2E 첫 실행에서 "완료 표시"가 실패한 적이 있다. 원인은 시험 코드였다. "곧 도착해요"에도 "도착"이 들어 있어서 완료 전에 기다리기를 끝냈다. 대기 조건을 정확한 문구로 고친 뒤 통과했다.

## 8. 남은 일과 한계

- **실기체 연결**: 주문 서버의 주행(Nav2)·조작(IL 정책) backend가 아직 실기체와 연결되지 않았다. 이 화면은 dry-run과 데모에서만 검증됐다.
- **인증 없음**: 손님 화면과 관제 화면 모두 로그인 없이 열린다. 관제 화면을 공개 주소에서 실서버에 연결할 때는 접근 제한(사내망, 터널 인증 등)이 먼저 필요하다.
- **테이블 QR**: 아직 QR 이미지는 만들지 않았다. 주소는 `…/order?table=N`이다.
- **음료 종류**: 서버 설정(`config/simulation/service_mission_control.json`)에 있는 냉수·온수 두 가지만 지원한다.
- **비상 정지**: 웹에는 비상 정지가 없다. 일시정지는 다음 단계를 시작하지 않을 뿐이다.

## 10. 웹 주문으로 실제 주행을 트리거할 수 있나 (검토, 미구현)

결론: 가능하다. 주행 실행기를 부르는 연결은 짧은 작업이다. 다만 급수대·테이블에서 팔 작업이 끝날 때까지 기다리는 신호가 지금 주행 코드에 없다. 이 신호를 추가하는 것이 핵심 작업이다.

### 지금 있는 것 (origin/main 3c7f660 기준)
- 실차 주행 진입점은 노트북에서 실행하는 `tools/jdamr/jdamr_depart.py go table_0N`이다.
  - 명령 하나로 도크 → 급수대 → 테이블 → 도크 복귀까지 실행한다.
  - 노트북이 SSH로 파이에 상주한 실행기(`box_service`)에 요청을 보낸다.
  - 이 스크립트 주석에도 "운영자의 `출발 table_0N`은 웹 호출을 대신한다"고 적혀 있다.
- 웹 주문 서버(`apps/service_order`)의 `navigate` 명령은 아직 즉시 성공을 돌려주는 mock이거나 Isaac 시뮬 안에서 처리된다. 실차와 연결되어 있지 않다.
- 급수대와 테이블에서는 고정 시간(`--dwell-s`, 0~120초)만 머문 뒤 다음 구간으로 떠난다. 팔 작업 완료 신호는 받지 않는다.

### 걸리는 시간 (주문 → 바퀴 움직임)
- 파이의 base·Nav2·상주 실행기가 켜져 있고 도크에서 위치 초기화(`init`)가 끝난 상태라고 가정한다.
- 이 경우 실차 기록상 첫 출발 준비에 약 11초가 걸렸다(2026-10-20). 세부 원인은 미확정이다.
- 웹 요청 처리와 SSH 제출은 1초 안팎일 것으로 본다. 따라서 주문 후 10~15초 안에 출발할 것으로 예상한다(실측 아님).
- 위치 초기화나 서비스 기동이 안 된 상태라면 그 시간이 더 걸린다. 이 시간은 기록이 없다.
- 조작 실행기(`rollout_service.py`)는 출발과 동시에 켜면 주방 도착 전에 준비가 끝난다(약 1분). 정렬 후 호출하면 시작 자세 이동(약 5초) + 0.4초 뒤 팔이 움직인다.

### 연결 방법 (제안)

| 단계 | 내용 | 예상 작업량 |
|---|---|---|
| ① 웹 → 주행 | 주문 서버에 실차 backend 추가: 주문의 테이블로 `jdamr_depart.py go table_0N` 실행, 상태·종료 코드를 phase로 반영 | 반나절 (dry-run 시험 포함) |
| ② 정렬 → 조작 | 급수대·테이블 정차(dwell) 구간에서 고정 시간 대신 "조작 완료" 신호를 기다리고, 정차 시점에 `rollout_service`의 `/run/pour`·`/run/place` 호출 | 1~2일 (실차 시험 포함) |
| ③ 실패 처리 | 조작 실패·중단 결과를 받으면 그 자리 유지 또는 도크 복귀로 분기 | ②와 함께 |

- ②는 `src/navigation`의 파이 실행기를 고쳐야 한다. 주행 담당자와 함께 main 기준 작업 브랜치에서 PR로 진행한다.
- 임시방편으로 `--dwell-s`를 조작 최대 시간보다 길게 줄 수는 있다. 하지만 팔이 아직 움직이는 중에 차가 출발할 수 있어 쓰지 않는다. "팔이 움직일 때 바퀴는 정지" 규칙 위반이다.

## 11. 손님 화면 식당 키오스크 개편 (2026-10-27)

데모 영상에서 "있어 보이는" 주문 화면이 필요해 손님 화면(`order.html`, `order.js`)의 디자인만 바꿨다. 서버 API, 주문 번호 형식, QR `?table=N`, 대기 중 취소, 새로고침 복구는 그대로다.

**구성**
- 상단 간판 `MS RESTAURANT`와 테이블 번호 표시.
- 탭 4개: **로봇 서빙** / 식사 / 사이드 / 음료.
  - 첫 화면은 로봇 서빙 탭이다. 실제로 주문되는 메뉴는 여기 있는 **얼음 냉수·따뜻한 온수 두 개뿐**이고 큰 카드로 보여 준다.
  - 식사(덮밥·파스타·스테이크·리조또), 사이드(샐러드·감자튀김), 음료(레몬에이드·콜라·탄산수)는 매장 분위기용이다. 가격과 그림은 있지만 "준비 중"으로 흐리게 표시되고 누를 수 없다.
- 넓은 화면(900px 이상)에서는 오른쪽에 주문 내역 패널(테이블 선택 + 주문하기)이 붙고, 휴대폰에서는 아래에 주문 바가 붙는다.
- `주문하기`를 누르면 확인 창이 한 번 뜨고 `주문 확정`을 눌러야 주문이 나간다. 데모 촬영 때 누르는 순서는 **메뉴 → 주문하기 → 주문 확정**이다.
- 진행 화면: 영수증 모양의 큰 주문 번호(주문 번호 끝 4자리), 단계별 그림(접수 → 로봇 → 따르기 → 완료), 5단계 진행 막대.

**색**
- 최종발표 표지와 같은 계열로 맞췄다: 흰 배경, 남색 글자(`#1f3553`), 파란 강조(`#1677c8`), 연한 하늘색 그림 바탕(`#e8f4fc`).
- 의미가 있는 색은 따로 둔다: 완료 초록, 실패 빨강, 온수 김 주황.
- 처음에는 어두운 바(bar) 콘셉트로 만들었으나 팀 콘셉트와 맞지 않아 식당 + 흰 배경으로 바꿨다(사용자 결정).

**구현 메모**
- 저장소 시험이 `innerHTML` 사용과 외부 주소(`http://`, `https://`)를 금지한다. 그래서 그림은 `order.html`의 `<template id="art-이름">` 인라인 SVG에 두고 `order.js`가 복제해 쓴다.
- `e2e_demo.js`는 확인 창 단계(`#confirm-ok`)를 거치도록 바꾸고 "첫 화면은 로봇 서빙 메뉴 2개" 검사를 추가했다.

**검증**
- Netlify 빌드를 로컬에서 띄워 E2E 15개 항목 통과(375px 가로 넘침 없음 포함). 메뉴·선택·확인 창·진행·준비 중 탭 화면을 캡처해 확인했다.
- 서버 시험 30개 중 29개 통과. 실패 1개(`test_roundtrip_timeout_requests_cancel_and_marks_unknown`)는 변경 전부터 실패하던 시험이다.
- Netlify에 재배포했고 공개 주소의 `/order`에 새 화면이 뜨는 것을 확인했다. 관제 화면(`/control`)은 바꾸지 않았다.

## 12. 실제 로봇과 연동해 실사용하려면 (정리, 2026-10-27)

**연결 구조**
```
손님 폰 (/order)  --주문-->  주문 서버 (노트북 :8765, --backend rollout-service)
관제 화면 (/control) --정렬 완료 버튼-->   |
                                          v  GRASP_CUP / REGRASP_CUP 단계에서 호출
                              상주형 조작 실행기 (노트북 :8770, rollout_service.py)
```
- 팔: `GRASP_CUP`에서 물따르기 정책, `REGRASP_CUP`에서 컵배치 정책을 실제로 실행하고 결과가 손님 화면 단계에 반영된다.
- 주행·충전: 아직 즉시 성공 mock이다. 차는 사람이 옮기거나 주행 명령을 따로 주고, 정렬되면 관제 화면 [정렬 완료]를 누른다.

**노트북에 연결돼야 하는 것** (조작 실행기가 직접 팔·카메라를 연다)
| 연결 | 개수 | 비고 |
|---|---|---|
| 팔로워 팔 USB 시리얼 | 2 | `start_scenario.bat` 기준 COM15·COM16. USB 구멍을 바꾸면 번호가 바뀔 수 있어 장치 관리자로 확인 |
| 카메라 USB | 3 | 왼 손목, 오른 손목, 상단 depth. 번호는 실행 때 자동 대입(`{left}` `{right}` `{depth}`) |
| 팔 전원 | 2 | 12V 어댑터 |
- 리더 팔은 필요 없다. NVIDIA GPU 노트북(`--policy.device=cuda`)에서 주문 서버도 같이 띄운다.
- 손님 폰은 노트북과 **같은 Wi-Fi**에서 `http://<노트북 IP>:8765/order?table=N`으로 연다(테이블별 QR).

**실행 순서**
1. `tools/rollout/start_scenario.bat`: 조작 실행기(정책 2개 로드·팔·카메라 연결·예열 후 현재 자세 대기), 주문 서버, 관제 화면을 함께 띄운다.
2. 관제 화면에서 조작 실행기가 준비 상태가 될 때까지 기다린다.
3. 주문 → 차를 주방에 정렬 → [정렬 완료] → 물따르기 → 차를 테이블에 정렬 → [정렬 완료] → 컵배치 → 손님 화면 "물이 도착했어요".

**제약과 남은 일**
- Netlify(https) 페이지는 노트북의 http 서버를 부를 수 없다(브라우저 혼합 콘텐츠 차단). Netlify는 발표 데모용이고 실사용은 노트북 주소로 연다.
- **주문 → 서빙 전체를 실물 팔로 시험한 적이 아직 없다.** 다음 단계는 읽기 진단(COM 포트·카메라 인식) → 사용자 확인 후 통합 시험이다.
- `start_scenario.bat`의 정책은 PC에 있는 SmolVLA 80 최적 체크포인트다. 서버·Brev에서 학습 중인 π0·GR00T·ACT는 HF에만 있으므로, 실기체에 쓸 모델을 정한 뒤에만 받는다.
- 완전 자동화(주행 → 정렬 완료 자동 신호)는 10절의 ②작업이 필요하다.
