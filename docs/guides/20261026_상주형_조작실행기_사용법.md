# 상주형 조작 실행기 — 출발할 때 미리 준비하고, 정렬이 끝나면 바로 실행

`tools/rollout/rollout_handoff.py`는 작업마다 새로 실행한다. 실행할 때마다 라이브러리와 모델을 불러오고 팔·카메라를 연결해서, 추론 명령을 내린 뒤 실제로 움직이기까지 1분 넘게 걸렸다.
주방에 정렬한 뒤 1분을 더 기다리면 서빙 흐름이 끊긴다.

`tools/rollout/rollout_service.py`는 이 준비를 충전소 출발과 동시에 한 번만 한다. 그 뒤 단계별 호출(`pour`, `place`)이 오면 해당 정책을 바로 실행한다.

## 1. 흐름

```text
[충전소 출발과 동시에 실행]
  그리퍼 사전 이완 → 물따르기 정책 로드 → 팔·카메라 연결(1번)
  → 컵배치 정책 로드 → 두 정책 모두 현재 관측으로 추론 예열(팔은 움직이지 않음)
  → 대기 (현재 자세 유지, 1초마다 관측만 읽음)
[주방 정렬 완료] 호출 pour  → 시작 자세(pour) 이동 → 물따르기 → 작업 끝 감지 → 그 자리 유지 → 대기
[테이블 정렬 완료] 호출 place → 컵배치 → 작업 끝 감지 → 끝 자세(place_end) → 대기
[다음 주문] 다시 pour부터 … 끝낼 때 shutdown
```

- **포트·카메라 공유**
  - 팔 포트와 카메라는 한 프로그램만 열 수 있다. 그래서 두 정책이 한 연결을 나눠 쓴다.
  - 명령어 두 개를 따로 띄우면 두 번째가 연결에서 실패한다.
- **작업별 부가 기능**: 시작·끝 자세, 붓기 훅, 작업 끝 자동 감지는 `rollout_handoff.py`와 같은 코드를 쓴다.
- **바퀴와 팔**
  - 시작 자세 이동은 호출을 받은 뒤에만 한다. 대기 중에는 팔에 아무 명령도 보내지 않는다.
  - 따라서 "팔이 움직일 때 바퀴는 정지" 규칙은 호출하는 쪽이 지킨다. 정렬이 끝나 바퀴가 멈춘 뒤 호출해야 한다.

## 2. 실행

평소 `rollout_handoff.py`에 붙이던 로봇·카메라 인자를 그대로 쓴다. 다른 점은 다음과 같다.

- `--policy.path`·`--task`·`--duration`·`--strategy.type`은 빼고, 작업별 `--pour.*`·`--place.*`로 준다.
- 카메라 번호 자리의 `{left}` `{right}` `{depth}` 자동 채움은 그대로 된다.

```bat
"C:\Users\USER\miniconda3\envs\so101_env\python.exe" tools\rollout\rollout_service.py ^
  --pour.policy="C:\Users\USER\lerobot-training\outputs\water_pour_chassis_smolvla_80\checkpoints\016000\pretrained_model" ^
  --place.policy="C:\Users\USER\lerobot-training\outputs\cup_place_chassis_smolvla_80\checkpoints\007000\pretrained_model" ^
  --end.tol=15 ^
  --policy.device=cuda --robot.type=bi_so_follower --robot.id=arms --robot.calibration_dir=calibration\bi_follower ^
  --robot.left_arm_config.port=COM15 --robot.left_arm_config.gripper_protection=true ^
  --robot.left_arm_config.disable_torque_on_disconnect=false --robot.left_arm_config.max_relative_target=20 ^
  --robot.left_arm_config.cameras="{ wrist: {type: opencv, index_or_path: {left}, width: 640, height: 480, fps: 30} }" ^
  --robot.right_arm_config.port=COM16 --robot.right_arm_config.disable_torque_on_disconnect=false ^
  --robot.right_arm_config.max_relative_target=20 ^
  --robot.right_arm_config.cameras="{ wrist: {type: opencv, index_or_path: {right}, width: 640, height: 480, fps: 30} }" ^
  --robot.cameras="{ top: {type: opencv, index_or_path: {depth}, width: 640, height: 480, fps: 30, mirror: true} }"
```

`준비 완료 …s -> 호출 대기`가 찍히면 준비가 끝난 것이다. 준비 중에 호출하면 `409 not_ready`를 돌려준다.

### 작업별 기본값

| 작업 | 시작 자세 | 끝 자세 | 작업 끝 자동 감지 | 최대 시간 | task 문자열 |
|---|---|---|---|---|---|
| `pour` | `pour` | `final` (그 자리 유지, 그리퍼 미는 힘만 줄임) | `pour` | 100 s | 차체 결합 물따르기 데이터셋과 같음 |
| `place` | 없음 | `place_end` | `place` | 50 s | 차체 결합 컵배치 데이터셋과 같음 |

- 바꾸는 인자: `--pour.start_pose`, `--pour.end_pose`, `--pour.auto`, `--pour.duration`, `--pour.task`. `place`도 같은 형식이다.
- 붓기 훅을 켜려면 `--pour.hook`을 붙인다. 훅 값은 `--hook.*`로 준다.
- 공통 인자도 `rollout_handoff.py`와 같다: `--grip.margin`, `--start.move_s`, `--start.max_speed`, `--start.tol`, `--end.move_s`, `--end.tol`, `--end.settle_s`, `--end.place_tol`.
- `--end.tol=15` 권장: 차체 결합 데이터의 물따르기 끝 자세는 기본 허용치 10°에 자주 걸린다. 근거는 [SmolVLA 60 vs 80 문서](../experiments/20261025_차체결합_SmolVLA_60vs80_학습결과.md)의 4절이다.

## 3. 호출

| 방법 | 명령 | 동작 |
|---|---|---|
| 명령줄 | `python tools\rollout\rollout_service.py call pour` | 작업이 끝날 때까지 기다렸다가 결과를 출력 |
| 명령줄 | `... call place` / `... status` / `... stop` / `... shutdown` | |
| HTTP | `POST http://127.0.0.1:8770/run/pour` | 끝날 때까지 기다렸다가 결과 JSON을 돌려줌 (`?wait=0`이면 바로 202) |
| HTTP | `GET /status` | 상태(`loading`/`ready`/`running`), 현재 작업, 최근 결과, 준비 시간 |
| HTTP | `POST /stop` | 진행 중인 작업 중단. 팔은 그 자리에 유지하고 그리퍼 미는 힘만 줄임 |
| HTTP | `POST /shutdown` | 팔 연결을 끊고 종료. 토크는 `disable_torque_on_disconnect` 설정을 따름 |

- 주행 쪽이나 주문 서버는 정렬이 끝나면 `POST /run/pour`를 부르고, 응답이 오면 다음 이동을 시작하면 된다.
- 다른 PC에서 부르려면 `--listen 0.0.0.0:8770`으로 연다. 인증이 없으므로 로봇 내부망에서만 쓴다.
- 한 번에 한 작업만 실행한다. 실행 중에 다른 호출이 오면 `409`를 돌려준다.

### 결과 JSON

```json
{"task": "pour", "ok": true, "reason": "auto_done", "start_pose_s": 5.6, "run_s": 41.2,
 "call_to_first_action_s": 6.0, "policy_first_action_s": 0.4}
```

| `reason` | 뜻 | 끝난 뒤 팔 |
|---|---|---|
| `auto_done` | 작업 끝 자동 감지 (`ok: true`) | 끝 자세 |
| `duration` | 끝을 감지하지 못한 채 최대 시간 도달. 성공 여부는 사람이 확인 | 끝 자세 |
| `stopped` | `/stop` 또는 Ctrl+C | 그 자리 유지 |
| `start_pose_failed` | 시작 자세에서 10° 넘게 벗어남. 추론하지 않음 | 그 자리 유지 |
| `pour_hook_fault` | 붓기 훅 스톨 | 그 자리 유지 |
| `error: …` | 예외 | 그 자리 유지 |

- `call_to_first_action_s`: 호출부터 정책의 첫 동작까지 걸린 시간. 시작 자세 이동 시간이 포함된다.
- `policy_first_action_s`: 정책 실행 시작부터 첫 동작까지 걸린 시간.

## 4. 검증 (2026-10-26, 하드웨어 없이)

실제 팔 대신 가짜 로봇(무작위 카메라 영상, 관절 0°)에 실제 두 체크포인트를 붙여 시험했다. 시험 PC는 RTX 5050 Laptop(8 GB)이다.

| 항목 | 결과 |
|---|---|
| 두 정책 로드(시작 때 1번) | 72.6 s |
| 첫 추론 예열 | 물따르기 4.11 s(CUDA 초기화 포함), 컵배치 0.42 s |
| 예열 뒤 추론 1회 | 0.39~0.41 s |
| 호출 → 정책 첫 동작 | 0.40~0.41 s (시작 자세 이동 제외) |
| GPU 최대 사용량 | 2.33 GiB (두 정책 동시 상주) |
| 예열 중 팔 명령 | 0회 |
| 호출 흐름 | `pour` → `place` 순차 실행 · 없는 작업 404 · 실행 중 다른 호출 409 · `/stop` 1초 안에 중단 · 결과가 `/status`에 남음 |

- 기존 방식이 1분 넘게 걸리던 준비는 시작 때 한 번으로 옮겨졌다. 호출 뒤에는 시작 자세 이동(약 5 s) + 0.4 s만 남는다.
- **실기체 확인 필요**: 실제 팔·카메라로는 아직 돌리지 않았다. 아래는 실물에서 처음 돌릴 때 확인한다.
  1. 준비 완료까지 걸린 시간 (`timings.ready_total_s`)
  2. 대기 중 그리퍼 과부하가 생기지 않는지
  3. 대기가 길 때(수 분) 첫 호출에서 카메라 시간 초과가 나지 않는지
  4. `pour` → `place` 연속 실행에서 끝 자세가 의도대로인지

## 5. 기존 래퍼와의 관계

- `rollout_handoff.py`는 그대로 쓸 수 있다(작업 하나씩 실행).
- 이번에 시작 자세 이동(`move_to_start_pose`)과 그리퍼 미는 힘 줄이기(`relax_grippers`)를 함수로 분리했다. 두 실행기가 이 함수를 같이 쓴다. 동작은 바뀌지 않았다.

## 6. 시나리오 통합 실행 (주문 서버와 연결)

시연에서는 카메라·팔·정책을 시나리오 시작부터 끝까지 유지한다. 실행기를 사람이 따로 부르지 않고, 주문 서버가 단계에 맞춰 부른다.

### 한 번에 켜기
```bat
tools\rollout\start_scenario.bat
```
이 배치 파일은 세 가지를 한다.
1. 창 `manip-service`: 위 2절의 상주형 실행기
2. 창 `order-server`: 주문 서버를 `--backend rollout-service --host 0.0.0.0`으로 실행
3. 관제 화면 `http://127.0.0.1:8765/control`을 연다

정책 경로와 COM 포트는 파일 맨 위의 `set` 줄에서 바꾼다. 관제 화면의 실행 모드 칸에 `rollout_service · 조작 대기`가 보이면 주문을 받을 수 있다. 준비 중에 들어온 주문은 준비가 끝날 때까지 기다린다.

### 주문 한 건의 흐름
| 주문 phase | 무엇을 하나 |
|---|---|
| 주방 이동 | (주행 미연동) 즉시 통과 |
| **주방 정렬** | 정렬 완료 신호를 기다린다. 관제 화면 위쪽에 **[정렬 완료 → 물따르기 시작]** 버튼이 뜬다 |
| 컵 파지 | 물따르기 정책 실행(`/run/pour`). 컵·물통 파지, 붓기, 물통 반환, 상판 적재까지 정책 한 번 |
| 물통 파지 ~ 상판 적재 | 위 결과를 그대로 반영(팔은 다시 움직이지 않음) |
| 테이블 이동 | (주행 미연동) 즉시 통과 |
| **테이블 정렬** | 정렬 완료 신호를 기다린다. **[정렬 완료 → 컵 배치 시작]** 버튼 |
| 컵 재파지 | 컵배치 정책 실행(`/run/place`) |
| 테이블 배치 | 위 결과를 그대로 반영 |

- **같은 정책은 한 주문에서 한 번만 돈다.** 주문 서버가 단계를 재시도해도 저장된 결과를 돌려주고 팔을 다시 움직이지 않는다.
- **실패 코드** (주문의 실패 원인 칸에 표시)
  - `POUR_END_NOT_DETECTED`: 작업 끝을 감지하지 못하고 최대 시간 도달. 주문 서버를 `--accept-duration`으로 켜면 성공으로 센다.
  - `POUR_STOPPED`
  - `POUR_START_POSE_FAILED`
  - `POUR_HOOK_FAULT`
  - `ROLLOUT_SERVICE_UNREACHABLE`
  - 컵배치는 `PLACE_…`로 같은 형식이다.
- **중단:** 관제 화면 [현재 주문 중단]을 누른다.
  - 정렬 대기 중이면 대기를 풀고 주문을 끝낸다.
  - 정책 실행 중이면 실행기에 `/stop`을 보낸다. 팔은 그 자리에서 유지한다.
- **정렬 신호 API:** `POST /api/align/confirm {"station": "kitchen"|"table"}`
  - 주행 연동 뒤에는 주행 쪽이 정차·정렬을 마쳤을 때 이 API를 부르면 된다. 버튼과 같은 동작이다.
  - 신호 없이 바로 진행하려면 주문 서버를 `--no-align-confirm`으로 켠다. 테이블 위 시험용이며, 실차에서는 쓰지 않는다.

### 검증 (2026-10-26, 하드웨어 없이)
가짜 조작 실행기를 HTTP로 띄워 확인했다(`tests/mission/test_rollout_service_backend.py` 7개 통과).
- 정책별 1회 실행, 재시도 시 재실행 없음
- 실패 코드 변환과 `--accept-duration`
- 정렬 대기·불일치 거부·대기 중 취소
- 준비 중(409 loading) 대기
- 연결 불가
- 주문 1건을 정렬 버튼 2번으로 끝까지 진행

관제 화면에서 정렬 버튼이 뜨고, 누르면 물따르기 → 테이블 정렬 대기로 넘어가는 것을 화면으로 확인했다. 실기체 연결은 아직이다.
