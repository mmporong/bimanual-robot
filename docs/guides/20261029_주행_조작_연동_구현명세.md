## 3. 주행 코드에서 확인한 사실 (PR #86 기준)

약어는 다음과 같다.
- DEP = `src/navigation/scripts/map_20260930_manual/jdamr_depart.py` (PC). `tools/jdamr/jdamr_depart.py`가 이것을 불러 쓴다.
- BOX = `src/navigation/jdamr_cube_navigation/jdamr_cube_navigation/box_service.py` (Pi 실행기)
- RS = `src/navigation/jdamr_cube_navigation/jdamr_cube_navigation/restaurant_service.py`
- CR = `src/navigation/jdamr_cube_navigation/jdamr_cube_navigation/corridor_route.py`

### 3-1. PC → Pi 요청 경로
- 모든 Pi 작업은 `pi()`(DEP L343)로 실행한다: `ssh -o BatchMode=yes -o ConnectTimeout=8 lim@192.168.0.159 <명령>`
- Pi에는 상주 실행기가 있다: `systemd-run --unit=jdamr-box-executor ... box_service --serve /home/lim/jdamr_data/box_executor_spool`
  - 시작은 `start_executor()` DEP L705, 이 함수를 `session-start` L675가 부른다.
- `go`의 처리 순서는 다음과 같다.
  1. `cmd_go` L1413이 `--dwell-s` 범위 [0, 120]을 확인한다(L1419).
  2. `go_one` L1470을 부른다.
  3. `run_cycle` L1132가 요청 인자를 만든다(L1169~1207, `--dwell-s`는 L1191).
  4. spool에 `{run}.part`를 쓰고 `flock {run}.lock` 아래에서 `.request`로 바꾼다(L1215~1233). `.cancelled`가 있으면 제출하지 않는다.
  5. PC는 `ssh cat …/cycle_events.jsonl`로 이벤트를 읽는다(`read_events` L884). 첫 이벤트 전에는 1 s, 이후에는 10 s 간격이다(L1283~1322).
  6. 읽을 때마다 heartbeat 파일 `{SPOOL}/{run}.heartbeat`를 touch하고(`running()` L1235), `{run}.result`가 생기면 끝낸다.
- 실행 상태는 PC의 `<세션>/runtime/state.json`에 저장된다. `last_unit = "executor:<run>"`, `last_run`이다.
- 실행 기록은 Pi `…/runtime/runs/<table>_<run>/cycle_events.jsonl`에 남는다. PC 쪽 같은 상대 경로의 `command.txt`에도 남는다.
- 정지는 `cmd_stop` L1632가 한다.
  - 실행기에 SIGINT를 보낸다. 실행기는 `request_operator_stop`으로 `stop_requested = True`를 세운다(CR L442).
  - `{run}.cancelled`를 touch한다.
  - `estop`은 `/emergency_stop`을 발행한다(L1695).

### 3-2. Pi 실행기의 한 사이클 (`BOX.run_attempt` L3482)
1. 급수대 정차: `visit_observed_box(via_route, …)`(L3564~3575)가 도크 이탈 → 이동 → 관측 → 최종 접근을 한다.
   - 주차가 확인되면 `box_approach_finished` 이벤트가 나간다(BOX L2168~2205). 확인되지 않으면 `box_gap_not_confirmed`다.
2. `dwell_and_leave(dwell_s)`(L3304)
   - 대기 후 직선 후진 이탈 `box_escape_finished`, 이어서 `via_stop_finished`가 나간다.
   - 대기가 실패하면 `failed phase=via_dwell`이다.
3. 배터리 부족(`battery_return_due`)이면 테이블을 건너뛰고 도크로 간다.
4. 테이블 정차: `visit_observed_box(approach_route, …, table_id)`(L3581~3594)
5. `dwell_and_return_home(dwell_s, timeout)`(L3314)
   - 대기 후 카메라를 끄고 `go_home`으로 후면 도킹한다.
   - 대기가 실패하면 `failed phase=table_dwell`이고, 그 자리에서 멈춘다.

### 3-3. 대기(dwell) 구현: **두 정차가 같은 함수를 지난다**
- `BOX._wait_optional_box_dwell(dwell_s)` L3286
  - `dwell_s > 0`이면 `RS.wait_parked(dwell_s)` L3169를 부른다.
    - `parked_dwell_started` → 5 s 정지 확인(`PARKED_CONFIRM_MAX_S` RS L185) → `_hold_still(dwell_s − 5)` → `parked_dwell_complete` 또는 `parked_dwell_failed` 순서다.
  - `dwell_s == 0`(기본)이면 직전 주차 확인 결과를 재사용한다. 바로 `parked_dwell_complete reused_final_stop=True`를 내고, 확인할 수 없으면 `parked_handoff_unavailable`이다.
- `RS._hold_still(seconds)` L3187: 대기 중 안전 감시
  - `stop_requested`면 즉시 실패한다.
  - odom을 `observation_timeout_s`보다 오래 못 읽으면 `parked_hold_unobserved`로 실패한다.
  - **2 cm 넘게 이동하거나 2° 넘게 회전하면 `parked_hold_moved`로 실패한다**(RS L186~187).
- 120 s 상한은 두 곳에서 검사한다: DEP L1419, BOX `parse_args` L3428.
- 운영자 링크: heartbeat 파일이 30 s(`OPERATOR_LINK_TIMEOUT_S` RS L96)보다 오래되면, 다음 이동(이탈)이 `departure_blocked reason=operator_link_lost`로 막힌다(RS L1693).
- `run_deadline_s`(작업 시간 상한)는 주차가 확인되면 풀리고 다음 방문을 시작할 때 다시 걸린다(BOX L2198, L1837). 그래서 **긴 대기가 다음 구간 시간을 잡아먹지 않는다.**

### 3-4. 외부에서 멈춤·재개하는 수단
- **없다.** pause·release 같은 ROS topic·service·파일 플래그·HTTP가 없다.
  - 있는 것은 정지(SIGINT, `.cancelled`)와 비상정지(`/emergency_stop`)뿐이다.
- `--resume-parked-log`(DEP L1817)은 이전 실행 기록을 읽어, 첫 정차에 이미 서 있는 상태에서 대기 → 이탈 → 다음 구간을 이어 간다.
  - 사람이 `stop` 뒤에 다시 이어 가는 용도라서 자동 연동에는 맞지 않는다.

## 4. 조작 쪽 인터페이스 (구현 완료, 주문 서버 = IL 노트북 :8765)

### 4-1. 정렬(정차) 완료 알림
```
POST http://<IL노트북IP>:8765/api/align/confirm
Content-Type: application/json
{"station": "kitchen"}      # 급수대 정차 완료 → 물따르기 시작
{"station": "table"}        # 테이블 정차 완료 → 컵배치 시작
```
- 성공하면 `{"confirmed": true, "station": "kitchen"}`를 돌려준다.
- 대기 중이 아니면 `{"confirmed": false, "reason": "not_waiting"}`, 지점이 다르면 `"station_mismatch"`다.
- 대기를 지원하지 않는 backend면 HTTP 409다.
- **주행의 지점 이름과 대응:** `water_station` ↔ `kitchen`, `table_01` ↔ `table`. 주문은 테이블 1(`table_1`)로 받는다.

### 4-2. 상태 조회
```
GET http://<IL노트북IP>:8765/api/state
```
필요한 필드는 다음과 같다(`execution_backend` 아래, 실제 값 예시).
```json
{
  "phase": "ALIGN_KITCHEN",
  "orders": [{"order_id": "...", "state": "RUNNING", "table_id": "table_1", "failure": null}],
  "execution_backend": {
    "waiting_alignment": {"station": "kitchen", "phase": "ALIGN_KITCHEN", "order_id": "..."},
    "running_policy": null,
    "arms": "stowed",
    "drive": {"next": "kitchen", "arms_ready": true},
    "manipulation_service_state": "ready"
  }
}
```
| 필드 | 뜻 |
|---|---|
| `waiting_alignment.station` | **지금 이 지점으로 가서 정차하라는 확정 신호다.** 이 값이 보일 때는 팔이 이미 이동 자세이고 정지해 있다 |
| `running_policy` | `pour`, `place`, `stow`이면 팔이 움직이는 중이다. **절대 출발하지 않는다** |
| `arms` | `stowed`, `carrying_cup`이면 출발할 수 있다. `busy`, `hold`, `unknown`이면 출발하지 않는다 |
| `drive.next` / `drive.arms_ready` | 다음 목적지와 출발 가능 여부 요약 |
| `orders[].state` | `SUCCEEDED` 또는 `FAILED`. 실패 원인은 `failure`(예: `GRASP_CUP:POUR_END_NOT_DETECTED`) |

### 4-3. 출발 판정 규칙 (브리지가 그대로 구현)
| 지금 위치 | 출발해도 되는 조건 | 다음 목적지 |
|---|---|---|
| 도크(주문 대기) | 진행 중 주문이 있고 `waiting_alignment.station == "kitchen"` | 급수대 |
| 급수대(물따르기 후) | `waiting_alignment.station == "table"` | 테이블1 |
| 테이블(컵배치 후) | 해당 주문 `state == "SUCCEEDED"`, `running_policy == null`, `arms == "stowed"` | 도크 |
| 어디서든 | 주문 `state == "FAILED"` | **출발하지 않는다.** 그 자리에서 정지하고 사람을 부른다 |

### 4-4. 조작 소요 시간 (정차 대기 설계용)
| 구간 | 시간 |
|---|---|
| 주문 → 양팔 접기(`stow`, 도크) | 약 5 s. 이미 접혀 있으면 0 s |
| 급수대 정렬 신호 → 물따르기 끝 + 오른팔 접기 | 시작 자세 이동 약 5 s + 정책 66~71 s(실측) + 오른팔 접기 약 5 s ≈ **80 s.** 상한은 정책 100 s 기준 약 110 s |
| 테이블 정렬 신호 → 컵배치 끝(`place_end`) | 정책 31~34 s(실측) + 끝 자세 이동 약 5 s ≈ **40 s.** 상한은 정책 50 s 기준 약 60 s |

**인자** (`BOX.parse_args` L3400 부근, 검사는 L3428 부근)

### 5-3. PC 브리지 `tools/jdamr/service_bridge.py` (신규)
주행 PC에서 돌며 주문 서버와 주행을 잇는다. 표준 라이브러리만 쓴다(`urllib`, `subprocess`, `json`).

**인자**
- `--order-url http://<IL노트북IP>:8765`
- `--table table_01`
- `--release-timeout-s 300`
- `--poll-s 1.0`
- `--dry-run`: 주행 명령을 실제로 실행하지 않고 출력만 한다.

**상태 기계**
```
IDLE_AT_DOCK
  └ 주문 서버 /api/state: 진행 중 주문 있음 + waiting_alignment.station == "kitchen"
    → subprocess: jdamr_depart.py go table_01 --hold-until-release --release-timeout-s 300
       (표준 출력은 로그 파일로 남기고, 이 프로세스가 끝날 때까지 아래를 병행한다)
DRIVING_TO_KITCHEN
  └ Pi 이벤트 parked_awaiting_release (station=water_station)
    → POST /api/align/confirm {"station":"kitchen"}   (confirmed=false면 1 s 간격 재시도, 30 s 넘으면 사람 호출)
POURING
  └ /api/state: waiting_alignment.station == "table"   (= 물따르기 끝, 오른팔 접힘)
    → jdamr_depart.py release water_station
  └ 주문 FAILED → 해제하지 않음. 로그·알림만 남긴다(Pi 상한 시간이 지나면 그 자리에서 실패·정지)
DRIVING_TO_TABLE
  └ Pi 이벤트 parked_awaiting_release (station=table_01)
    → POST /api/align/confirm {"station":"table"}
PLACING
  └ 주문 SUCCEEDED and running_policy == null and arms == "stowed"
    → jdamr_depart.py release table_01   (Pi가 도크로 복귀)
  └ 주문 FAILED → 해제하지 않음
RETURNING
  └ go 프로세스 종료 코드 0 (home_arrived 확인) → IDLE_AT_DOCK
  └ 0이 아니면 → ERROR (사람 확인, 자동 재시도 없음)
```
**Pi 이벤트 읽는 방법**
- (권장) `go`의 표준 출력을 읽는다. `show_event`(DEP L1109)가 `{"event": …}` 줄을 찍는다. 단, `table_id`가 출력되지 않으니 `show_event`의 keep 목록에 `table_id`를 더한다.
- 또는 `state.json`의 `last_run`으로 Pi 기록 경로를 계산해 `ssh cat`으로 직접 읽는다.

**지켜야 할 것**
- 브리지는 **팔을 직접 부르지 않는다.** 주문 서버 API만 쓴다.
- 해제는 4-3절 조건이 **모두** 참일 때만 한다.
- 브리지가 죽거나 끊기면 해제가 오지 않는다. Pi는 상한 시간 뒤 그 자리에서 실패·정지한다. 이것이 안전 쪽 기본값이다.
- 주문 서버가 응답하지 않으면 해제하지 않는다. 같은 이유다.
- `stop`이나 `estop`을 사람이 누르면 브리지는 ERROR로 들어가고 새 `go`를 시작하지 않는다.
- 한 번에 한 주문만 처리한다. 다음 주문은 도크 복귀 뒤에 받는다.

**테스트**
- 가짜 주문 서버를 쓴다(`tests/mission/test_rollout_service_backend.py`의 `FakeRolloutService` + `ServiceApplication`).
- 가짜 `jdamr_depart` 실행 파일은 이벤트 줄을 순서대로 찍고 `release` 호출을 기록하게 만든다.
- 확인할 것:
  - 정상 흐름: confirm 2회, release 2회
  - 주문 실패 시 release 0회
  - 주문 서버가 응답하지 않을 때 release 0회

### 5-4. (선택) Pi를 고치기 전 임시안
Pi 코드를 바꾸기 전에 오늘 바로 쓸 수 있는 방식이다. **덜 안전하므로 시연 전에는 5-1~5-3으로 바꾼다.**

  - 정책이 늦어지면 `stop`에 의존해야 한다.

   - 6절 4단계에서 실제 흔들림을 재고, 필요하면 해제 대기 중에만 임계값을 조정할지 정한다. 조정은 주행 담당 판단이다.
2. **정차 정확도와 팔 성공률**
   - 팔 데이터는 같은 위치에서 모았다(위치 일반화 미수집).
   - 정밀주차 오차가 크면 팔이 실패한다. 평가 기록에도 "차량 약간 오른쪽으로"에서 병을 툭 친 사례가 있다.
   - 주차 반복 오차를 재고, 팔이 버티는 범위와 맞춰 봐야 한다([모델 평가 계획](../20261028_IL_모델평가계획과_일반화_발표전략.md) 3절).
3. **Pi 발열**
   - 급수대 대기 중에도 카메라가 켜져 있다. DEP L310 주석에 80 °C 기록이 있다.
   - 해제 대기가 길어지면(상한 300 s) 발열을 확인한다.
4. **배터리**
   - `battery_return_due`는 급수대 뒤에만 검사한다. 배터리가 부족하면 테이블을 건너뛰고 도크로 가는데, 이때 브리지는 주문을 실패로 처리해야 한다. 컵은 왼손에 들려 있다.
5. **실패 시 컵·병**
   - 실패 시 자동 복구는 없다. 사람이 회수하고, 다음 주문 전에 `rollout_service.py stow`(차 정지 상태)로 팔을 접는다.
6. **테이블 번호**
   - 주행은 `table_01`만 등록돼 있다. 주문을 테이블 1로만 받게 할지, 관제에서 다른 테이블을 막을지 정한다.
7. **heartbeat**
   - 브리지 대신 `go`가 heartbeat를 touch한다. `go` 프로세스가 끝나거나 끊기면 30 s 뒤 이탈이 막힌다. 안전 쪽 동작이다.
8. **조작 실행기 실물 미검증**
   - 6절 4단계가 상주형 실행기의 첫 실물 실행이다.
   - 단건 실행과 동작이 같은지 확인한다: 시작 자세, 끝 감지, 오른팔 접기.
