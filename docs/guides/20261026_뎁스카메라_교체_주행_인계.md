# 뎁스 카메라 교체 상황과 주행 쪽 설정 인계

최초 작성 2026-10-26 · 조작(IL) 담당자 작성 · 받는 사람: 주행(이동·연결) 담당

## 0. 요약

- **지금 차체 상판 뒤쪽 카메라 자리에는 Orbbec Astra(USB ID `2bc5:0401`)가 달려 있다.**
  - 조작 노트북에 연결돼 있다.
  - 조작 정책의 top 카메라로 쓰인다.
- **주행 설정은 전부 Astra S(`2bc5:0402`, 시리얼 17120813010) 기준이다.**
  - USB 복구 서비스, VSLAM 설정, 카메라 장착값(높이·각도·초점거리)이 모두 Astra S 기준이다.
- **카메라 한 대를 파이(주행)와 노트북(조작)이 동시에 쓸 수 없다.**
- **권장안은 카메라 2대 구성이다.** Astra(0401)는 조작용으로 노트북에, Astra S(0402)는 주행용으로 파이에 둔다(2절).

## 1. 바뀐 경위 (2026-10-23)

1. 양팔을 차체에 결합했다. 차체에 달려 있던 Astra S(0402)를 노트북에 꽂아 조작 정책의 top 카메라로 쓰려 했다.
2. Astra S 컬러 영상에 천장 조명(60Hz) 때문에 가로 줄무늬가 흘렀다.
   - 줄무늬 세기는 23~24였다(학습 데이터를 찍은 카메라는 1.2~2.3).
   - 원인: 자동 노출이 2.5 ms로 잡혀, 조명 깜빡임 주기 8.3 ms보다 짧았다.
   - 노출을 8.3 ms로 고정하면 줄무늬는 사라지지만 화면의 55%가 하얗게 날아갔다.
3. 그래서 조작 학습 데이터를 찍은 기종인 **Astra(0401)로 바꿔 끼웠다.**
   - 조작 화면을 학습 때와 맞추려고 **카메라 각도도 다시 조정했다.**
4. 이 상태로 조작 학습 데이터 160개(물따르기 80, 컵배치 80)를 모으고 정책을 학습했다. 실기체에서 정상 동작하는 것도 확인했다.

상세: [카메라 재구성 기록](../experiments/20261023_차체결합후_카메라_재구성_뎁스플리커_정렬.md)

## 2. 구성 선택지

### 권장: 카메라 2대

| 카메라 | 연결 | 용도 | 스트림 |
|---|---|---|---|
| Astra (0401) | 노트북 | 조작 정책 top 카메라 | 컬러만 (브리지 → 가상 카메라) |
| Astra S (0402) | 파이 | 주행 책상 면 관측·정밀주차 | 깊이만 |

- **Astra(0401)는 지금 위치와 각도를 그대로 유지한다.**
  - 조작 정책이 이 화면으로 학습됐다.
  - 위치나 각도가 바뀌면 정책이 학습 때와 다른 장면을 보게 된다.
- **Astra S(0402)는 주행용 브래킷을 하나 더 달아 파이에 연결한다.**
  - 주행 쪽 USB ID, 거리 설정, 드라이버는 원래대로 쓰면 된다.
  - **새 장착 위치의 높이와 숙임 각만 다시 재서 `camera_mount_current.yaml`에 반영한다.**
  - Astra S의 조명 줄무늬는 컬러 영상 문제다. 깊이만 쓰는 주행에는 영향이 없다.
- 두 카메라가 함께 켜져 있을 때 서로의 적외선 패턴이 간섭하는지는 확인하지 않았다.
  - 조작용 Astra는 컬러만 연다.
  - 첫 시험에서 주행 깊이 영상에 구멍이나 노이즈가 늘어나는지 확인한다.

### 비권장: Astra(0401) 한 대를 파이에 연결해 같이 쓰기

- 조작 정책이 top 화면을 잃는다.
- 조작에 쓰려면 파이에서 노트북으로 컬러 영상을 무선으로 보내야 한다.
  - 원본 640×480, 30fps는 약 220 Mbps라서 압축이 필요하다.
  - 압축 화질과 지연이 학습 때와 달라 정책이 흔들릴 수 있다.
- 이 경우 주행 쪽도 3절의 수정이 모두 필요하다.

## 3. Astra(0401)를 주행에 쓸 경우 고쳐야 할 곳 (main 기준)

권장안(2대 구성)을 따르면 아래 수정 중 **`camera_mount_current.yaml`의 장착값 재측정만** 필요하다.

### 기종 차이

| | Astra (0401) | Astra S (0402) |
|---|---|---|
| 장치 이름 | ORBBEC Depth Sensor | ORBBEC Close Depth Sensor |
| 깊이 측정 거리 (제조사 사양, 실측 아님) | 약 0.6 ~ 8 m | 약 0.4 ~ 2 m |
| 화각·해상도 | 60°×49.5°, 640×480 | 같음 |
| ROS 드라이버 | `astra_camera` `astra.launch.xml` | 같음 |

**주의: 가까운 거리**
- 카메라 렌즈는 바닥에서 1.26 m 높이에서 약 52.5° 숙여 책상(상판 높이 약 0.78 m)을 본다.
- 책상 앞 가장자리까지의 거리는 대략 0.6 m 안팎이다.
- Astra(0401)는 0.6 m보다 가까운 곳의 깊이를 못 잰다. 그래서 **1 cm 접근 마지막 구간에서 면이 Astra S보다 일찍 안 보일 수 있다.**
- "근접해서 가려진 뒤에는 마지막 승인 면과 odom으로 이어가는" 기존 동작이 이를 메울 수 있는지는 실차로 확인해야 한다.

### 수정 목록

| 파일 | 지금 값 | 할 일 |
|---|---|---|
| `src/navigation/jdamr_cube_bringup/scripts/jdamr-astra-usb-recover` | `usb_id` 기본값 `2bc5:0402` | `2bc5:0401` |
| `src/navigation/jdamr_cube_bringup/systemd/jdamr-astra-usb-recover.service` | `ASTRA_USB_ID=2bc5:0402` | `2bc5:0401` |
| `src/navigation/deployment/systemd/jdamr-astra-usb-recover.service.in` | 같음 | 같음 |
| `src/navigation/jdamr_cube_bringup/test/test_astra_usb_recovery.py` | `idProduct 0402`를 가정 | 위와 맞추기 |
| `src/navigation/jdamr_cube_navigation/config/camera_mount_current.yaml` | z 1.26 m, pitch 0.9172 rad, `table_observation.focal_y_px 285.17`, `base_offset_m 0.37` | **재측정과 재계산.** 10-23에 카메라를 바꿔 끼우고 각도를 조정했다. |
| `src/navigation/jdamr_cube_navigation/config/depth_obstacles.yaml` | `min_depth_m: 0.4` | Astra 사양에 맞춰 `0.6` 검토 |
| `src/navigation/jdamr_cube_vslam/config/astra_s_rgbd.yaml` | 모델명·USB ID·시리얼이 Astra S | VSLAM을 쓴다면 갱신 |

- 파이에 이미 설치된 서비스는 `sudo systemctl edit jdamr-astra-usb-recover`로 `Environment=ASTRA_USB_ID=2bc5:0401`을 덮어써도 된다.

**바꾸지 않아도 되는 것**
- `jdamr-box-rgbd` 서비스의 드라이버 실행 줄. 기종과 무관하다.
  - `astra.launch.xml enable_color:=false enable_depth:=true ... depth_width:=320 depth_height:=240 depth_fps:=30`
- 카메라 내부값(초점거리 등). `box_service`가 `/camera/depth/camera_info`에서 매번 읽는다.

## 4. 파이 연결 후 확인 절차

```
lsusb | grep 2bc5                                   # 연결한 기종의 ID가 보여야 함 (0402 또는 0401)
ros2 topic hz /camera/depth/image_raw              # 30Hz 근처
ros2 topic echo --once /camera/depth/camera_info   # 초점거리 확인 → camera_mount 값 재계산에 사용
```

1. 장착 높이(렌즈 중심, 바닥 기준)와 숙임 각을 줄자로 재서 `camera_mount_current.yaml`에 반영한다.
2. `table_observation`의 `focal_y_px`, `base_offset_m`을 다시 계산한다.
3. 정지 상태에서 책상 면 관측을 확인한다. 이어서 1 cm 접근을 같은 조건에서 3회, 다른 위치에서 3회 시험한다.

## 5. 조작 쪽 (노트북) 현재 세팅

조작 실행에 필요한 것이고, 주행 쪽에서 바꿀 필요는 없다.

- **장치:** 노트북 USB에 양팔(COM15 왼팔, COM16 오른팔), 손목캠 2대, Astra(0401)가 연결돼 있다.
- **Astra 브리지:** `python tools/camera/astra_rgb_virtualcam_bridge.py`
  - 컬러 영상을 OBS 가상 카메라로 보낸다.
  - **옵션 없이** 켠다. `--exposure`는 Astra S 줄무늬 대응용이다.
  - **OBS 앱은 꺼 둔다.** 가상 카메라는 한 프로그램만 잡을 수 있다.
  - **컵과 병을 올려 둔 상태에서** 켠다. 켤 때 보이는 장면으로 노출이 고정된다.
- **카메라 번호:** 롤아웃 명령에서 `{left}` `{right}` `{depth}`가 USB 경로로 자동으로 채워진다(`tools/camera/resolve_camera_indices.py`).
- **추론:** `tools/rollout/rollout_handoff.py`
  - 물따르기는 `--start.pose=pour`로 시작 자세를 맞추고, 컵배치는 `--end.pose=place_end`로 끝 자세를 맞춘다.
  - 상세: [롤아웃 자세 가이드](20261026_롤아웃_시작끝_자세_저장_가이드.md)
- **모델:** SmolVLA 차체 결합 80개 모델(물따르기 step 16000, 컵배치 step 7000)
  - 상세: [학습 기록](../experiments/20261025_차체결합_SmolVLA_60vs80_학습결과.md)

## 6. 주행과 조작 연동 (제안 순서)

1. **목적지에서 조작만 시험:** 급수대와 서빙 테이블 앞에 로봇을 손으로 세워 두고 롤아웃을 돌린다.
   - 학습 데이터를 찍은 테이블과 높이·배치가 다른지 여기서 확인한다.
2. **팔을 단 채 주행만 시험:** 노트북을 싣고, 팔은 운반 자세로 둔 채 주행한다.
   - 무게중심, 케이블 당김, 1 cm 주차 정밀도를 확인한다.
   - 라이다 자기 차체 필터(`scan_self_filter_config`)가 양팔 기둥을 거르는지도 확인한다.
3. **반자동 통합:** `jdamr_depart.py go`에 `--dwell-s`로 정차 대기 시간을 넉넉히 준다.
   - 물따르기는 최대 100초, 컵배치는 최대 50초다.
   - 로봇이 정차해 대기하는 동안 노트북에서 롤아웃을 실행한다. 코드 수정이 필요 없다.
4. **자동 연결:** 주차 완료 → 롤아웃 실행 → 종료 신호 → 다음 이동을 잇는 스크립트를 만든다.

**안전 규칙**
- 팔이 움직일 때 바퀴는 정지해 있어야 한다.
- 주행 중 팔은 운반 자세로 토크를 유지한다.
- 팔을 움직이는 모든 동작은 사람이 확인한 뒤 실행한다.

## 7. 확인되지 않은 것
- Astra(0401)의 실제 최소 측정 거리(사양만 확인함)와, 이 거리가 1 cm 접근에 주는 영향
- 카메라 2대를 동시에 켰을 때의 적외선 간섭
- 10-23 각도 조정 뒤 카메라의 실제 숙임 각 (현재 yaml 값은 10-16 기준)
- 급수대·서빙 테이블과 조작 학습 데이터 테이블의 높이·배치 일치 여부
