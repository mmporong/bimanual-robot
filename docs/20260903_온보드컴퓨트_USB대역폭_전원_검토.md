# 온보드 컴퓨트·USB 대역폭·전원 검토

> 목적: 무선 주행과 양팔 조작을 한 대의 온보드 SBC와 한 대의 노트북으로 성립시키기 위한 컴퓨트·인터페이스 배분을 확정한다
> 기준일: 2026-09-03
> 상태: **계산과 문헌값 기반 설계안. 실측 전이다.** 6절 확인 항목을 통과하기 전에는 하드웨어 발주 근거로 쓰지 않는다
> 선행 문서: [기구설계 제작명세 v0.2](20260901_기구설계_제작명세_v0.2.md) · [250mm 차체 계산검증 v0.2](20260901_250mm_차체_계산검증_v0.2.md)

## 1. 결론

| 항목 | 결정 | 근거 |
|---|---|---|
| 온보드 SBC | **Raspberry Pi 4B 4GB 유지** | Pi 5는 USB 포트가 4개로 동일하고 CUDA도 없어 해결하는 문제가 없다 |
| 자율주행 | **Pi 단독** | Nav2와 2D LiDAR SLAM은 CPU 작업이다. 노트북이 꺼져 있어도 주행한다 |
| 정책 추론 | **노트북 GPU, WiFi 경유** | ACT/SmolVLA는 액션 청크를 반환해 왕복 주기가 0.5 s 이상이다 |
| 학습 | **오프보드** | 8 GB VRAM으로 ACT는 가능, SmolVLA는 VLM 동결 조건 |
| Jetson 전환 | **보류** | "노트북 없이 로봇 단독 자율"이 요구사항으로 확정될 때만 |

## 2. SBC 선정

### Pi 5를 채택하지 않는 이유

| 항목 | Pi 4B | Pi 5 |
|---|---|---|
| USB 포트 수 | 4 | **4 (동일)** |
| USB 대역폭 | VL805, PCIe Gen2 x1을 4포트가 공유 | RP1, PCIe Gen2 x4 |
| 버스 분리 | 불가 (컨트롤러 1개) | PCIe HAT 추가 시 가능 |
| CUDA | 없음 | **없음** |

포트 부족이 이 프로젝트의 실제 제약인데 Pi 5는 포트를 늘리지 않는다. 온보드 추론에 필요한 CUDA도 없다. 버스 분리를 위해 PCIe USB HAT을 추가하는 구성은, 그 구성으로도 정책 추론이 불가능하므로 목적을 달성하지 못한다.

### Jetson Orin Nano 8GB로 전환하는 조건

다음 중 하나가 요구사항으로 확정될 때 재검토한다.

- 노트북 없이 로봇 단독으로 자율 조작까지 수행
- 온보드 데이터셋 기록에 M.2 NVMe가 필요할 만큼 카메라 수·해상도 증가
- USB 컨트롤러 물리 분리가 필수로 판정

전환 시 확인 항목: `electronics` 예산 350 g 대비 실측 질량, 중판↔상판 43 mm 높이 수납, 15 W 모드 기준 운용시간 재계산, 조달기간.

## 3. 무선 구성

명세의 `base_motion_during_manipulation: prohibited` 규약에 따라 주행과 조작은 겹치지 않는다. 이 시분할이 컴퓨트 배분의 근거다.

```
① Pi 단독 자율주행        → 노트북 무관
② 정지
③ Pi ─이미지→ 노트북(추론) ─액션 청크→ Pi   → 노트북 필요
④ 정지 해제, 다시 Pi 단독 주행
```

### 지연 예산

| 항목 | 값 |
|---|---:|
| 청크 재계획 주기 (`--replan 15`, 30 Hz) | 500 ms |
| 노트북 추론 (RTX 5050, bf16) | ~20 ms |
| WiFi 왕복 | 10~30 ms |
| **여유** | **예산의 약 90%** |

### 통신 규약

- 정책 채널은 **ROS 2 DDS를 쓰지 않는다.** 전용 TCP 또는 WebSocket 한 경로로 분리한다. 공유 LAN에서 DDS 디스커버리가 오염된 사례가 있다
- 로봇 내부 ROS는 `ROS_LOCALHOST_ONLY=1`로 묶는다
- **워치독 필수.** 마지막 청크 수신 후 타임아웃이 지나면 팔을 정지한다. 없으면 통신 두절 시 낡은 액션을 계속 재생한다

## 4. USB 포트 배분

온보드 장치는 7개, Pi 4B의 USB 포트는 4개다. 세 개를 USB 밖으로 내린다.

| 장치 | 경로 | 비고 |
|---|---|---|
| LDS-03 | **GPIO UART** | USB2LDS는 UART-USB 브리지다. 직결하면 포트를 쓰지 않는다 |
| 주행 C018 | **GPIO UART** | MCU 경유. JD-AMR에서 검증된 경로 |
| 좌팔 + 우팔 | USB ×1 | 12서보를 ID로 한 버스에 합친다 |
| Astra S | USB ×1 | |
| 손목캠 ×2 | USB ×2 | |

합계 USB 4개로 정확히 소진된다. 여유는 없다.

### 팔 버스 합침의 대가

1 Mbps에서 12서보 sync read는 약 3 ms로 30 Hz 예산 33 ms 안에 들어간다. 다만 좌우 팔이 **실패 도메인을 공유**하므로 한쪽 서보 이상이 양팔을 동시에 멈춘다. `sync_write`는 응답 없는 브로드캐스트라 관절별 검증이 별도로 필요하다.

## 5. USB 2.0 대역폭

### 전제

Pi 4B의 VL805는 내부에 USB 2.0 허브를 하나 갖고, 4개 포트의 USB2 경로가 전부 여기 물린다. **모든 USB 2.0 카메라가 480 Mbps 하나를 공유한다.** 포트를 나눠 꽂아도 달라지지 않는다.

| 기준 | 값 |
|---|---:|
| 이론 최대 | 480 Mbps = 60 MB/s |
| 스펙상 아이소크로너스 상한 (80%) | 384 Mbps = 48 MB/s |
| 실무 관측 한계 | **35~40 MB/s** |

### 스트림별 무압축 대역폭

```
640×480 = 307,200 px × 2 B = 614,400 B/frame × 30 fps = 18.43 MB/s = 147.5 Mbps
320×240 =  76,800 px × 2 B = 153,600 B/frame × 30 fps =  4.61 MB/s =  36.9 Mbps
```

YUYV와 16비트 뎁스는 픽셀당 2바이트로 같다. 손목캠은 YUYV 고정이라 해상도가 유일한 레버다.

| 스트림 | 해상도 | MB/s |
|---|---|---:|
| Astra 뎁스 (16bit) | 640×480@30 | 18.43 |
| Astra 뎁스 (16bit) | 320×240@30 | 4.61 |
| Astra RGB | MJPEG 640×480@30 | ~3 |
| 손목캠 (YUYV) | 640×480@30 | 18.43 |
| 손목캠 (YUYV) | 320×240@30 | 4.61 |

### 조합 판정 (40 MB/s 기준)

| # | 구성 | 합계 | 점유율 | 판정 |
|---|---|---:|---:|---|
| A | 뎁스 640 + RGB + 손목캠 2×320 | 30.6 | 77% | 위험 |
| B | 뎁스 640 + 손목캠 2×320 | 27.6 | 69% | 경계 |
| **C** | **뎁스 320 + 손목캠 2×320** | **13.8** | **35%** | **채택** |
| D | 뎁스 640 + 손목캠 2×640 | 55.2 | 138% | 불가 |

**C를 기본값으로 한다.** 붓기 태스크의 병과 컵은 얇은 물체가 아니므로 320×240 뎁스로 파지점 추정에 충분하다. 정책 입력은 어차피 224 근방으로 리사이즈된다.

### 스트림 개폐 정책

**세션 중 카메라를 껐다 켜지 않는다.** 구성 C는 상시 스트림으로 예산 안에 들어오므로 전환 로직이 필요 없다. 안 쓰는 구간에서는 프레임을 읽지 않으면 된다.

개폐를 금지하는 이유는 대역폭이 아니라 복구 경로다. UVC 재열기가 실패하면 사실상 재부팅 외에 복구 수단이 없고, 시연 중 재부팅은 곧 실패다. 대역폭이 모자라면 **해상도를 더 내리거나 카메라 수를 줄이는 순서로 대응하고, 개폐는 최후 수단으로 둔다.**

Astra는 **별도 프로세스로 격리**한다. 같은 프로세스에서 UVC와 섞였을 때 동결한 사례가 있고, 프로세스를 분리하면 카메라 계층이 죽어도 팔 제어가 살아 있다.

## 6. 확인 항목

전부 로봇 완성 전에 책상 위에서 확인할 수 있다. 실패 확률이 높은 순이다.

| # | 확인 | 방법 | 실패 시 |
|---|---|---|---|
| U-01 | 손목캠 2 + Astra 동시 스트림에서 프레임 드랍 0 | 구성 C로 수 분간 연속 수신, 드랍 카운트 로깅 | 해상도 추가 인하 → 손목캠 1대 |
| U-02 | Astra의 USB 전송 타입 | `lsusb -v`의 `Transfer Type` 확인 | 벌크면 초과가 조용한 프레임률 저하로 나타나므로 드랍 로깅을 필수화 |
| U-03 | 좌우 팔 12서보 한 버스 30 Hz 유지 | sync read 왕복 시간 측정 | 버스 분리 복귀, 카메라 1대 감축 |
| U-04 | WiFi 청크 왕복 500 ms 이내, 드랍률 | 실제 무선 환경에서 왕복 측정 | 청크 길이 증가 또는 전용 AP |
| U-05 | 주행 C018을 MCU UART로 뺄 수 있는지 | JD-AMR ESP32 펌웨어의 반이중 방향 제어 재사용 가능 여부 | USB 어댑터 사용, 카메라 2대로 감축 |

## 7. 노트북 배분

현재 확인된 사양: AMD Ryzen 7 260 8C/16T, RAM 30 GB, **RTX 5050 Laptop VRAM 8 GB** (Blackwell sm_120), PyTorch 2.11.0+cu130에 sm_120 커널 포함으로 호환 문제 없음.

| 작업 | 판정 |
|---|---|
| IK | 문제 없음. CPU 수치해석 |
| SLAM | 노트북 부담 아님. Pi에서 2D LiDAR + slam_toolbox |
| 정책 추론 | 여유. SmolVLA bf16 약 2 GB |
| ACT 학습 | 가능. 배치 8에 5~6 GB |
| SmolVLA 학습 | VLM 동결 조건부. 전체 파인튜닝은 8 GB로 불가 |
| 학습과 롤아웃 동시 | **불가.** 같은 GPU를 점유한다 |

### 1대 운용 규칙

노트북 1대로 진행하는 동안 지킨다.

- 밤에는 학습만, 낮에는 수집·롤아웃만. 겹치지 않는다
- 학습은 세션에서 분리해 실행하고 메모리 상한을 건다
- 시연 1주 전 체크포인트를 동결하고 이후 롤아웃 반복만 수행한다
- 수집 데이터는 Pi의 SD가 아니라 **WiFi로 노트북에 기록**한다. 단 프레임 드랍을 반드시 로깅한다

### 2대가 필요해지는 조건

학습 1회가 수 시간에서 밤샘이라 1대에서는 수집과 학습이 직렬이 되어 실험 주기가 하루가 된다. 일정이 밀리기 시작하면 동일 사양 1대를 추가해 학습 전담으로 분리한다. 동일 사양이어야 시연 당일 환경 재설정 없이 백업기로 전환된다.

### 디스크

`/home` 여유가 8.9 GB다. 수집 시작 전에 데이터셋 경로를 별도 파티션으로 옮긴다. 학습 중 디스크 소진으로 중단되는 손실이 가장 크다.

## 8. 로컬 LLM 인터페이스 계약

로컬 LLM은 강사 담당이다. 구현과 무관하게 아래 경계를 지킨다.

**정책 입력 문장을 LLM이 직접 생성하지 않는다.** [R26 명령문장 규격](../research/R26_명령문장_규격.md)이 학습 문장을 3종으로 고정했고, 실행 문장이 학습 문장과 어긋나면 학습셋이 갈라진다. LLM은 슬롯만 채우고 문장은 코드가 템플릿으로 조립한다.

| 항목 | 규격 |
|---|---|
| 입력 | STT가 출력한 한국어 텍스트 |
| 출력 | `{"target": ..., "receptacle": ..., "skill": ..., "confidence": 0.0~1.0}` |
| 어휘 | 대상 `red cup / blue cup / bottle`, 목적지 `left tray / right tray / held cup`, 스킬 `move / handover / pour`. 이 밖의 값 금지 |
| 실행 위치 | 정책 GPU와 분리된 별도 머신 |
| 연결 | HTTP `POST /parse` 단일 엔드포인트. ROS 2 DDS 사용 금지 |
| 지연 예산 | 500 ms~2 s. 조작 시작 전 1회 호출이며 제어 루프 밖이다 |
| 실패 규약 | 어휘 밖이거나 confidence 미달이면 `null`을 반환한다. 로봇은 동작하지 않고 재발화를 요청한다 |

범위가 3문장 매핑이 아니라 에이전틱 태스크 분해라면 출력이 스킬 시퀀스가 되고, 스킬 큐를 순서대로 실행하며 실패 시 정지하는 실행기가 우리 쪽에 추가로 필요하다. 어느 쪽인지 먼저 확정한다.
