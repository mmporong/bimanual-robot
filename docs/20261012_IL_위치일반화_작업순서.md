## 0단계 — 반경·jitter 범위 실측

- [ ] 왼팔(컵) 중심점(= 평소 컵을 놓는 자리, 로봇 시작 자세가 아님)을 정하고,
  **전후·좌우·대각선 포함 8~9곳 전부**에서 "쥘 수 있다/빠듯하다/불가능"을 표에 기록한다.
- [ ] 오른팔(물통)도 동일하게 중심점을 정하고 같은 방식으로 기록한다.
- [ ] (정정: "뒤끝"은 로봇 몸체 뒤쪽이 아니라 "중심점보다 조금 덜 앞으로"일 뿐이라 실제로 일어날
  수 있는 위치다. 좌끝/우끝도 배제할 확실한 근거가 없어, 축소하지 않고 전부 측정한다.)
- [ ] 각 중심점의 **절대 위치**를, 로봇암이 아니라 **책상 위 고정 기준(모서리·테이프 표시 등
  팔과 무관한 지점)**으로부터 거리로 한 줄 적어둔다 — 팔이 나중에 다시 조립돼도 중심점을
  되찾을 수 있게 하기 위함이다. (예: "책상 좌측 모서리에서 전후 OOmm, 좌우 OOmm")

- [ ] 각 팔의 "안전하게 쥘 수 있는 최대 반경"보다 한 단계 안쪽을 **가제(임시) jitter 상한**으로
  정한다 (예: 안전 최대 전후 ±6cm → 가제 상한 전후 ±4cm). 왼팔·오른팔 각각 숫자로 확정한다.

- [ ] **(2026-10-12 추가) 동시 안쪽 충돌 확인**: 컵(왼팔)의 "안쪽" 방향(우끝·앞-우·뒤-우,
  즉 병 쪽으로 가까워지는 방향)과 병(오른팔)의 "안쪽" 방향(좌끝·앞-좌·뒤-좌, 즉 컵 쪽으로
  가까워지는 방향)은 **한쪽 팔만 테스트해서는 안전을 보장할 수 없다** — 두 팔이 동시에
  집기를 시작하는 순간에만 드러나는 충돌 위험이 있기 때문이다.
  - 참고용 출발값: 두 팔 중심 사이 거리의 절반(중간 지점까지의 거리)을 안쪽 jitter 상한의
    1차 후보로 쓴다 — 매번 감으로 찾는 것보다 빠르다. (단, 이건 "집기 시작 순간"에만
    적용되는 참고값이고, 에피소드 전체를 이 선 안에 가두는 규칙은 아니다 — 붓기 이후
    적재 단계에서는 왼팔이 중간선을 넘어가는 게 정상 동작이다.)
  - **컵·병을 안쪽 jitter 후보 지점에 놓고, 집기부터 붓기·반환·적재까지 에피소드 전체를
    실제로 텔레옵으로 한 번 끝까지 해본다** — 집기 시작 순간만 보지 말고, 전체 구간
    중 어디서든 두 팔이 부딪히거나 위험하게 가까워지는지 확인한다(천천히, 바로 멈출 수
    있는 속도로).
  - 부딪히거나 너무 가까우면, 안쪽 jitter 상한을 **더 덜 안쪽인 지점**으로 당겨서
    다시 확정한다 — **최종 안쪽 jitter 상한 = min(한쪽 팔만 테스트한 경계, 전체
    에피소드 동시 테스트에서 충돌 없던 경계)**.
  - 바깥쪽 방향(앞끝·뒤끝·왼팔의 좌끝·오른팔의 우끝)은 다른 팔이 움직여도 새로운 충돌
    위험이 생기지 않으므로 이 확인이 필요 없다.

**⚠️ 유의할 점**
- 반경은 **줄자로 실물을 재서** 확정한다 — 인코더·자작 프로브 값만 믿지 않는다(프로브가 실물과 다르면 프로브를 의심한다).
- 왼팔·오른팔은 장착 위치·캘리브레이션이 다를 수 있으므로 **대칭이라고 가정하지 않는다** — 각자 따로 잰다.
- "빠듯하다"로 기록한 지점은 경계값이라 애매하다 — 애매하면 "불가능" 쪽으로 보수적으로 처리한다.
- jitter 상한을 안전 최대 반경과 **똑같게** 잡지 않는다 — 여유를 둬야 반복 수집 중 스톨(정지 상태에서 계속 밀리는 것) 위험이 줄고, 사람이 수동으로는 겨우 쥐는 지점을 정책이 안정적으로 재현하길 기대하기도 어렵다.
- 이 단계는 사람이 직접 텔레옵으로 테스트하는 것이라 토크 ON 자체는 필요하지만, 혹시 스톨(팔이 안 움직이는데 계속 힘이 들어가는 상태)이 느껴지면 **즉시 정지**한다 — 계속 밀면 서보가 탄다.
- 동시 안쪽 충돌 확인은 **처음엔 아주 천천히, 중간에 언제든 멈출 수 있는 속도로** 접근한다 — 두 팔이 가까워지는 상황을 처음 보는 테스트이므로 빠르게 움직이다 부딪히면 그제서야 알게 된다.

## 1단계 — Smoke (10~15 에피소드)

- [ ] 매 에피소드마다 컵·물통을 **둘 다 동시에**, 각자의 jitter 상한 안에서 무작위 위치에 놓고 녹화한다.
- [ ] 그중 1~2개는 컵·물통 모두 중심점(jitter 0)으로 놓고 녹화한다.
- [ ] 각 에피소드의 실제 오프셋(전후/좌우 cm, 컵·물통 각각)을 줄자로 재서 기록한다.
- [ ] 녹화 설정: `--dataset.streaming_encoding=false`로 둔다.
- [ ] 세션 시작 시 `output/capture_indexed.py`로 카메라 인덱스를 재확인한다.
- [ ] **게이트 A**: 중심점(jitter 0) 에피소드에서 기존(60개) 체크포인트로 추론을 돌려본다. 재현 여부와 무관하게 다음 단계로 진행한다.
- [ ] **게이트 B**: 손목·탑뷰 영상을 눌러보고, 위치가 다른 에피소드끼리 접근 경로/정렬이 실제로 다르게 찍혔는지 확인한다. 거의 같으면 시연 방식을 고치고 1단계를 다시 한다.

**⚠️ 유의할 점**
- 컵·물통 위치는 **눈대중이 아니라 줄자로 실제 오프셋을 재서** 놓는다 — 나중에 "jitter가 클 때 실패율이 올라가는지" 분석하려면 숫자 기록이 꼭 필요하다.
- 0단계에서 "동시 안쪽 충돌 확인"으로 안쪽 jitter 상한을 이미 충돌 없는 범위로 조정해뒀어야 한다 — 그래도 실제 수집 중 안쪽 극단 조합(컵이 우끝 쪽+물통이 좌끝 쪽으로 동시에 jitter되는 경우)이 나오면 한 번 더 눈으로 확인한다.
- `--dataset.streaming_encoding=false`를 빠뜨리면 SVT-AV1 인코더 워밍업 때문에 녹화 영상이 **동작 중간부터 시작**된다 — 저장이 느려지는 건 정상이다.
- 손목캠 케이블이 팔 움직임에 당겨지면 **카메라 인덱스가 뒤바뀐다** — 지난 세션의 "확정 매핑"을 그대로 믿지 말고 매번 재확인한다.
- 재녹화 키(`r`)가 오작동하면 좋은 에피소드가 삭제될 수 있다 — `lerobot_record.py`의 lock-in 타이밍 패치가 그대로 있는지 의심되면 먼저 확인한다.
- **게이트 A는 실패가 예상된 결과다**(캘리브레이션이 바뀌어서) — 안 된다고 디버깅에 시간 쓰지 않는다. 혹시 된다면 오히려 다시 확인해볼 일이다.
- **게이트 A 실행 자체가 로봇이 추론만으로 자율 이동하는 것**이다 — 시작 전 사람이 바로 옆에서 지켜보고, 이상 동작 시 즉시 멈출 수 있는 상태로 실행한다.
- 게이트 B에서 "거의 같은 동작"을 대충 눈으로만 훑고 넘기지 않는다 — 여기서 놓치면 2단계에서 수십 개를 더 찍은 뒤에야 전부 다시 찍어야 하는 상황이 된다.

## 2단계 — 본수집 (목표 50~70 에피소드, smoke 포함)

- [ ] 1단계와 같은 방식(컵·물통 동시 무작위 jitter, 오프셋 기록)으로 에피소드를 계속 녹화한다.
- [ ] 전체 수집 중 각 팔의 jitter 범위에서 **중심·양끝 근처·중간**이 각각 최소 몇 번 이상 나오도록 분산시킨다(쏠림 방지, 엄격한 격자는 아님).
- [ ] 목표 수량(50~70개)에 도달하면 수집을 멈춘다.
- [ ] 전체 중 10~15개를 **held-out**으로 지정한다 — 이 에피소드들의 위치 조합은 학습에서 제외하고 4단계 평가에만 쓴다. 지정 후에는 결과를 보기 전까지 건드리지 않는다.
- [ ] (시간이 남으면, 선택) jitter 상한 바로 바깥에 1~2개 "스트레치" 지점을 추가로 찍는다 — 평가에서 "참고용(성공 기대 안 함)"으로 따로 본다.

**⚠️ 유의할 점**
- 수집하다 보면 편한 자세로 자꾸 중심 근처에만 놓게 되기 쉽다 — 중간중간 "최근 10개가 어디에 몰렸는지" 스스로 점검해서 **의식적으로 끝 쪽도 채운다.**
- held-out으로 뺄 10~15개는 **수집 결과(잘 찍혔는지)를 보고 고르지 않는다** — 미리 "이번엔 이 조합을 평가용으로 뺀다"고 정해두고, 나중에 결과가 안 좋아 보여도 다른 걸로 바꾸지 않는다. 결과를 본 뒤 고르면 평가 자체가 왜곡된다.
- 기존 60개(옛 캘리브레이션) 데이터와 이번 데이터를 **절대 같은 학습에 섞지 않는다** — 관절각 기준 자체가 다르다.
- 1단계의 파이프라인 버그 3건(인코딩 설정, 카메라 인덱스, 재녹화 키)은 수집이 길어질수록 다시 발생할 여지가 커진다 — 세션마다, 특히 팔을 많이 움직인 뒤에는 한 번씩 재확인한다.
- 수집 중 스톨(팔이 안 움직이는데 계속 힘이 들어감)이 감지되면 로그만 남기지 말고 **즉시 정지 명령**을 보낸다.
- 에피소드마다 재둔 오프셋(컵·물통 전후/좌우 cm)은 사이드카 메타데이터로 같이 남긴다 — 수집 조건 기록은 이 저장소의 데이터 규칙상 필수다.

## 3단계 — 재학습

- [ ] "ROBOT" 와이파이 연결 확인 (`ping`으로 먼저 테스트).
- [ ] 원격 서버(RTX 4090) 접속, conda env `lerobot_vla` 활성화.
- [ ] 2단계 데이터(held-out 제외)로 SmolVLA 학습 시작, `nohup`/`disown`으로 띄운다.
- [ ] 설정 확인: `EVAL_PATIENCE=3`, `EVAL_MIN_DELTA=1e-4`, `save_freq=eval_steps` (반드시 일치시킨다).
- [ ] 학습 종료 후, "가장 최근"이 아니라 **eval_loss가 가장 낮았던 시점**의 체크포인트를 고른다.
- [ ] HF에 `{모델}_{에피소드수}E_{스텝}S` 이름, `jun-seo` 네임스페이스, **`private=True`**로 업로드한다.
- [ ] 로컬로 체크포인트를 받아올 때 `config.json` 필드 차이로 로드 에러가 나면 필드 차이부터 확인한다.
- [ ] 작업이 끝나면 서버의 `~/.cache/huggingface/token`을 삭제한다.

**⚠️ 유의할 점**
- "ROBOT" 와이파이는 자주 끊긴다 — `ping` 확인 없이 바로 돌리다 중간에 끊기면 학습이 끊긴 채 방치될 수 있다.
- `save_freq`를 `eval_steps`와 다르게 두면 **진짜 최저점 체크포인트가 저장 안 될 수 있다** — ACT-20에서 실제로 겪었던 문제라 다시 반복하지 않는다.
- 체크포인트는 "가장 최근 것"을 습관적으로 고르지 않는다 — eval_loss 곡선을 직접 보고 최저점을 확인한다.
- HF 업로드를 `private=True` 없이 시도하면 자동 승인 정책에 막힌다 — 처음부터 옵션을 넣는다.
- 작업이 끝났는데 토큰 삭제를 잊으면 팀 공유 서버에 개인 자격증명이 남는다 — 학습이 끝난 그 자리에서 바로 지운다(나중으로 미루면 잊기 쉽다).
- 로컬·서버 lerobot 버전이 달라서 생기는 `config.json` 로드 에러를 "데이터가 잘못됐나"로 오해하지 않는다 — 먼저 필드 차이를 의심한다.

## 4단계 — 평가

- [ ] 2단계에서 지정한 held-out 10~15개 위치 조합에서 각 5~10회씩 실제 롤아웃한다.
- [ ] (수집했다면) 스트레치 지점도 같은 방식으로 돌리되 결과는 별도로 표시한다.
- [ ] 매 시행 전 로봇을 녹화 때와 같은 시작 자세로 되돌린다.
- [ ] 매 시행마다 **CUP_PICK 성공/실패**와 **POUR 성공/실패**를 따로 기록한다.
- [ ] held-out 전체에 대한 성공률(전체/CUP_PICK/POUR)을 숫자로 집계해 보고한다.
- [ ] 스트레치 지점 결과는 "참고용"으로 별도 줄에 적는다.

**⚠️ 유의할 점**
- 성공/실패는 **로그 문자열이 아니라 실좌표·실물 관측**으로 센다 — "성공으로 찍혔는데 실제로는 쏟았다" 같은 괴리를 걸러낸다.
- 시작 자세를 안 맞추고 바로 시행하면, 정책이 분포 밖(OOD)에서 시작해서 **일반화 실패가 아닌 다른 이상 동작**이 나올 수 있다 — 평가 전 반드시 복귀한다.
- held-out 조합을 평가 중에 "이건 너무 어려워 보이니 빼자"는 식으로 바꾸지 않는다 — 2단계에서 미리 정해둔 그대로 다 돌린다.
- 실패가 한두 번 나왔다고 바로 "일반화 실패"로 단정하지 않는다 — 같은 지점에서 반복 실패인지, 조건 따라 갈리는지부터 본다(이 저장소 실패 원인 귀속 규칙: 반복 실패는 로직·파라미터, 조건별로 갈리면 데이터·분포 쪽을 먼저 의심).
- 실패를 기록할 때 `failure_code`에는 **관측된 증상만** 적고, 아직 확인 안 된 원인(예: "일반화 안 됨")과 섞어 쓰지 않는다.
- 전체적으로 실패율이 높게 나와도, Nav2·TF·캘리브레이션·기구·서보 문제가 배제되기 전에는 "정책 데이터가 부족해서"로 바로 단정하지 않는다 — 1-2절의 캘리브레이션 사건처럼 하드웨어 쪽 원인일 수도 있다.
