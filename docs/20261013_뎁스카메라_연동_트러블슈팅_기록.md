# 뎁스카메라(Orbbec Astra S) 연동 트러블슈팅 기록

최초 작성 2026-10-13 · 조작(IL) 담당자 작성 · 목적: 과정 기록 + 포트폴리오용 소재

이 문서는 3인칭(탑뷰) 카메라를 일반 RGB 웹캠에서 Orbbec Astra S(뎁스카메라)로
교체하면서 겪은 문제와 해결 과정을 정리한 것이다. 최종 결론만이 아니라
**어떻게 원인을 좁혀갔는지**를 남겨서, 나중에 비슷한 문제를 겪거나 포트폴리오에
"문제 해결 과정"을 쓸 때 참고할 수 있게 한다.

---

## 0. 전체 그림 — 무엇을 왜 했는가

**목표**: 기존 3인칭 RGB 웹캠을 Orbbec Astra S로 바꿔서 쓰고 싶다.
**문제**: Astra S는 일반 웹캠이 아니라서 단순히 연결한다고 되는 게 아니었고,
아래 6단계 문제를 순서대로 만나고 풀었다.

1. 윈도우가 장치 자체를 못 읽음 (USB 인식 실패)
2. 인식은 됐는데 드라이버가 없음
3. 드라이버는 깔았는데 컬러 영상을 lerobot 파이프라인에 넣을 방법이 없음
4. 가상 카메라로 우회했는데 좌우반전
5. 가상 카메라가 중간에 멈춤(라이브인 줄 알았는데 정지 사진)
6. 카메라 화각(FOV)·각도·노출값 — 데이터 품질 관련 세부 조정

---

## 1. 1단계 — "설정에 카메라가 안 떠요" → 사실은 USB 레벨 문제였다

**증상**: 윈도우 설정 > 카메라에 아예 안 보임.

**처음 의심한 것(사용자)**: 오디오 인터페이스가 포트를 점유하고 있을 수도 있다.

**진단 방법**: `Get-PnpDevice`, `Get-CimInstance Win32_PnPEntity`로 장치 관리자
수준의 정보를 PowerShell로 직접 조회. "설정 앱에 안 보인다"는 증상만으로
추측하지 않고, 실제 USB 열거(enumeration) 상태부터 확인했다.

**발견**: 오디오 인터페이스(MI_01)는 **이미 정상 작동 중**이었다 — "오디오가
점유" 가설은 기각. 대신 완전히 다른 장치(`VID_0000&PID_0002`, "장치 설명자
요청 실패")가 **3개의 서로 다른 USB 포트/허브에서 동일하게** 실패하고 있는 걸
발견 — 포트를 바꿔도 안 됐다는 건 포트 문제가 아니라 **케이블 또는 장치 자체**
문제라는 신호였다.

**교훈**: "증상이 어디서 보이는가"(설정 앱)와 "진짜 원인이 있는 계층"(USB
enumeration)이 다를 수 있다. 증상 레벨에서 바로 추측하지 말고 더 아래
계층(장치 관리자 → PowerShell 진단)까지 내려가서 확인하는 게 빨랐다.

---

## 2. 2단계 — 인식은 됐는데 "드라이버가 없음"(Code 28)

연결 포트를 바꿔가며 재시도한 끝에, 장치가 `Orbbec(R) Astra(TM) 3D Camera(F)
Depth`라는 이름으로 잡히기 시작했다. 다만 **오류 코드 28**("드라이버가 설치되지
않음")이 떠 있었다.

받아둔 Astra SDK(C++ 개발용 패키지)를 열어봤지만 **드라이버 설치 파일(.inf)이
없었다** — SDK와 드라이버가 별도 배포라는 걸 그때 알게 됐다. Orbbec 공식
사이트에서 Windows용 드라이버 패키지(`SensorDriver_V4.3.0.22.exe`)를 별도로
받아 설치하고 재부팅하니 해결됐다(장치 상태 OK, `obdrv4` 드라이버 서비스로 등록).

**교훈**: 하드웨어 벤더가 "SDK"와 "드라이버"를 분리 배포하는 경우가 있다 —
SDK 안에 당연히 드라이버가 있을 거라고 가정하지 않고, 설치 전에 실제로 폴더
안에 뭐가 있는지 확인하는 과정이 필요했다.

---

## 3. 3단계 — 드라이버는 깔렸는데, 컬러 영상을 어떻게 꺼내나

Astra S가 정상 인식된 뒤에도, 일반 웹캠처럼 `cv2.VideoCapture(index)`로 바로
안 잡혔다. `pygrabber`로 DirectShow 장치 목록을 직접 뽑아보니, 노트북 웹캠과
손목캠 2대만 보이고 **Astra의 컬러 스트림은 목록에 아예 없었다** — Astra는
일반 UVC 웹캠이 아니라 OpenNI2(Astra SDK) 전용 인터페이스로만 컬러 영상을
꺼낼 수 있는 구조였다.

**해결**: "가상 카메라 브리지"를 직접 만들었다.
1. `primesense`(OpenNI2의 파이썬 ctypes 래퍼)로 Astra 컬러 스트림을 읽는다.
2. `pyvirtualcam`으로 그 프레임을 가상 카메라에 계속 송출한다.
3. 가상 카메라 백엔드로 **OBS Studio의 Virtual Camera**를 썼다(GitHub
   릴리즈 API로 최신 버전을 찾아 설치 — 실제 OBS 앱은 켤 필요 없고, 설치
   시점에 가상 카메라 드라이버만 등록되면 된다).
4. 그러면 Astra의 컬러 영상이 "OBS Virtual Camera"라는 이름의 평범한
   DirectShow 장치로 보이고, lerobot의 `type: opencv, index_or_path: N`
   설정에 그대로 쓸 수 있다.

실제로 캡처한 프레임을 파일로 저장해서(AI는 실시간 화면을 볼 수 없어서) 읽어
확인하는 방식으로, "진짜로 로봇 작업대가 찍히는지"를 검증했다.

**교훈**: 벤더 전용 SDK로만 접근 가능한 센서를, 기존 파이프라인(여기선
OpenCV 기반 lerobot)이 이해하는 형태로 바꿔주는 **브리지/어댑터 패턴**이
센서 교체 시 자주 필요하다. 가상 카메라는 그 브리지를 만드는 한 가지 방법.

---

## 4. 4단계 — 좌우반전

컬러 영상은 나왔는데 좌우가 뒤집혀 있었다. lerobot 공식 설정(`Cv2Rotation`)에는
0/90/180/270도 회전만 있고 **순수 좌우 미러 옵션이 없어서**, lerobot 로컬
포크에 `mirror: bool` 설정을 직접 패치로 추가했다(`cv2.flip(frame, 1)` 적용).
이미 이 저장소에 있던 "로컬 lerobot 포크 + 패치 파일로 기록"이라는 기존
관례(`tools/servo/*.patch`)를 그대로 따라서, `tools/camera/lerobot_opencv_mirror.patch`로
저장해뒀다 — 나중에 lerobot을 다시 설치해도 패치만 다시 적용하면 복구된다.

**검증 방법**: 테스트로 캡처한 사진에서 "병이 왼쪽, 컵이 오른쪽"으로 찍힌 걸
보고(실제로는 컵이 왼쪽, 병이 오른쪽이어야 함) 반전을 역으로 확인했다 — 단순히
"이상해 보인다"가 아니라 **알고 있는 정답(컵-병 배치 순서)과 대조**해서
반전 여부를 명확히 판별했다.

---

## 5. 5단계 — "라이브가 아니라 멈춘 사진이었다"

미리보기가 떴는데 사용자가 "실시간 영상이 아니라 사진 같다"고 의심했다.
장면이 원래 안 움직이는 정적인 구도라 **눈으로는 구분이 안 됐다.**

**검증 방법**: 연속된 4프레임을 받아서 픽셀 차이를 직접 계산(`numpy`로
diff sum). 결과가 **정확히 0** — 진짜 멈춰있었다는 게 숫자로 증명됐다.
(나중에 또 멈췄을 때도 같은 방법으로 재확인 — 매번 "그런 것 같다"가 아니라
diff 값으로 판정했다.)

**원인 추정**: OBS 앱을 띄우는 시점, 그리고 로봇 팔 텔레옵을 돌리는 시점에
맞춰 두 번 멈췄다 — USB 대역폭/허브 공유로 인한 간섭일 가능성이 있다(확정은
아님, 계속 재발하면 카메라와 로봇 팔 시리얼선을 별도 USB 포트로 분리하는
게 다음 조치).

**교훈**: "눈으로 보기에 live 같다/아니다"는 주관적이고 틀리기 쉽다.
연속 프레임을 직접 비교해서 **숫자로 판정**하는 쪽이 훨씬 빠르고 확실했다 —
이 저장소의 "성공/실패 판정은 로그 문자열이 아니라 실좌표·실물 관측으로
센다"는 원칙과 같은 맥락.

## 6. 6단계 — 화각·각도·노출 조정 (데이터 품질)

### 6-1. "줌아웃"이 안 된다 → 물리적으로 멀리/높이 두는 수밖에 없다

소프트웨어 줌아웃은 존재하지 않는다(렌즈가 못 보는 범위를 소프트웨어가
만들어낼 수 없음) — 카메라를 물리적으로 더 멀리/높이 두는 것만이 답이었다.

### 6-2. 뭘 꼭 프레임 안에 담아야 하는지 기준을 세웠다

- **반드시 보여야 하는 것**: 물체(컵·병), 그리퍼가 쥐고 있는 것, 집기·붓기
  같은 동적인 상호작용.
- **안 보여도 되는 것**: 로봇 베이스(고정 모터), 천장 같은 빈 공간 — 로봇의
  관절 상태는 이미 인코더 값으로 모델에 전달되므로, 카메라가 "안 움직이는
  고정 부품"까지 보여줄 필요는 없다.

이 기준 덕분에 "베이스가 잘려도 되냐"는 질문에 "그리퍼·물체만 안 잘리면
된다"는 명확한 답을 낼 수 있었다.

### 6-3. 각도(틸트)에 대한 반직관적인 결론

천장이 보일 만큼 카메라 각도가 얕으면(눈높이에 가까우면), 물체를 조금만
들어올려도 화면에서 크게 움직여 잘리기 쉽다. 반대로 **카메라를 더
수직(위에서 아래로)에 가깝게 숙이면, 같은 들어올리는 동작이 화면에서 덜
움직여 보여서 오히려 덜 잘린다** — "옆에서 보면 작은 움직임도 커 보이고,
위에서 보면 큰 움직임도 작아 보인다"는 원근감의 성질 때문. 카메라를 숙이면
"잘릴까봐 걱정"했는데 실제로는 반대 효과였다.

### 6-4. 노출/화이트밸런스는 고정이 맞다 — 단, 추론 때도 똑같이

"노이즈를 없애면 오히려 실전에서 노이즈에 약해지지 않냐"는 질문이 나왔는데,
핵심은 **자동 노출의 흔들림이 "진짜 환경 다양성"이 아니라 카메라 자체가
만드는 잡음**이라는 것. 조명이 실제로 안 바뀌는데 카메라가 혼자 밝기를
흔드는 걸 학습에 넣어도 진짜 강건성은 안 생긴다. 대신 **학습 때 쓴 고정값을
추론 때도 똑같이 쓰는 것**이 중요하다는 결론으로, 별도 문서
(`20261013_뎁스카메라_노출_화이트밸런스_고정.md`)로 남겨뒀다.

## 7. 작업 중 겪은 운영 실수 (정직하게 남겨둠)

- 멈춘 브리지를 재시작하면서 미리보기 창도 같이 새로 띄워야 한다는 걸 처음엔
  놓쳐서 "재시작했는데 왜 여전히 멈춰있냐"는 혼선이 한 번 있었다 — 오래된
  `VideoCapture` 연결은 새 송출 프로세스로 자동 재연결되지 않았다.
- `taskkill`로 특정 PID만 끄려다가 실수로 `/IM python.exe`(이름 기준 전체
  종료)를 보내서, 돌아가던 로봇 팔 텔레옵 세션까지 같이 꺼진 사고가 있었다.
  다행히 하드웨어 피해는 없었지만, **이름 기준 전체 종료 명령은 위험하다**는
  걸 직접 겪었다 — 이후로는 PID를 정확히 지정하는 방식으로만 종료하기로 함.

## 8. 포트폴리오에 쓸 만한 요약 한 줄

"벤더 전용 SDK로만 접근 가능한 뎁스카메라를, 기존 OpenCV 기반 파이프라인에
가상 카메라 브리지로 연동하고, 좌우반전·노출 안정성·화각 문제를 각각
원인을 좁혀가며(USB 레벨 진단, 프레임 diff 비교, 기하학적 추론) 해결한 경험."
