# 물 서빙 로봇 팀 보고: 무선 운용, SLAM, PLANNED·ACT 비교

- 작성일: 2026-09-08
- 최종 갱신: 2026-09-08 — 산업형 피킹 조사와 `PLANNED_ALL / ACT_ALL / HYBRID` 반영
- 대상: 주행·정책·인지·기구·통합 담당 팀원
- 목적: 물 서빙 전체 절차와 Pi·노트북의 처리 분담, 지도 운용 방식, 구현·검증 순서를 공유한다.

이 문서는 [2026-09-07 회의 결정](20260907_물서빙로봇_회의결정과_실행범위.md)을 설명하는 보고서다.
태스크와 담당 팔 등 회의 결정을 새로 확정하지 않는다. `확정`은 회의 결정 또는 저장소 기록,
`제안`은 구현 배치안, `미검증`은 현재 장비에서 실행 증거가 없는 항목을 뜻한다.

## 1. 보고 요약

현재 태스크는 웹 요청을 받은 로봇이 주방에서 물 한 잔을 준비하고, 선반에 실어 손님
테이블로 운반한 뒤 서빙하고 충전소로 돌아오는 것이다. 커넥터 연결·범용 다중 태스크·
음성 명령·LLM은 현행 범위에 넣지 않는다.

로봇에는 Pi를 싣고, 노트북은 로봇 밖에 둔 채 같은 실험용 네트워크로 연결하는 구성을
검증한다. Pi는 센서 수신·자율주행·미션 순서·명령 실행과 안전 검사를 맡고, 노트북 GPU는
ACT 추론을 맡는다. 산업형 `PLANNED` 조작은 Pi의 좌표변환·IK·검증 궤적·센서 폐루프를
기준으로 하고, ACT는 비교·선택 가능한 backend다. 따라서 무선 운용을 시작하기 위한 선행
조건이 ACT 경량화는 아니다.

| 질문 | 현재 답변 | 상태 |
|---|---|---|
| 로봇과 노트북을 무선으로 연결할 수 있는가 | 관측을 보내고 행동 묶음을 받는 공식 원격 추론 경로가 있다 | 상류 지원 확인, 우리 양팔 통합은 미검증 |
| Pi 한 대로 운용한다는 뜻인가 | 로봇 탑재 SBC는 한 대이고, 외부 노트북과 모터 제어보드·서보는 별도로 필요하다 | 제안 구성 |
| 노트북 없이 Pi 혼자 ACT까지 처리하는가 | 현재 목표 배치가 아니다. Pi CPU 추론 가능성과 실시간 운용 가능성은 별도 검증 대상이다 | 미검증 |
| 지도를 미리 만들어야만 하는가 | 저장 지도를 사용하거나, 이동하면서 지도를 만드는 두 방식이 가능하다 | 두 방식 모두 상류 지원 |
| 반복 물 서빙의 기준선은 무엇인가 | 기존 회의 문서는 사전 지도 + AMCL + Nav2를 권장한다 | 권장 기준선 |
| 온라인 SLAM으로 변경됐는가 | 이번 논의에서 가능성을 확인했으며 채택 결정은 아직 없다 | 미결 |
| 산업 현장에서 피킹을 전부 IL로 하는가 | 공개 제품은 AI 인식·그립 판단과 경로계획·정밀 제어를 결합한다 | 공식 자료 확인, 전체 업계 빈도는 미확인 |
| 우리도 ACT를 반드시 써야 하는가 | 작동을 위해 필수는 아니다. PLANNED·ACT·HYBRID를 같은 조건에서 비교한다 | 후속 구현 결정 |
| 현재 무선 물 서빙이 완료됐는가 | 데이터 규약·검증 도구는 있으나 현행 정책·무선 통합·실물 완료 증거는 없다 | 구현·실험 필요 |

## 2. 물 서빙 전체 절차

주행 중에는 컵을 팔로 들고 이동하지 않고 로봇 선반에 둔다. 팔이 조작할 때는 베이스를
정지한다. `policy 1`과 `policy 2`는 미션의 조작 구간 이름이며 실행기를 ACT로 고정하지
않는다. 이동과 충전은 어떤 조작 전략에서도 ACT에 맡기지 않는다.

| 순서 | 로봇 동작 | 주 처리 위치 | 다음 단계로 넘어가는 확인 |
|---|---|---|---|
| 1 | 충전소에서 웹 요청 대기 | Pi 미션 관리자, 노트북 웹 UI | 유효한 요청 ID·음료·테이블 등록 |
| 2 | 충전소 이탈 후 주방으로 이동 | Pi 주행 계층 | 도크 이탈과 Nav2 도착 결과 |
| 3 | 주방 작업대 앞에서 거리·방향 정렬 | Pi 정렬·좌표변환 계층 | 작업 셀 상대 자세와 베이스 정지 |
| 4 | 왼팔로 컵, 오른팔로 물통을 잡아 붓기 | 선택한 PLANNED·ACT·HYBRID, Pi 실행 계층 | phase·backend 결과, 물 양·흘림 관측 |
| 5 | 오른팔 물통 원위치, 왼팔 컵 선반 적재 | 같은 조작 전략의 반환·배치 phase | 물통 반환·컵 안착·팔 운반 자세 |
| 6 | 손님 테이블로 이동 | Pi 주행 계층 | 테이블 도착과 정렬 조건 |
| 7 | 선반의 컵을 테이블에 내려놓기 | 선택한 PLANNED·ACT backend | 컵 안착·그리퍼 이탈·팔 복귀 |
| 8 | 충전소 복귀·도킹·충전 | Pi 주행·도킹 계층 | 접촉뿐 아니라 충전 시작 신호 |

policy 2의 사용 팔은 회의 본문과 괄호 표기가 서로 달라 미확정이다. 단팔 조작이라는
범위만 유지한다. 회의 TODO의 `3번 policy`도 별도 정책인지 안건 번호인지 확인되지 않았다.
임의로 세 번째 정책이나 데이터셋을 만들지 않는다.

웹에서 누르는 요청 버튼과 미션 완료는 구분한다. HTTP 응답이 왔다고 서빙이 끝난 것이
아니며, 한 요청 ID로 접수·이동·조작·검증·복귀 또는 실패 상태를 추적한다.

## 3. 장비와 연결 전제

아래는 [온보드 컴퓨트 검토](20260903_온보드컴퓨트_USB대역폭_전원_검토.md)에 기록된
장비와 설계 전제다. 연결과 동시 부하까지 검증됐다는 뜻은 아니다.

| 구분 | 기록된 구성 | 보고 시 주의점 |
|---|---|---|
| 로봇 탑재 SBC | Raspberry Pi 4B 4GB | Pi 5 사양이나 성능으로 바꿔 인용하지 않는다 |
| 개발·추론 노트북 | Ryzen 7 260, RAM 30GB, RTX 5050 Laptop VRAM 8GB | 현행 ACT 모델의 추론 시간은 미측정 |
| 주행 센서 | LDS-03 LiDAR, 바퀴 오도메트리·IMU 구성 | 센서 연결·TF·시간 정합을 각각 확인해야 한다 |
| 카메라 | Astra S RGB-D, 좌·우 손목 카메라 | 동시 수신·USB 부하·정책 입력 채널 확정 필요 |
| 팔 | SO-101 양팔, 평행 그리퍼 | 실측 기하·서보 변종·하중·정지 조건 검증 필요 |
| 통신 | 실험용 공유기/AP를 통한 로컬 네트워크 | 인터넷 서비스나 외부 클라우드 접속이 필수인 구조는 아니다 |

카메라·LiDAR·모터는 로봇의 Pi 또는 해당 제어보드에 로컬로 연결한다. 노트북과 로봇
사이의 케이블을 없애는 것이며, 로봇 내부 배선과 전원까지 무선으로 바꾸는 것은 아니다.

## 4. 어떤 작업을 어디서 처리하는가

이 표는 통합을 위한 배치 제안이다. 구현 완료 목록으로 읽지 않는다.

| 작업 | 처리 위치 | 입력과 출력 |
|---|---|---|
| 웹 UI | 노트북 | 음료·테이블 선택을 요청으로 전송, 진행 상태 표시 |
| 요청 검증·중복 방지·미션 상태기계 | Pi | 요청을 받아 주행·정렬·policy·도킹 순서를 전환 |
| 센서 드라이버·오도메트리·TF | Pi | LiDAR·바퀴·IMU·관절 상태를 수신하고 좌표·시간을 관리 |
| SLAM 또는 AMCL | Pi | 지도 생성과 위치 추정, 또는 저장 지도에서 위치 추정 |
| Nav2·장애물 감시 | Pi | 목표 위치와 센서 관측으로 경로·속도·감속·정지 판단 |
| 카메라 수신·전송 대기열 관리 | Pi | 프레임에 시각을 연결하고 오래된 대기 프레임이 쌓이지 않게 전송 |
| 모델용 영상 전처리·ACT 추론 | 노트북 | ACT phase에서만 학습과 동일한 채널·전처리로 관절 목표값 묶음 계산 |
| YOLO 기반 인식 | 노트북 GPU 제안 | 컵·물통·액체 등 선택한 라벨 결과와 신뢰도 반환 |
| PLANNED 조작·작업대 상대 자세·IK·검증 궤적 | Pi CPU 제안 | 그립·접근·들기·붓기 폐루프·반환·배치와 제어 마감 확인 |
| 팔 명령 중재·한계 검사·실행 | Pi | 유효한 명령만 선택해 관절별 목표를 로컬 버스에 전달 |
| 실제 모터 구동 | 모터 제어보드·서보 | 상위 목표를 바퀴·관절 동작으로 변환 |
| 학습·재학습·결과 분석 | 노트북 또는 별도 학습 장비 | 데이터·설정·코드 버전을 고정해 모델과 평가 결과 생성 |
| 실패 근거 보존 | Pi 로컬 기록 후 지정 저장소로 수집 | 관측·명령·통신·실패 레코드를 요청·실행 ID로 연결 |

Pi에서 ACT를 다시 추론하지 않는다. 노트북도 서보 포트를 직접 열지 않는다. 실물 버스는
Pi의 하드웨어 브리지 하나만 소유하고, PLANNED·ACT·수동 조작 명령은 중재기를 거쳐 전달한다.

## 5. 무선 데이터 흐름과 통신 계약

```text
노트북 웹 UI ── 요청·취소 ───────────────────▶ Pi 미션 관리자
              ◀─ 상태·실패·완료 ────────────────┘

로봇 카메라·관절 ─▶ Pi 관측 수집 ── Wi-Fi ──▶ 노트북 ACT 서버(ACT phase만)
                      ▲                         │
                      │                         │ 행동 묶음
                      │                         ▼
                  다음 관측 ◀─ 실제 팔 ◀─ Pi 중재·안전 검사·실행

LiDAR·오도메트리 ─▶ Pi SLAM/AMCL·Nav2 ─▶ 로컬 베이스 제어

Pi RGB-D·TF ─▶ PLANNED 조작 ─▶ Pi 중재·안전 검사·실행
```

LeRobot 0.6.1은 `PolicyServer`와 `RobotClient`를 별도 기기에 두는 비동기 추론 경로와
ACT 정책을 지원한다. 관측으로 다음 행동 묶음을 계산하고 로봇 쪽에서 실행하는 분담을
재사용한다. 공식 클라이언트의 직접 하드웨어 실행을 우리 ROS 명령 중재·안전 계층에
연결하는 어댑터는 별도로 검증해야 한다.
[근거: LeRobot 비동기 추론](https://github.com/huggingface/lerobot/blob/v0.6.1/docs/source/async.mdx)

정책 채널은 상류 비동기 추론 RPC 경로를 우선 평가하고, 웹 요청 채널은 HTTP 게이트웨이로
분리하는 안이다. 로봇 내부 ROS 그래프를 무선망 전체에 그대로 확장하는 것을 전제하지
않는다. 내부 메시지를 어떻게 어댑터로 옮길지 결정하기 전에는 두 기기에서 같은 서보에
직접 명령을 쓰는 예제를 실행하지 않는다.

다음은 우리 통합 어댑터가 보장해야 할 논리 계약이다. 공식 CLI가 아래 항목을 모두 자동으로
구현한다고 가정하지 않는다.

| 방향 | 전달·검사할 내용 | 목적 |
|---|---|---|
| Pi → 노트북 | 요청·실행·관측 ID, policy ID, 영상·관절 상태와 시각 | 어떤 상태를 보고 계산했는지 추적 |
| 노트북 → Pi | 대응 관측 ID, checkpoint·계약 버전, 관절 목표 순서·단위·주기·유효기간 | 다른 policy·과거 상태·잘못된 단위의 명령 혼입 방지 |
| Pi 내부 | 현재 미션 상태, 베이스 정지, 선택된 제어 주체, 관절 한계·스톨 | 실행 직전 허용 여부 판단 |
| 양쪽 기록 | 송수신·추론·큐 대기·실행 시각, 드랍·재연결 사유 | 지연과 실패 위치 분리 |

미션 전환·취소·재연결 시 이전 행동 대기열을 무효화한다. 최신 관측인지 확인되지 않은
명령은 실행하지 않는다. Pi의 단조 시계로 왕복·경과 시간을 재고, 기기 간 시각을 비교할 때는
시계 동기화 오차도 기록한다. 서로 다른 컴퓨터의 시각을 보정 없이 빼서 지연값으로 쓰지 않는다.

무선망은 실험용 신뢰 네트워크로 제한하고 추론 포트를 인터넷에 공개하지 않는다.
배포 시 RPC 인증·암호화 지원과 필요 시 VPN 등 보호 경계를 별도로 확인한다.

## 6. 지도 운용 방식 두 가지

### A. 미리 만든 지도로 반복 운행

처음 공간을 돌아다니며 SLAM으로 지도를 만들고 저장한다. 물 서빙 운용에서는 `map_server`로
지도를 읽고 AMCL로 현재 위치를 추정하며 Nav2로 이동한다. 지도 파일 외에 초기 위치·방향,
충전소·주방·테이블의 목표 위치·방향과 실제 차체 외곽 설정이 필요하다.
[근거: AMCL](https://docs.nav2.org/jazzy/configuration_and_development/configuration_guide/others/configuring_amcl/)

지도 제작을 마쳐도 LiDAR·오도메트리·위치 추정·장애물 회피를 끄지 않는다. 사람이 통로를
막으면 현재 센서 정보를 costmap에 반영해 피하거나 멈춘다. 움직인 의자 하나 때문에 매번
전체 지도를 새로 만들 필요는 없지만, 고정 배치가 바뀌면 지도와 station 위치를 다시 검증한다.
[근거: 지도·위치 추정·costmap](https://docs.nav2.org/jazzy/configuration_and_development/first_time_robot_setup_guide/sensors/mapping_localization/)

### B. 지도를 생성하면서 운행

`slam_toolbox`가 이동 중 지도와 현재 위치를 갱신하고, Nav2가 그 지도로 경로를 계산한다.
이 모드에서는 AMCL과 정적 map server 대신 SLAM이 `/map`과 `map→odom`을 제공한다.
같은 변환을 SLAM과 AMCL이 동시에 발행하지 않도록 launch 구성을 분리한다.
[근거: 이동하며 지도 만들기](https://docs.nav2.org/jazzy/tutorials/general_tutorials/navigation2_with_slam/navigation2_with_slam/)

온라인 SLAM을 켰다고 미지 공간의 탐색 목표나 주방의 의미가 자동으로 정해지지는 않는다.

- 사람이 조종하거나 도달 가능한 목표를 지정하면 이동한 주변의 지도를 만들 수 있다.
- 미탐색 영역을 스스로 찾아 지도 전체를 완성하려면 별도 탐색 목표 선택 기능이 필요하다.
- "주방으로 가라"는 요청에는 주방의 위치 등록 또는 인식·연결 규칙이 추가로 필요하다.
- 지도 보정으로 추정 위치가 바뀔 수 있으므로 station의 일관성과 마지막 작업대 정렬을 확인한다.

| 비교 항목 | 사전 지도 + AMCL | 온라인 SLAM + Nav2 |
|---|---|---|
| 지도 | 저장 지도를 사용 | 이동하며 생성·갱신 |
| 위치 추정 | AMCL | SLAM |
| 처음 보는 공간 | 사전 지도 제작 필요 | 관측한 영역부터 지도 확장 가능 |
| 자율 탐색·장소 의미 인식 | 별도 기능 | 역시 별도 기능 |
| 컴퓨트 검증 | 위치 추정·주행·센서 동시 부하 | 지도 갱신·보정까지 포함한 동시 부하 |
| 현재 팀 결정 | 반복 물 서빙의 권장 기준선 | 가능한 대안, 아직 채택 미결 |

두 모드 모두 Pi 주행·노트북 ACT라는 분담을 유지할 수 있다. 온라인 SLAM을 선택하더라도
팔 조작 중에는 베이스를 정지한다. 미지 공간 자율 탐색은 이번 물 서빙 필수 구현 범위에
추가하지 않는다.

## 7. PLANNED·ACT·HYBRID와 물 양 판정

### 7.1 산업용 피킹 조사에서 반영한 경계

씨메스로보틱스·ABB·FANUC의 공식 공개 자료는 AI를 물체 인식·깊이 복원·피킹 순서·그립
후보 계산에 사용하고, 경로계획·정밀 로봇 제어·전용 그리퍼·PLC·리커버리를 결합한 구조를
설명한다. 공개 자료만으로 씨메스로보틱스가 IL을 전혀 사용하지 않는다고 단정할 수는 없지만,
`AI 피킹`을 곧 사람 시연 기반 end-to-end 관절 정책으로 해석할 근거도 없다.

ACT 원 논문은 단순 pick-and-place보다 밀리미터 오차·양손 접촉·폐루프 시각 협응이 필요한
fine manipulation을 겨냥한다. 현재 물 서빙은 station·컵·물통을 구조화할 수 있고 조작 중
베이스를 정지하므로, 전체 ACT를 필수 전제로 두지 않고 산업형 기준선과 직접 비교한다.
근거와 사실·추론 경계는 [R33 산업용 피킹과 IL·ACT 적용 경계](../research/R33_산업용_피킹과_IL_ACT_적용경계.md)에 정리했다.

### 7.2 세 실행 전략

| 전략 | 주방 조작 | 목적 |
|---|---|---|
| `PLANNED_ALL` | RGB-D·그립 계산·IK·검증 궤적·그리퍼 피드백·액면 폐루프 | 산업형 기준선 |
| `ACT_ALL` | 주방의 모든 조작 phase를 ACT로 실행 | 전체 IL 가능성과 한계 측정 |
| `HYBRID` | phase별로 PLANNED 또는 ACT 선택 | 실제 이점이 확인된 구간만 학습 적용 |

첫 HYBRID 후보는 `CUP_PICK / JUG_PICK / MOVE_TO_PREPOUR / JUG_RETURN / SHELF_PLACE`를
PLANNED로, `POUR`를 ACT로 둔다. ACT 파지가 위치·재질 변화에서 더 낫다는 결과가 나오면
해당 phase만 교체한다. 미션 상태기계·Nav2·안전·물 양 독립 평가는 세 전략 모두 공통이다.

전체 시연에는 `CUP_PICK`, `JUG_PICK`, `MOVE_TO_PREPOUR`, `POUR`, `JUG_RETURN`,
`SHELF_PLACE`의 시작·종료 timestamp를 기록한다. 같은 원본을 전체 ACT와 phase별 ACT 학습에
재사용한다. 하나의 긴 ACT만 학습하면 중간 진입·종료 상태가 정의되지 않아 HYBRID로 바꾸기
어렵다.

### 7.3 중간 전환과 새 모델 필요 여부

phase별 순차 전환에는 별도 `IK+IL` 통합 신경망이 필요하지 않다. 미션 관리자가 phase별
backend를 선택한다. 단, 사람이 시연한 시작 상태와 PLANNED가 만든 시작 상태가 다르면
HYBRID rollout에서 해당 phase의 성공 시연 또는 검토된 복구 데이터로 보강한다.

```text
backend 종료
  → 목표 자세 허용오차·관절 속도 0 확인
  → 남은 ACT chunk 폐기
  → command lease 해제
  → 다음 backend reset·시작 조건 확인
  → 다음 lease 획득·실행
```

두 backend가 같은 관절에 동시에 명령하거나 움직이는 중간에 전환하지 않는다.
`q_command = q_planned + delta_q_learned` 형태의 residual 결합은 출력 의미가 다른 새 모델과
안정성 검증이 필요하므로 첫 구현에서 제외한다.

### 7.4 ACT 실행과 무선 조건

학습은 수집한 시연으로 모델을 만드는 과정이고, 운행 중 필요한 것은 추론이다. 같은 노트북
GPU에서 학습과 실시간 추론을 함께 돌리는 것을 기준선으로 잡지 않는다.

정책 입력은 RGB와 관절 상태를 기본으로 하고, phase·컵/물통 상대 자세·액면 상태의 포함은
feature 계약과 ablation으로 고정한다. 실제 수집 전에 카메라 key·해상도·crop·fps·관절
순서·단위·action 표현을 확정한다. 전송 부하를 이유로 입력을 바꾸면 학습 입력과 일치하는지
다시 검증한다.

ACT의 행동 묶음 길이, 새 관측으로 재계산하는 시점, Pi의 관절 명령 주기는 서로 다른 값이다.
추론 지연·통신 두절로 큐가 비거나 낡은 행동이 남을 수 있으므로 관측·행동 ID와 유효기간,
로컬 watchdog을 둔다. 남은 chunk보다 안전 게이트가 우선한다.

### 7.5 물 양 판정

YOLO 계열 비전 사용은 회의 결정이지만 검출·분할 형식과 실시간 배치는 미확정이다. 바운딩
박스가 곧 mL는 아니다. 컵 재질·시야·액면 관측 가능성, 컵별 보정, 목표량·허용 오차와 실측
정답 방법을 먼저 정한다.

`PLANNED` 붓기에서는 액면 추정을 기울임 감속·정지의 폐루프 입력으로 사용한다. `ACT`에서는
액면 상태를 관측에 넣는 안과 외부 감독기가 목표 도달 시 종료시키는 안을 분리해 비교한다.
`OVER / SPILL / UNKNOWN`은 strategy와 무관하게 외부 감독기가 추가 기울임을 금지한다.
성공 판정은 YOLO 자기평가만 사용하지 않고 저울 또는 눈금 계량 ground truth와 비교한다.

## 8. 안전·실패 처리의 책임

| 상황 | 로봇 쪽에 필요한 처리 | 남길 근거 |
|---|---|---|
| Wi-Fi 끊김·노트북 추론 정지 | 명령 유효기간·로컬 watchdog에 따라 조작을 안전 정지 | 마지막 유효 관측·명령·두절 시각 |
| 늦거나 중복된 ACT 행동 묶음 | 폐기하고 재연결·재시작 조건 확인 | ID·순서·폐기 사유 |
| 베이스 이동 중 팔 조작 요청 | 조작 시작 거부 | 미션 상태·베이스 상태 |
| 스톨·관절 한계·충돌 위험 | 즉시 해당 안전 절차로 전환 | 목표·실측 관절·상태·안전 게이트 결과 |
| 사람·장애물 접근 | 로컬 감속·정지, 필요 시 미션 중단 | LiDAR·costmap·속도 명령 |
| Pi 자체 정지·프로세스 장애 | 하위 제어기의 통신 타임아웃과 독립 정지 수단 검증 | heartbeat·보드 상태·정지 확인 |
| 물 양 불명·컵 불안정 | 성공·운반 전환 보류, 수동 확인 또는 안전 종료 | 영상·물 양 추정·실측·선반 상태 |

안전 정지는 무조건 토크 OFF를 뜻하지 않는다. 컵을 든 상태에서 토크를 끄면 낙하할 수 있고,
스톨 상태에서 계속 힘을 유지해도 위험하다. 자세·하중·고장 종류별 정지 처리를 검증해야 한다.
무선 단절 뒤 이미 시작한 주행을 계속할지 정지할지도 미션 정책으로 확정한다. 주행 연산이
Pi에 있다는 사실만으로 무조건 계속 운행하도록 정하지 않는다.

실물 팔 동작은 건별 승인과 결정적 차단 장치가 있는 환경에서만 수행한다. 차단 장치가 없는
Codex 환경에서는 dry-run까지만 다룬다. 일반적인 ROS 안전 노드나 watchdog이 안전 인증을
대체한다고 주장하지 않는다.

## 9. 기존 설명에서 정정할 점

| 기존 설명 또는 혼동 | 이 보고서의 판정 |
|---|---|
| Pi에는 CUDA가 없으니 ACT 추론이 불가능하다 | CPU 추론 가능성과 요구 성능 충족은 별개다. CUDA 부재만으로 불가능 판정하지 않는다 |
| Pi 5로 바꾸면 SLAM과 ACT가 해결된다 | 현재 장비는 Pi 4B이며, Pi 5에서도 실제 모델·센서·주행 동시 부하 검증이 필요하다 |
| 노트북 추론 20ms, Wi-Fi 10~30ms라 여유가 충분하다 | 과거 컴퓨트 문서의 추정·예산값이다. 우리 태스크의 실측 결과가 아니다 |
| ACT 행동 묶음이 길면 무선 지연은 문제가 없다 | 관측 노후화와 반응 지연이 생긴다. 큐·유효기간·정지 조건을 검증해야 한다 |
| 지도만 만들면 주행 준비가 끝난다 | 초기 위치·목표 위치와 방향·센서·위치 추정·장애물 회피 설정이 남는다 |
| 온라인 SLAM은 자율 탐색과 주방 인식까지 한다 | 지도 생성·위치 추정, 탐색 목표 선택, 장소 의미 인식은 서로 다른 기능이다 |
| ACT 경량화가 무선 운용의 선행 작업이다 | 외부 GPU 추론을 사용하면 경량화 없이 무선 기준선을 검증할 수 있다 |
| 산업용 피킹은 AI를 사용하지 않는다 | 인식·깊이·피킹 순서·그립 후보에는 AI를 쓰되 경로계획·제어와 모듈형으로 결합한다 |
| 물체를 집으려면 반드시 IL이 필요하다 | 구조화된 물체·station은 비전·IK·그리퍼 피드백으로 기준선을 만들 수 있다 |
| 전체 ACT를 만든 뒤 임의 지점에서 IK를 켜면 HYBRID가 된다 | phase 경계·정지·lease·ACT reset과 실제 PLANNED 시작 분포 검증이 필요하다 |

완전 Pi 온보드 추론과 경량화는 이번 보고의 구현 목표에 추가하지 않는다. 필요성이 생기면
기존 모델의 지연·메모리·실패율을 먼저 측정한 뒤 별도 과제로 판단한다.

## 10. 구현과 검증 순서

팀의 1순위는 지정 policy 학습·배포와 실패 개선이다. 주행·인지 담당은 분리된 계약과
가짜 응답을 반환하는 mock으로 병행하고, 실물 통합은 선행 검증을 통과한 뒤 진행한다.

| 단계 | 할 일 | 확인할 결과 |
|---|---|---|
| 1. 계약 확정 | phase·사용 팔·관측/action key·station·성공/실패·backend 전환 정의 | 담당 간 같은 입력·출력·단위 사용 |
| 2. PLANNED 기준선 | 그립·IK·검증 궤적·붓기 폐루프를 phase별 dry-run·mock으로 연결 | planner·trajectory·controller·config 버전과 재현 결과 |
| 3. ACT 기준선 | phase 표시 smoke 시연 → 로더 확인 → 과적합 → ACT_ALL·로컬 ACT | dataset·checkpoint·설정·코드 버전과 재현 결과 |
| 4. 주행 기준선 | 지도 모드를 골라 충전소·주방·테이블 접근 평가 | 위치·방향 오차, 장애물 정지, 실패·복구 기록 |
| 5. 무선 무동작 시험 | 녹화 관측 또는 mock을 Pi↔노트북으로 보내고 실제 모터 명령은 차단 | 송수신·추론·큐 지연, 명령 계약, 두절·지연·재연결 처리 |
| 6. 센서 동시 부하 시험 | 실제 카메라 수신과 주행 계층을 함께 실행하되 이동은 별도 안전 게이트 적용 | 프레임 드랍, CPU·RAM·발열, 제어 마감 누락 |
| 7. 정지 베이스 건식 비교 | 승인 환경에서 PLANNED_ALL·ACT_ALL·HYBRID를 빈 컵·물통으로 비교 | phase 전환, 팔/베이스 상호 배제, strategy별 결과 |
| 8. 물 서빙 검증 | 같은 하중·물 양·scenario matrix에서 세 전략 평가 | 실측 물 양, 흘림, 컵 안착, 도킹·충전 확인 |
| 9. 실패 개선 | 원인별 시스템 수정 또는 검토된 phase 데이터 보강 후 동일 조건 재시험 | 전략·phase별 변경 전후·회귀 결과 |

각 단계의 수치 통과 기준은 실제 속도·하중·카메라·안전 요구를 근거로 시험 전에 정한다.
아직 정하지 않은 기준을 임의의 fps·ms·성공률로 채우지 않는다.

측정할 항목은 다음과 같다.

- 영상 획득부터 실제 명령 적용까지의 전체 지연과 관측 나이: 평균뿐 아니라 p95·p99·최댓값.
- 추론 단독 시간, 전송 시간, 전처리·큐 대기 시간, 큐 고갈·낡은 명령 폐기 횟수.
- 카메라별 실제 fps·드랍, 관절 수신·명령 주기와 마감 누락, CPU·RAM·온도·throttling.
- 지도 모드별 위치·방향 오차와 지도 보정 발생 시 영향, 장애물 정지·재계획 결과.
- 요청·strategy·phase·backend별 성공/실패, 사람 개입, 목표 물 양 오차·흘림·컵 안착·충전 상태.

SLAM 지도 작성, 온라인 SLAM 주행, 저장 지도 주행은 각각 구분해 기록한다. 한 모드에서 얻은
성능을 다른 모드나 카메라 구성의 성능으로 대신 보고하지 않는다.

## 11. 실패 데이터 저장과 활용

실패는 `관측 → 근거 → 원인 가설·기각 → 확인 원인 → 조치 → 동일 조건 재시험 → 회귀 확인`
순으로 기록한다. 예를 들어 컵을 놓친 사실만으로 ACT 학습 데이터가 부족하다고 단정하지
않는다. `control_strategy`, phase backend, 도착 오차·TF·카메라 시각·통신 지연·서보·기구를
먼저 분리해 확인한다.

영상·rosbag·관절 궤적은 Git 밖에 보존한다. 코드·스키마·익명화된 예시만 커밋하고,
실데이터와 모델의 공유 위치·버전은 data 인덱스에 기록한다. 데이터 업로드는 별도 작업이다.

현재 구현된 `failure_bank.py`는 근거 복사·SHA-256 검사·레코드 집계를 제공한다. 자동으로
원인을 판정하거나 실험 성공을 인증하거나 실제 로봇의 로그를 수집해 주는 런타임은 아니다.

- `capture`: 관측 입력과 근거를 보존하며 미분석·학습 제외 상태로 시작한다.
- `verify-evidence`: 로컬 근거의 누락·해시 불일치·경로 이탈을 검사한다.
- `summary`: 관측 증상·확정 원인·재시험·데이터 사용 결정을 구분해 집계한다.
- 성공 실행까지 포함한 분모가 없으면 성공률을 계산하지 않는다. 실패 레코드 수와 실행 수는 다르다.
- 실패 원본을 성공 행동의 모방학습에 넣지 않는다. 검토한 사람 개입 복구 구간은 별도 파생
  데이터셋·시간 범위·근거를 남긴다. 현재 검증기는 확인된 `policy_data` 원인만 HIL 학습 보강으로 허용한다.
- 원본과 파생물의 train/holdout 분할을 유지한다. 분석·튜닝한 실패 조건은 회귀 평가용이며
  미사용 holdout 성과로 보고하지 않는다. 메타데이터 일치 외에 실제 원본과 영상의 담당자 대조가 필요하다.

사용법과 스키마는 [실패 데이터 규약](../data/failures/README.md)과
[데이터 인덱스](../data/README.md)를 따른다.

## 12. 역할과 회의에서 닫을 결정

| 작업 | 담당 상태 | 우선 산출물 |
|---|---|---|
| SLAM/Nav2·장애물 회피·station·반복 접근 | @mmporong | 지도 모드별 주행 기준선과 조작 시작 조건 |
| IL·IK 연결, 최종 URDF 이후 Isaac Sim | @mmporong | 좌표·관절 규약, 시뮬 연결 검증. 실행 장비 적합성은 별도 확인 |
| PLANNED·ACT 비교, policy 수집·학습·배포·실패 개선 | 팀 1순위, 세부 담당 확정 필요 | phase 계약, PLANNED 기준선, smoke 데이터, ACT checkpoint, 세 전략 비교 |
| YOLO·컵 보정·물 양 검증 | 세부 담당 확정 필요 | 영상 POC, 라벨·교정·실측 기준 |
| 무선 어댑터·미션 관리자·로컬 안전 통합 | 세부 담당 확정 필요 | 메시지 계약과 무동작·두절 시험 |
| 선반·작업 셀·도크·전원 | 세부 담당 확정 필요 | 실측 좌표·하중·충전 판정 인터페이스 |

본수집 또는 해당 통합을 막는 결정을 먼저 닫는다.

1. `3번 policy`의 의미와 시작·행동·종료 조건, policy 2 사용 팔.
2. 컵·물통·선반의 실측 규격, 주방·테이블 작업 위치·방향, 도달·하중 조건.
3. 목표 물 양·허용 오차·컵 재질·YOLO 라벨 형식·실측 정답 방법.
4. 관측·행동 규약과 비사용 팔 처리, 카메라 수·키·해상도·제어 주기.
5. 반복 시연에 쓸 지도 모드, 초기 위치 확인, station 등록·지도 버전 관리.
6. 무선 명령 유효기간·두절·재연결·중단 동작과 담당자, 수치 검증 기준.
7. 충전 도크 위치·접점·충전 시작 신호, 최종 URDF와 시뮬 실행 환경.
8. phase별 시작·종료 허용오차, 세 전략의 공통 scenario matrix와 합격 판정.

온라인 SLAM·Pi 단독 추론·자동 탐색을 질문했다는 이유만으로 새로운 필수 태스크나
구매 요구사항으로 바꾸지 않는다.

## 13. 현재 완료 범위와 참고 문서

초기 보고서 작성 당시 물 서빙 회의 문서와 데이터 규격, 실패 근거 보존·검증·집계 도구의
로컬 단위 테스트 46개가 통과했다. 이는 데이터 도구의 근거이며, 주행·정책·무선·실물 동작
성능이나 이번에 추가한 세 조작 전략의 구현 완료 근거가 아니다.

현행 태스크의 ACT 데이터·모델, 웹→주행→조작→충전 통합, 무선 지연·두절 시험,
실제 물 서빙과 Isaac Sim 실행은 이 보고서에서 완료로 표시하지 않는다. 다른 세션의 진척도
코드·실행 로그가 합쳐지기 전에는 이 보고서의 검증 완료 항목으로 승격하지 않는다.
