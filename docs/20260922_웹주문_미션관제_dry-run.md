# 웹 주문·Mission Queue·배터리 관제 dry-run

## 1. 구현 범위

웹에서 `몇 번 테이블에 냉수 또는 온수`를 요청하면 주문을 Mission으로 바꾸고, 한 번에 하나의
Mission을 실행한다. 실행 중 들어온 주문은 큐에 저장한다. 기본 backend는 모든 명령을 즉시
성공으로 돌려주는 CPU dry-run이다. 선택형 `ros2-mock`은 조작 명령만 ROS 2 Action으로 보내며
두 모드 모두 실물, 카메라, Isaac Sim에 접속하지 않는다.

구현 파일은 다음과 같다.

- 관제 상태기계: `tools/service_mission_control.py`
- SQLite 저장 계층: `tools/service_order_store.py`
- 로컬 HTTP 서버: `tools/service_order_server.py`
- 웹 화면: `tools/service_order_dashboard/index.html`
- 웹 동작: `tools/service_order_dashboard/dashboard.js`
- 관제 설정: `config/simulation/service_mission_control.json`
- 예제 주문: `config/simulation/service_orders_demo.json`
- 조작 Action 계약·mock: `src/hold_flow_interfaces`, `src/hold_flow_mission`
- 관제 backend adapter: `tools/service_execution_backend.py`

## 2. 책임 경계

```text
웹 주문
  -> Order Queue
  -> MissionController
  -> backend command
       navigate   -> 이후 Nav2 Action
       manipulate -> immediate mock 또는 ExecuteManipulationSkill Action
       charge     -> 이후 도크·충전 확인
```

관제기는 바퀴 속도나 관절 목표를 만들지 않는다. `dock`, `kitchen`, `table_1`처럼 지도에 등록된
목적지와 `grasp_cup`, `pour_water` 같은 skill 이름만 backend에 전달한다. 현재 주행 명령에는
`restaurant_layout.json`의 장애물 팽창 A* 경로를 넣어 목적지 연결 여부를 검사한다. Nav2 실행이나
동적 장애물 회피 성공을 뜻하지 않는다.

## 3. 주문 계약

```json
{
  "order_id": "ORD-20260922-001",
  "table_id": "table_3",
  "drink": "COLD_WATER",
  "created_at": "2026-09-22T12:00:00+09:00",
  "priority": 0
}
```

- `order_id`: 1~64자의 영문·숫자·`._:-`. 재전송 멱등 키로 사용한다.
- `table_id`: 현행 지도에 있는 `table_1`~`table_4`만 허용한다.
- `drink`: `COLD_WATER`, `HOT_WATER`만 허용한다.
- `created_at`: 생략하면 서버 UTC 시각을 사용한다. 입력할 때는 시간대가 포함된 ISO-8601이어야 한다.
- `priority`: 0~9 정수다. 실행 중인 Mission을 선점하지 않고 대기 큐 안에서만 높은 값이 먼저다.

같은 `order_id`와 같은 내용이 다시 오면 기존 주문을 반환한다. 같은 ID에 다른 테이블이나 음료를
보내면 오류로 거부한다.

## 4. 실행 phase

```text
NAVIGATE_KITCHEN
ALIGN_KITCHEN
GRASP_CUP
GRASP_BOTTLE
POUR
RETURN_BOTTLE
PLACE_DECK
NAVIGATE_TABLE
ALIGN_TABLE
REGRASP_CUP
SERVE
```

정렬·파지 phase는 설정된 횟수만 재시도한다. `POUR`처럼 재시도 목록에 없는 phase가 실패하면
그 주문을 `FAILED`로 종료한다. 원인을 `PHASE:failure_code`로 주문에 저장하고 다음 주문 또는 충전
복귀로 전환한다.

## 5. 연속 주문과 충전

각 주문을 시작하기 전에 다음 값을 합산한다.

1. 현재 위치에서 주방까지의 경로
2. 주방에서 손님 테이블까지의 경로
3. 테이블에서 충전소까지 돌아올 경로
4. 조작 phase의 명목 소비량
5. 충전소 도착 뒤 남겨야 하는 배터리 reserve

배터리가 충분하고 대기 주문이 있으면 손님 테이블에서 충전소로 돌아가지 않고 다음 주방 Mission을
시작한다. 부족하면 충전소로 이동하고 목표 충전량에 도달한 뒤 다음 주문을 시작한다. 이 계산은
관제 분기 시험용 명목값이며 실제 전류·전압·하중 기반 추정기가 아니다.

## 6. 실행 방법

### 주문 묶음 dry-run

```bash
cd "$HOME/bimanual-robot"
python3 tools/service_mission_control.py \
  --orders config/simulation/service_orders_demo.json \
  --output-dir /tmp/bimanual-service-mission
```

출력 파일:

- `/tmp/bimanual-service-mission/snapshot.json`
- `/tmp/bimanual-service-mission/commands.json`
- `/tmp/bimanual-service-mission/events.jsonl`

### 웹 주문 화면

```bash
cd "$HOME/bimanual-robot"
python3 tools/service_order_server.py \
  --host 127.0.0.1 \
  --port 8765
```

브라우저에서 `http://127.0.0.1:8765`를 연다. 기본 실행은 0.75초마다 한 phase를 성공 처리한다.
화면은 식당 지도·현재 경로·11개 조작 phase·새 주문·대기열·누적 이력·이벤트를 표시한다.
API에는 `simulation_dry_run`, `hardware_accessed: false`가 표시된다.

### ROS 2 조작 mock과 연결

터미널 1에서 Action server를 실행한다.

```bash
cd "$HOME/bimanual-robot"
source /opt/ros/jazzy/setup.bash
source install/setup.bash
ros2 run hold_flow_mission mock_manipulation_server
```

터미널 2에서 별도 상태 경로와 포트로 웹 관제를 실행한다. 시스템 Python 3.12를 사용해야 Jazzy
Python 모듈과 ABI가 일치한다.

```bash
cd "$HOME/bimanual-robot"
source /opt/ros/jazzy/setup.bash
source install/setup.bash
/usr/bin/python3.12 tools/service_order_server.py \
  --host 127.0.0.1 \
  --port 8766 \
  --state-dir "$HOME/.local/state/bimanual-robot/service-order-server-ros2-mock" \
  --backend ros2-mock \
  --manipulation-timeout-s 30
```

이 모드에서도 주행·충전은 immediate mock이다. 조작 phase만 Action 결과를 기다린다. 화면 상단
badge와 `저장·backend 진단`에서 실행 모드, 활성 Goal, 최근 성공·실패 코드를 확인할 수 있다.

### 검증된 PLANNED 산출물과 연결

현재 소스·입력 해시가 기록과 같은 Isaac Sim 성공 결과가 있으면 phase 근거 재생 모드로 연결할
수 있다. 이 모드는 새 시뮬레이션을 실행하지 않는다.

```bash
cd "$HOME/bimanual-robot"
source /opt/ros/jazzy/setup.bash
source install/setup.bash
ARTIFACT_ROOT="/data/$USER/robot-artifacts"

ros2 run hold_flow_mission planned_artifact_server --ros-args \
  -p result_path:="$ARTIFACT_ROOT/restaurant/cinematic_wide01/result.json" \
  -p repo_root:="$HOME/bimanual-robot"
```

별도 터미널에서 다음 관제를 실행한다.

```bash
cd "$HOME/bimanual-robot"
source /opt/ros/jazzy/setup.bash
source install/setup.bash
/usr/bin/python3.12 tools/service_order_server.py \
  --host 127.0.0.1 --port 8767 \
  --backend ros2-planned-artifact \
  --state-dir "$HOME/.local/state/bimanual-robot/planned-artifact"
```

현재 근거의 범위는 `table_1`, `COLD_WATER`다. 범위 밖 요청은 Action을 `ABORTED`로 끝내고
`ARTIFACT_TABLE_UNSUPPORTED` 또는 `ARTIFACT_DRINK_UNSUPPORTED`를 SQLite에 저장한다.

### 상태를 유지하는 PLANNED IPC mock

Isaac Sim Python 3.11과 ROS 2 Jazzy Python 3.12를 Unix socket으로 분리했다. 현재 executor는
Isaac 물리 대신 phase 순서와 session 상태를 검사하는 mock이다. 세 실행 명령은
[ExecuteManipulationSkill 문서의 Python ABI 분리 절](20260922_ExecuteManipulationSkill_ROS2_Action.md#8-python-abi-분리와-상태-보존-executor-ipc)에 있다.

웹 관제는 `--backend ros2-planned-session`을 사용한다. 진단 화면에서
`ros2_planned_session`, `unix_socket_json`, 활성 Action을 확인할 수 있다. 이 모드의 완료는
프로세스 경계와 상태 전이 검증이며 Isaac Sim 물리 성공이 아니다.

### 영속 저장과 재시작 복구

기본 저장 경로는 다음과 같다.

```text
$HOME/.local/state/bimanual-robot/service-order-server/
├── service_mission_control.sqlite3
├── snapshot.json
└── events.jsonl
```

`XDG_STATE_HOME`이 설정되어 있으면 `$XDG_STATE_HOME/bimanual-robot/service-order-server/`를 사용한다.
SQLite가 주문, 전체 이벤트, 실행 명령, 최신 관제 snapshot을 보존한다. JSON과 JSONL은 사람이 상태를
확인하기 위한 호환 출력이다. 서버를 다시 실행하면 SQLite의 최신 snapshot을 검증한 뒤 활성 주문,
현재 phase, 배터리, 큐와 이벤트 번호를 복구한다. 재시작 때 지정한 `--battery-percent`보다 저장된
상태가 우선한다.

별도 시험 저장소를 쓰려면 다음처럼 지정한다.

```bash
python3 tools/service_order_server.py \
  --state-dir "$HOME/.local/state/bimanual-robot/service-order-server-test"
```

## 7. HTTP API

| 메서드 | 경로 | 용도 |
|---|---|---|
| `GET` | `/api/health` | 서버 모드 확인 |
| `GET` | `/api/state` | 주문·큐·Mission·배터리·이벤트 조회 |
| `GET` | `/api/orders/history?limit=100` | SQLite 주문 이력 조회 |
| `GET` | `/api/events?limit=100` | SQLite 이벤트 이력 조회 |
| `POST` | `/api/orders` | 주문 생성 또는 같은 ID 재조회 |
| `POST` | `/api/orders/{order_id}/cancel` | 실행 전 주문 취소, 실행 중이면 현재 Mission 종료 |
| `POST` | `/api/step` | dry-run 한 phase 실행 또는 실패 주입 |

`/api/step`은 개발·시연용이다. 실제 backend에서는 Nav2·조작 Action 결과가 같은 역할을 맡는다.

## 8. 상용 구조와의 정합성

Bear Robot API가 공개한 Mission·Queue·Status·Feedback과 같은 층을 따른다. 지도 목적지와 한 개의
활성 Mission, 순차 큐, 충전을 별도 Mission으로 다루는 부분을 참고했다. 베어의 소스 코드나 운행
데이터, Kinisi 모델은 사용하지 않았다.

- [Bear Robot API Mission](https://base.api.bearrobotics.ai/concepts/mission/)
- [Bear Locations & Maps API](https://cloud.api.bearrobotics.ai/v1.1/resources/LocationsAndMaps/)
- [Bear Robot API v1.3 ChargeRobot](https://base.api.bearrobotics.ai/v1.3/resources/Mission/)
