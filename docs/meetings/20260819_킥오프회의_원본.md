## 2. 역할 분담

### 현재 자연스럽게 나뉜 파트
- **이미테이션 러닝 / 학습** — 계속 맡아주시는 방향
- **데이터셋 구축·관리** — 준선님
- **로봇 제어(IK + Depth)** — IK 방식과 이미테이션 방식 둘 다 적용 가능하도록 진행 중
- **웹 / 풀스택** — 기존 데이터 팀 경력자가 우선 담당, 로봇 파트는 이후 학습

### 웹을 포함하자는 제안 배경
- OT에서 나온 부트캠프 분류가 **"서비스 로봇 엔지니어"**
- 서비스 로봇은 웹 비중이 매우 크고, 강사님도 **풀스택 방향**을 반복 언급
- → 로봇이 메인이되, 이를 잘 활용할 수 있는 **웹 인터페이스도 함께 구축**

### 분담 방식에 대한 합의
- 프로젝트 규모가 아주 복잡하지 않아 각자 할 일이 그렇게 많지 않을 수 있음
- 따라서 **"파트를 나누되 다 같이 하는 느낌"** 으로
- 파트를 정해두면 각자 **공부 방향**을 잡기 편하다는 장점
- 데이터 수집(텔레옵)은 누구나 할 수 있고, 학습도 관심 있으면 참여 가능 → 자연스럽게 흘러가는 구조

## 3. 시뮬레이션 vs 실물 (→ 실물로 결정)

**시뮬레이션이 어려운 이유**
- 유니트리 같은 상용 로봇과 달리 **URDF가 없음**. URDF/USD를 직접 만들어야 하는데 공수가 큼
- 예시로 제공되는 모델이 아니라 양팔 재현 자체가 난이도 높음

**결정적 이유: Sim2Real 갭**
- 시뮬에서 학습해도 결국 리얼에서 돌려야 하는데, 환경이 어긋나면 성능 보장이 안 됨
- → **텔레오퍼레이션으로 직접 데이터 수집하는 쪽이 빠르고 성능도 좋을 것**

**남은 과제: 양팔 동시 텔레옵**
- 한 팔 리더-팔로워 구성은 익숙하나 **양팔 동시 텔레옵은 미검증**
- 접근안: 팔별로 캘리브레이션 후, 리더 없이 팔로워 기준으로 각각 구성
- 인터넷에 선례가 있을 가능성이 높으므로 리서치 필요

## 4. 태스크 선정

### 기본 방향
- **픽앤플레이스 1단계**부터. "일단 다 해보자"는 기조
- 복잡한 프로젝트도 처음부터 바로 가는 게 아니라 간단한 것부터 차례대로
- **설계는 전체를 다 잡아놓고, 구현만 단계별로**
- 픽앤플레이스는 반드시 되어야 하는 마일스톤 → 기한 맞춰 완료해야 다음 단계 진행 가능
- 이미테이션으로 안 되면 다른 방법으로 전환

### 검토된 태스크 후보
| 후보 | 평가 |
|---|---|
| 픽앤플레이스 | ✅ 1단계로 확정 |
| 빨래 접기 | 너무 단순하거나, 이미 많이 하고 있고 실제론 쉽지도 않음 |
| 사람과 상호작용 | 움직이는 대상이라 난이도 급상승 + **안전 문제(다칠 위험)** |
| 좁은/제한된 공간 픽앤플레이스 | 임팩트는 있으나 아래 반론 참고 |
| 음성 명령 제어 | 긍정적 반응 (아래 참고) |

### "제한된 조건" 태스크에 대한 논의
- **제안**: 좁은 공간에서도 잘 동작하는 픽앤플레이스 → 발표 시 임팩트
- **반론(합의됨)**: 문제점을 미리 가정하지 말고, **일단 돌려보고 실제로 발생한 문제를 나열**한 뒤 "이걸 어떻게 해결했는지"를 보여주는 편이 훨씬 명확하고 설득력 있음

## 5. 기술 아이디어

### 5.1 에이전틱 태스크 분해
- 전체 인스트럭션을 한 번에 주면 로봇이 제대로 수행하지 못할 수 있음
- 예: "오른팔로 들고 → 왼팔로 옮겨 → 내려놓기"
- **VLM/LLM으로 태스크를 서브액션으로 분해**하고, 실행 결과 피드백을 받아 수정하며 순차 실행
- 실제 최신 연구에서도 이런 방식을 사용
- ⚠️ 우려: 3개월 안에 소화 가능한지 (시간 리스크)

**연산 자원**
- 라즈베리파이에서 **로컬 VLM은 불가**
- **API 방식(Claude, GPT 등)은 서버에서 처리하므로 문제없음** → 이 방향으로

### 5.2 음성 제어
- 로봇에 마이크가 달려 있음 → **STT로 음성을 텍스트 변환 후 인스트럭션으로 전달**
- 스피커를 달면 "네, 알겠습니다" 같은 응답도 가능 → 데모 완성도 상승
- 구현 난이도 대비 효과가 좋다는 평

### 5.3 모델 선택
- 최신 VLA 모델 구조: **앞단 VLM + 뒷단 액션 헤드(트랜스포머 / 디퓨전)**
- 산업 현장에서는 **SmolVLA, ACT** 등 **가벼운 모델**을 선호 → 실시간 추론 속도 때문
- 기성 모델을 그대로 쓰거나 파인튜닝 가능하나 **VRAM 20GB 이상 필요**
  - → 클라우드에서 학습 후 **웨이트 파일만 가져오는 방식** 검토 (비용 확인 필요)

### 5.4 월드 모델 (검토했으나 현실적 제약)
- NVIDIA **Cosmos** 계열: 현재 로봇 상태 + 액션 입력 → 비디오 프레임 생성 + 액션 출력
- **A100급 GPU 필요**, 학교 자원 협조 필요
- DiT 구조 기반이라 **디퓨전 특유의 느린 추론** → 실기 적용 속도 미지수

### 5.5 IK vs 이미테이션 러닝
- **IK**: 그리퍼 목표 위치로부터 관절값을 역산 → **결정론적**
- **이미테이션 러닝**: 데이터 기반 → **확률론적**
- 실무에서 IK도 사용된다는 이야기가 있음
- → **결국 목표는 "잘 잡는 것"** 이므로 구분해두고 잘 되는 쪽을 채택

### 5.6 비전 (대학원 연구 접목 가능성)
- 객체 탐지 + 세그멘테이션 + 위치 정보 생성 경험 보유 (YOLO 계열은 미사용)
- 객체 인식 파이프라인 자체는 좋으나 **속도 저하** 우려 → 로봇은 실시간 추론이 중요
- 부트캠프 장비 한계는 있으나, **"더 좋은 장비면 더 빠르다"** 는 구조면 평가상 긍정적

## 6. 구현 방식

- **LeRobot 라이브러리로 먼저 구현**해보고 검증
- 동시에 **커스텀 코드도 병행 제작 중** (공부 목적)
- 이유: 라이브러리만 쓰면 "그냥 클론했구나"로 보일 수 있음 → **자기 코드가 하나라도 들어가야 어필됨**
- 커스텀 방식은 이후 팀에 설명 공유 (예: LeRobot은 이렇게 잡지만 우리는 그리퍼를 먼저 접근시킨다 등의 차이)

## 7. 미니 프로젝트 아이디어 (메인과 별개)

- 메인 하나만 파면 매몰될 수 있으니 **여러 개를 병행**하는 것도 검토
- **주행 로봇 + 팔**: 양팔은 무게·전력상 어려움 → **한 팔만 장착**하거나 **소형 암** 사용
  - SO-101 같은 큰 것 대신 소형으로 제작하면 부담 적음
  - 터틀봇/와플 급은 되어야 할 것으로 예상
  - 엔코더 이슈 확인 후 미니 버전에 장착 시도 예정
- **SLAM** 접목 가능
- **배달 컨셉**: 바구니 장착 → 물체 인식 → 지정 장소로 이동해 놓고 오기
- (농담) 성게처럼 사방에 다리 달린 구형 로봇 / 6족 보행 → 모터 수와 제어 복잡도로 비현실적
