# 프로젝트 현황 — 2026-09-23 기준 (장준서)

이 문서 하나로 지금까지 진행 상황·기술적 결정과 근거·현재 결론·앞으로의 계획을 모두
파악할 수 있도록 정리했다. 팀 공유와 개인 포트폴리오 제작 양쪽에 쓸 수 있게 작성한다.

## 0. 요약

- 담당 업무: **양팔 로봇의 "물 따르기" 조작을 모방학습으로 구현**
- 데이터: 텔레옵으로 20 → 40 → 60개 에피소드까지 단계적으로 수집, 각 단계가 이전 단계를
  포함하도록(부분집합 관계) 설계해 데이터 양 효과를 깨끗하게 비교
- 모델 4종(ACT, SmolVLA, pi0, GR00T)을 데이터 2단계(20/40, 이후 60 추가)로 비교 실험
- **SmolVLA가 사실상 확정** — 데이터를 늘릴수록 꾸준히 개선되고, 실제 로봇에서 태스크를
  완수한 유일한 모델. 60개 학습 결과 eval_loss 0.1559까지 도달(20개 대비 약 39% 개선)
- ACT는 구조적 한계, pi0는 학습은 되지만 로컬 하드웨어로 실시간 제어가 불안정, GR00T는
  이 GPU로 학습 자체가 불가능 — 세 모델 모두 이유를 확인하고 실험 종료
- 하드웨어 사고 2건(그리퍼 Phase 반전, 오른쪽 그리퍼 토크 EEPROM 손상)을 원인까지 규명해
  해결
- 데이터 수집 파이프라인의 버그 3건(녹화 시작 프레임 밀림, 카메라 인덱스 뒤바뀜, 재녹화 키
  오작동)을 진단·해결
- 다음 단계: 정량 평가 체계 구축 → 조건 다양성 데이터 추가 → 실패 지점 재수집

## 1. 팀 전체 미션에서 내 위치

### 1.1 팀 목표 (4인)

세미휴머노이드형 양팔 로봇이 웹 요청을 받아 특정 위치로 이동하고, 물을 잔에 따른 뒤
그 잔을 로봇 본체에 실어 요청된 위치(예: 특정 테이블 번호)로 이동해 고객에게 건네는
전체 미션이다.

| 담당 | 역할 |
|---|---|
| 팀원 A | SLAM·자율주행(로봇 이동) |
| 팀원 B | 하드웨어 설계 |
| **장준서(본인)** | **조작 정책 — 양팔로 물 따르기(모방학습)** |
| 팀원 C | 비전 객체 인식 + 붓는 동안의 무게 변화 대응 기법 |

### 1.2 내 담당 범위

전체 미션 중 "왼팔로 컵을, 오른팔로 물통을 잡아 물을 따르는" 조작 구간을 맡고 있다.
현재는 이동(Nav2)·비전 기반 물체 탐지·무게 판정과 분리해서, **고정된 위치에 컵과
물통이 있는 상태에서의 붓기 조작 자체**를 먼저 모방학습으로 완성하는 데 집중하고
있다 — 전체 미션에 통합하기 전, 조작 자체의 성능을 독립적으로 검증하는 단계다.

## 2. 하드웨어 — 결정 사항과 사고 이력

### 2.1 그리퍼 선정

두 STL 후보를 실제로 뜯어보고 비교했다.

- **A (Ender_Follower_SO101.stl)**: SO-ARM100 저장소의 프린터 베드 크기에 맞춰 팔 전체
  부품 12개를 한 판에 몰아넣은 출력 플레이트다. 독립된 그리퍼 조 파일이 아니라, 팔 전체
  구조 부품 중 일부에 그리퍼 조가 포함된 형태다.
- **B (SO101_soft_fin.stl)**: XLeRobot 저장소의 Fin Ray(핀레이) 소프트 핑거 키트로,
  TPU95A로 출력해야 설계 의도(곡면을 감싸는 적응형 그립)가 성립한다.

5가지 재질 조합(A경질 / A전체TPU / A핑거만TPU / B경질 / B+TPU)을 비교한 결과,
**B(Fin Ray)+TPU95A가 잔(컵) 파지에 가장 이상적**이라고 판정했다 — 적응형 그립,
고마찰, 넓은 접촉면적이 이유다. B를 경질로 출력하면 내부 리브가 안 휘어 설계 의도가
완전히 무효화되고 오히려 구조적으로 더 약해져서 최악의 조합이었다.

오른쪽 그리퍼는 최종적으로 **ggao50 랙-피니언 방식**을 채택했으며, 닫힘 부하가 약
35%로 스톡 회전 죠(왼쪽에 사용)보다 큰 힘이 필요하다는 특성이 있다.

### 2.2 사고 1 — 그리퍼 Phase 레지스터 반전 (해결됨)

오른팔 그리퍼 서보(ID 6)가 어떤 목표를 줘도 열림 끝으로 달아나 레일 이탈이 4회
발생했다. 8개 가설을 순차 기각한 끝에 **Phase 레지스터(18번지)가 개체에 맞지 않는
값(12, 정답은 76)**이었다는 걸 확인했다. 76으로 수정 후 재부팅하니 즉시 정상화됐다.
상세 분석은 `docs/20260909_그리퍼_서보_Phase반전_사고분석.md`에 8개 가설의 기각
과정과 원본 EEPROM 덤프까지 남겨뒀다.

### 2.3 사고 2 — 오른쪽 그리퍼 토크 EEPROM 손상 (해결됨, 이번 세션)

오른쪽 그리퍼가 다른 관절보다 반응이 느리다는 걸 발견해 조사했다. 직접 EEPROM을
읽어보니 `Max_Torque_Limit=500`(정상 1000), `Protection_Current=250`(정상 320),
`Overload_Torque=25`(정상 80)로 **형제 관절의 절반 값**이 박혀 있었다.

원인은 코드 갭이었다 — `so_follower.py`의 `configure()`가 `gripper_protection=True`일
때 이 값들을 절반으로 낮추는 코드는 있지만, `False`로 되돌릴 때 **원래 값으로 복원하는
코드가 없었다.** 과거 어느 시점에 오른팔에도 실수로 protection이 걸렸던 적이 있었고,
그 흔적이 EEPROM에 영구히 남아있던 것이다. 실물 재조립 자체는 원인이 아니었고,
재조립으로 늘어난 마찰이 이미 낮았던 토크 상한과 겹치며 증상이 눈에 띄게 된 것으로
판단했다.

해결: 4개 레지스터(주소 16/28/36/48)를 직접 읽기→백업→쓰기→검증 순서로 형제 관절과
같은 값으로 복원했다. 조치 후 텔레옵에서 반응 속도 개선을 확인했다.

## 4. 모델 비교 실험

### 4.1 대상 모델과 선정 근거

직무(휴머노이드 모방학습 엔지니어) 채용 요건에 명시된 모델 위주로 골랐다.

| 모델 | 선정 이유 |
|---|---|
| ACT | 채용 요건 명시, 가벼운 비-VLA 베이스라인 |
| SmolVLA | LeRobot 내장 경량 VLA(약 4.5억 파라미터) |
| pi0 | 채용 요건 명시("OpenPi"), SmolVLA보다 큰 VLA |
| GR00T | 채용 요건 명시, 직무명(휴머노이드)과 직결 |

**제외**: Gemini Robotics(비공개 API라 파인튜닝 자체 불가), OpenVLA(70억 파라미터급,
8GB 로컬 GPU로 무리, 우대사항일 뿐 필수 아님)

### 4.2 데이터 개수

20 / 40 / 60개 3단계로 학습. 매 단계가 이전 단계를 포함(20⊂40⊂60).

### 4.3 결과표

| 실험 | 최선 eval_loss | 도달 스텝 | 종료 방식 | HF 체크포인트 |
|---|---|---|---|---|
| ACT-20 | 0.4000 (주1) | 2000 | 3250에서 조기중단 | `jun-seo/ACT_20E_2000S` |
| ACT-40 | 0.3674 | 3500 | 5000에서 조기중단 | `jun-seo/ACT_40E_3500S` |
| SmolVLA-20 | 0.2549 | 3000 | 3750에서 조기중단 (~39분) | `jun-seo/smallVLA_20E_3000S` |
| SmolVLA-40 | 0.2130 | 5500 | 7000에서 조기중단 (~71분) | `jun-seo/smallVLA_40E_5500S` |
| SmolVLA-60 | **0.1559** | 6500 | 8000에서 조기중단 | `jun-seo/smallVLA_60E_6500S` |
| pi0-20 | 0.3055 | 8500 | 10000스텝 완주 | `jun-seo/pi0_20E_8500S` |
| pi0-40 | 0.2778 | 9500 | 10000스텝 완주 | `jun-seo/pi0_40E_9500S` |
| GR00T-20/40 | — | — | 실행 불가 (4.2절) | — |

(주1) ACT-20은 `save_freq`(1000)와 `eval_steps`(250)가 안 맞아 진짜 최저점(step2500,
0.3908)의 체크포인트가 저장되지 않은 사례다. 이후 모든 실험은 `save_freq=eval_steps`로
통일해 같은 문제가 재발하지 않게 했다.

**공통 방법론**: 학습 중 eval_loss가 3번 연속(`eval_steps` 간격 기준) 무개선이면
자동으로 체크포인트를 저장하고 중단하는 조기중단 로직을 모든 실험에 동일 적용했다.
채택 체크포인트는 항상 "가장 최근"이 아니라 "eval_loss가 가장 낮았던 시점"으로
고른다.

### 4.4 SmolVLA — 데이터 양에 따른 추이

| 데이터 | 최선 eval_loss | 20개 대비 개선율 |
|---|---|---|
| 20개 | 0.2549 | — |
| 40개 | 0.2130 | 16.4% |
| 60개 | 0.1559 | 38.8% |

데이터가 늘수록 최종 성능이 꾸준히 개선될 뿐 아니라, 과적합 없이 더 오래(더 많은
스텝까지) 학습이 이어졌다 — 노이즈가 아니라 데이터 증가의 실제 효과로 해석하고 있다.

### 4.5 실제 로봇 롤아웃 결과 (정성적, 아직 정량 평가 전)

| 모델 | 관찰 |
|---|---|
| SmolVLA-20 | 초반 학습에 없던 방향으로 움직이다가, 중반부터 학습된 궤적으로 스냅되며 성공 |
| SmolVLA-40 | **처음부터 끝까지 이상 동작 없이 태스크를 완수한 첫 사례** |
| pi0-20/40 | 로컬 GPU(8GB)로는 추론이 너무 느려(1회 최대 7.4초) 실질적으로 실행 불가 |

**중요한 제약**: 위 결과는 전부 시행 1회짜리 정성 관찰이다. 정식 정량 평가(다회 반복,
성공률 기록)는 아직 진행 전이며, 다음 단계의 최우선 과제다(6절 참고).

### 4.6 GR00T — 학습 자체가 불가능했던 이유

백본(`nvidia/GR00T-N1.7-3B`)과 필요 게이트 모델(`nvidia/Cosmos-Reason2-2B`) 접근은
문제없었으나, 학습 가능 파라미터를 최소(LLM·비전 인코더 프리즈)로 줄여도 1B 이상
남아 서버 GPU(24GB)에서 `batch_size=1`조차 OOM이 났다. LoRA로 우회하려 했으나, 이
lerobot 버전은 "이미 파인튜닝된 체크포인트 위에서만 LoRA 적용 가능"하게 막혀 있어
처음부터 LoRA로 학습하는 경로 자체가 없다는 걸 확인하고 실험을 접었다.

## 5. 인프라

- **로컬(RTX 5050, 8GB)**: ACT 학습(batch=8), 가벼운 추론
- **원격 서버(RTX 4090, 24GB)**: SmolVLA·pi0·GR00T 학습 전부. SSH로 `ROBOT` 전용
  와이파이 통해 접속(자주 끊김 — 학습 자체는 `nohup`+`disown`으로 서버에서 독립 실행돼
  네트워크 끊김과 무관하게 계속 돎)
- **원격 서버의 lerobot 학습 스크립트에 조기중단 로직을 직접 패치**해 4.3절의 방법론을
  구현

### 5.1 pi0 서버 원격 추론 시도 (부분 성공)

pi0가 로컬에서 느려 실행 불가능했던 걸, **정책 연산은 서버에서, 로봇 제어는
로컬에서** 하는 방식(LeRobot 내장 `async_inference`)으로 우회 시도했다.

- SSH 터널로 포트를 네트워크에 노출하지 않고 연결(보안 고려)
- **속도 문제는 완전히 해결** — 추론 1회 130ms대(로컬 7초+ 대비 압도적)
- 그런데도 로봇이 "제자리에서 지 혼자 움직이는" 증상은 남음 — 속도가 아닌 다른 원인
  (액션 청크 블렌딩 로직 또는 전처리 불일치로 추정, 미해결)

상세는 `docs/20260923_pi0_서버원격추론_실험기록.md` 참고.

## 6. 현재 결론과 다음 단계

### 6.1 결론

**SmolVLA를 최종 모델로 잠정 확정**한다. 데이터를 늘릴수록 확실히·꾸준히 개선되고,
실제 로봇에서 완주한 유일한 사례다. ACT(구조적 한계)·pi0(하드웨어 제약으로 실시간
제어 불안정)·GR00T(학습 자체 불가)는 이유가 명확해 재시도할 필요가 없다.

### 6.2 다음 단계 (우선순위 순)

1. **정량 평가 체계 구축** — 고정 프로토콜로 SmolVLA 20/40/60 각 10회 롤아웃, 잡기/
   붓기/흘림 성공률 기록. 지금까지의 "성공" 판정은 전부 시행 1회짜리라 이게 최우선
   과제다.
2. **다양성 데이터 추가 수집** — 컵·물통 시작 위치/방향을 다양화한 별도 데이터셋으로
   일반화 성능 확인. 같은 조건 반복(현재 데이터)보다 다양성이 노력 대비 효과가 클
   것으로 예상.
3. **실패 지점 타겟 재수집** — 2번 평가에서 드러난 구체적 실패 패턴만 추가 수집·재학습.
4. (여유 되면) pi0 서버 브리지 문제 마무리, 또는 BC 이후 경량 RL 후처리 시도.

### 6.3 지금 당장은 고려하지 않는 것 — IK·시뮬레이션·강화학습

세 기법 모두 "지금 쓰는 방법(모방학습)이 한계에 부딪혔다는 증거가 나온 뒤에만" 검토
대상이다.

| 기법 | 검토 시점 |
|---|---|
| IK(역기구학) | end-to-end 모방학습이 기하학적으로 뻔한 구간(접근·복귀·배치)에서 일관성 없이 흔들릴 때 |
| 시뮬레이션 | 다양성 있는 실측 데이터로도 특정 조건에서 반복 실패가 남을 때 |
| 강화학습 | 정량 평가로 확정한 성능이 데이터를 더 넣어도 정체될 때 (평가 체계가 선행돼야 보상을 정의할 수 있음) |
