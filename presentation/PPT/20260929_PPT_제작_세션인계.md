## 2. 다음 세션이 바로 할 일

1. **`presentation/deck/HOLD_THE_FLOW_출정식.pptx`를 PowerPoint로 열어서 검수한다.** 코드로는 슬라이드 경계를 벗어나는 도형이 없다는 것만 확인했고, 텍스트가 박스 안에 자연스럽게 들어맞는지·글자 크기가 적절한지는 실제로 열어봐야 안다.
2. 고칠 점을 찾으면 **`presentation/deck/build_pptx.py`의 해당 `build_sNN()` 함수를 고치고** 아래 명령으로 재생성한다.
   ```bash
   cd presentation/deck
   python build_pptx.py
   ```
   (PowerPoint에서 직접 고쳐도 되지만, 그러면 다음에 스크립트를 다시 돌릴 때 그 수정이 사라진다 — 스크립트로 고치는 쪽을 기본으로 삼는다.)
3. 팀원 B(기구)·C(인지)의 이력·실적을 받으면 `build_s25()`에 채운다. 받기 전까지는 지어내지 않는다.

## 4. 디자인 시스템 (PPT.pdf에서 추출)

`build_pptx.py` 상단에 토큰으로 정의돼 있다.

| 요소 | 값 | 용도 |
|---|---|---|
| 남색(NAVY) | `#1A2E66` | 헤더 바, 파이프라인 박스, 인사이트 바 칩 |
| 크림 배경(CREAM) | `#F2EFE7` | 모든 콘텐츠 슬라이드 배경 (표지만 흰색) |
| 주황 강조(ORANGE) | `#DD8341` | 아이콘, 카드 왼쪽 강조선, 화살표 |
| 연한 파랑(LIGHT_BLUE) | `#DCE6F6` | 인사이트 바 오른쪽 박스, 표 강조 열 |
| 폰트 | 맑은 고딕(Malgun Gothic) | 전체 — Windows 기본 폰트라 폰트 깨짐 위험 없음 |

**표준 슬라이드 구조** (거의 모든 콘텐츠 슬라이드가 이 뼈대를 따른다):
1. 상단 남색 헤더 바 + 흰 굵은 제목 (eyebrow로 섹션 번호 표시, 예: "02 · 배경")
2. 헤드라인 — 검은 굵은 문장, 중앙 정렬
3. 본문 — 표/카드그리드/파이프라인/인용블록 중 하나
4. 하단 "주요 인사이트" 바 — 남색 칩(라벨) + 연한 파랑 박스(한 줄 요약)
5. 페이지 번호(중앙 하단)

재사용 가능한 컴포넌트 함수(`build_pptx.py`): `add_header`, `add_headline`, `add_insight`, `add_flow`(파이프라인), `add_flow_labeled`(phase별 PLANNED/ACT 색 구분), `add_columns`(번호 아이콘 3~4열), `add_cards_grid`(카드 그리드, 2~5열), `add_table`, `add_quote_block`(인용/통계 강조 박스), `add_badge`(사실등급 배지).

## 5. 사실등급 라벨 체계 — 반드시 유지할 것

SLAM 담당자 초안의 핵심 장치. 슬라이드에 적은 모든 수치 옆에 근거 등급을 배지로 붙인다. 근거 없이 확정처럼 보이는 문장을 쓰지 않기 위한 안전장치이자, 이 프로젝트/저장소 전체의 문화(`CLAUDE.md`: "구현 완료 주장은 재현 가능한 근거가 있을 때만 표시")와 일치한다.

| 배지 | 뜻 |
|---|---|
| `실차·1회` | 선행 JD-AMR 실제 공간 주행 기록 |
| `시뮬·1회` | Isaac Sim 5.1 시뮬레이션 1회 실행 |
| `코드·단위시험` | 코드·로컬 시험까지 완료, 실기체 실행 전 |
| `계획` | 아직 팀 합의 전, 앞으로 할 일 |

새 수치를 추가할 때는 반드시 이 중 하나를 붙인다.

## 6. 목차 구조 — 팀이 최종 합의한 11개 항목과 29장 매핑

팀 논의 결과 확정된 항목(순서는 발표 논리 흐름에 맞춰 재배열됨):

1. 개요(파이프라인 형식) → **2~3장**
2. 기술 개발 배경(필요성-기술/시장/사회/정책) → **4~7장** (각 관점 1장씩)
3. 핵심 문제 및 솔루션, 환경 분석(관련 기업 수행 현황) → **8~11장**
4. 개발 창의성 및 혁신성 → **12장**
5. 기술개발 목표·성과목표·목표 성능치(기간별·사람별) → **17~18장**
6. 핵심 포인트 → **19장**
7. 개발 추진 계획(추진체계·주차별·개인별·수행일정-시나리오 형식) → **20~21장**
8. 예상 난제와 해결 방안 → **22장**
9. 팀 우수성 및 수행실적(개인/팀 보유역량) → **23~27장**(5장: 이동·연결/연결·시뮬검증/조작정책/기구/인지 — 2026-09-29 이후 세션에서 5장으로 확장, 뒤 항목 슬라이드 번호는 +2 밀림, 부록 A/B/C 3장이 29장 뒤에 추가되어 최종 34장)
10. 기대 효과(적용범위-후속연계, 사업화 방향 실용성 어필) → **26~27장**
11. 보안/안전성 검증 및 조치 → **28장**

추가된 장(11개 항목엔 없지만 발표 흐름상 필요해서 넣음): 1(표지), 13(시뮬레이션 데모), 14(시스템 구조), 15~16(조작 전략), 29(마무리·멘토링 질문).

지난 세션에 만들었던 "필수/판단/제외" 항목 채택 판단(`docs/20260929_출정식_발표자료_준비_계획.md`)은 이미 이 11개 목록에 반영된 결과다 — 원천기술·IP현황·인증표준화·SWOT·기술이전전략은 팀 판단으로 제외됐다.

## 7. 청중과 톤

- 청중: **솔트룩스(CTO 참석), 위고로보틱스** 관계자. 기술 이해도 있음으로 가정 — 전문 용어를 풀어쓰지 않는다.
- 톤: 계획 중심 + 성과 일부. 현업에 맞게 쉽게 풀되, 근거 없는 과장은 하지 않는다(사실등급 라벨이 이걸 강제한다).
- 마무리(29장)의 멘토링 질문 2가지는 두 회사를 염두에 두고 설계됨 — "에이전트 계층의 경계"는 솔트룩스(에이전트·피지컬AI 사업 방향과 접점), "모바일 매니퓰레이터 현장 운용"은 위고로보틱스(AgileX 유통·모바일 매니퓰레이터 솔루션)를 겨냥한 것. 슬라이드엔 회사 이름을 직접 넣지 않았다 — 필요하면 발표 중 구두로만 언급.

### 9-4. 판단은 아직 열려 있음

**두 파일을 어떻게 합칠지는 아직 정해지지 않았다.** 이전 세션에서 "구조는 본인 버전 유지, 미디어는 팀원 버전에서 가져온다" 식의 특정 융합 방식을 제안했었는데, 이건 하나의 가능한 선택지였을 뿐 확정된 방침이 아니다. 다음 세션은 이 문서의 사실 정보(9-1~9-3)와 아래의 **이미 확정된 제약**만 참고해서, 그 안에서 가장 나은 방향을 스스로 판단하면 된다 — 반드시 이전에 제안됐던 특정 병합 방식을 따를 필요는 없다.

**이미 확정된 것(팀 결정 — 여기서부터 다시 논의하지 않는다):**
- 산출물은 PPT(.pptx). 웹 슬라이드로 되돌리지 않는다(0절).
- 목차의 큰 항목 11개와 그 순서는 팀이 합의했다(6절). 다만 그 11개 안에서 세부 슬라이드를 몇 장으로 나눌지, 개인 lane을 몇 장으로 할지 같은 **하위 구성**은 열려 있다.
- "예상 난제", "보안/안전성"은 팀이 필수 본문 항목으로 합의했다(5절) — 부록으로 격하하지 않는다.
- 사실등급 라벨(실차/시뮬/코드/계획) 체계는 유지한다(5절) — 이건 이 프로젝트 저장소 전체의 문화(`CLAUDE.md`)와 맞닿아 있어서 임의로 뺄 항목이 아니다.

**아직 열려 있는 것(다음 세션이 판단):**
- 디자인을 어느 쪽 기준으로 통일할지, 혹은 제3의 방향으로 갈지
- 미디어(영상 4개, 이미지 10장)를 어느 슬라이드에 어떻게 쓸지, 다 쓸지 일부만 쓸지
- 개인 lane 슬라이드 분량(본인 버전 3장 vs 팀원 버전 6장, 혹은 다른 배분)
- 두 파일의 문구·톤 중 어느 쪽을 더 살릴지
